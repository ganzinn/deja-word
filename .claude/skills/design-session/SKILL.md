# design-session

機能の仕様詰め・設計を、**トピック単位**で確定を積み上げながら進めるためのスキル。1 セッションで進めるトピック数は固定せず、コンテキスト使用量の見込みで継続を判断する（基準はセッション継続モード手順 7）。設計ドキュメントはハブ（README.md）＆スポーク（トピックファイル）構成で `docs/design/<機能名>/` に置き、セッション間の引き継ぎはハブに集約する。作業は本体の checkout ではなく機能ごとの起点 worktree で行う（「作業場所（起点 worktree）」節）。

## 引数

`$ARGUMENTS`

- 1 行目の最初のトークンが対象の機能名。kebab-case で、`docs/design/<機能名>/` のディレクトリ名になる
- 機能名より後に続くテキストがある場合は、ユーザーからの事前指示（目的・決定への回答・進め方の許可など）として扱う。事前指示が回答している事項は、改めて質問せずその内容を適用する
- 空（未指定）の場合: 進行状況の一覧（機能名・確定/全トピック数・次の推奨トピック）に「新しい機能の設計を始める」の選択肢を添えて提示し、選んでもらう。シリーズの把握は本体の checkout に依存せず行う: `git fetch origin main` の上で、進行中は作業ブランチ一覧（`git branch --list 'docs/*-design-plan'`）、マージ済みは `git ls-tree --name-only origin/main docs/design/` で把握し、ハブは `git show <作業ブランチまたは origin/main>:docs/design/<機能名>/README.md` で読む。新規を選んだ場合は機能名を聞いてから新規立ち上げモードへ進む

## 作業場所（起点 worktree）

設計シリーズの作業は本体の checkout では行わず、機能ごとの起点 worktree `../deja-word-worktrees/<機能名>` で行う（本体側で別の作業が進んでいても衝突しないため。命名族・ライフサイクルの共通定義は worktree スキル）。設計シリーズの入口である本スキルが起点 worktree の作成起点になる。**機能名が決まったらまず worktree を準備し**、以降のファイルの読み書き・調査委譲・コミットはすべて worktree の絶対パス配下で行う。

- 準備（worktree スキル）: `scripts/wt-new.sh <機能名> origin/main --branch docs/<機能名>-design-plan --no-install`。worktree `../deja-word-worktrees/<機能名>` が既にあればそのまま使う
- 保持: 起点 worktree は設計〜クローズ完了までフェーズ横断で保持する（ticket-split は同じ worktree・作業ブランチで続け、ticket-implement は同じ worktree でブランチを統合ブランチへ切り替える）。撤去はパイプライン終端の feature-close スキルが行う

## モード判別

起点 worktree を準備した上で、worktree 内に `docs/design/<機能名>/README.md` が**存在しなければ「新規立ち上げ」、存在すれば「セッション継続」**。

## 新規立ち上げモード

1. 目的・スコープをヒアリングする（何を作るか、アプリのコンセプトとの関係、MVP の範囲感）
2. トピック分割を提案して合意を取る。標準形は「01 要求 → 02 データモデル → 03 ロジック/アルゴリズム → 04 UI → 05 アーキテクチャ」＋機能固有トピック。**番号順 = 想定確定順**（要求が先、実装構成が後）。テスト戦略はアーキテクチャトピックに含める
3. [templates/hub.md](templates/hub.md) と [templates/topic.md](templates/topic.md) から `docs/design/<機能名>/` を生成する（プレースホルダ: 機能名・目的・トピック一覧）
4. **整合性レビュー（必須）**: 生成したハブ・雛形間でトピック分割の重複や抜け、目的・スコープの記述ブレがないか確認する
5. ハブの「次セッションの推奨トピック」を 01 にセットする。継続判断（セッション継続モード手順 7 と同じ見積もり基準）を満たすならそのまま 01 の議論に入ってよい（以降はセッション継続モードのフローに従う）

## セッション継続モード

1. ハブを読み、「次セッションの推奨トピック」と引き継ぎ事項を確認する。**読み込みはハブ＋対象トピック 1 ファイルに限定**する。他トピックの決定は対象トピックの「前提」再掲で足りるはずで、足りない場合も自分で全読みせず Explore エージェントに必要箇所の抽出を委譲する
2. 対象トピックの「前提」と「検討事項リスト」を起点に、必要なら Explore エージェントで既存コード・関連資料を並行調査する。委譲した調査と同じ対象を自分でも読み進めず、結果が返ってから使う（二重調査はコンテキストの無駄になる）
3. 論点ごとに進める:
   - 推奨案＋採用理由＋有力な却下案（1〜2 個）を提示する
   - ユーザー判断が必要な分岐（確定事項を覆す・トレードオフが拮抗・好みの問題）は AskUserQuestion で確認する。技術的に明確な答えがあるものは推奨で進めてよい
   - 決定をトピックファイルの「議論・決定」に記録する。**採用理由と却下案も必ず残す**。見出しは「決定 N: タイトル」形式で番号を振り、本文には「採用理由:」「却下した代替案:」のラベル付き行を置く（後続の実装チケットから `NN-xxx.md の決定 N` で安定参照し、理由・却下案を機械的に抽出できるようにするため）
   - 実コードの挙動・ADR の内容は決定に必要な範囲だけ引用し、引用した事実は記載前に裏取りする（行レベルの挙動説明を要求レベルのトピックへ持ち込まない。未検証の引用は突き合わせの指摘対象になり、修正の周回を増やす）
4. **整合性レビュー（必須）**: 仕様書・設計書に記載した後は、トピックの確定・未確定にかかわらず毎回必ず実施する。「記載 → レビュー → 修正」を独立したステップとして回してから次に進む。観点は後述の「整合性レビュー」セクション
5. トピック終了処理（トピックの区切りごと・/clear 前に必ず行う）:
   - トピックの状態行を更新する（`未着手` → `議論中` → `確定`）。確定時の表記は `状態: **確定**（YYYY-MM-DD）` で統一する（太字は状態語のみ、日付は太字の外）
   - ハブの確定事項サマリに結論を昇格する（各 1〜3 行。採用理由・議論過程・却下案は昇格しない）。「〜しない」型の決定でも理由は書かず、理由が気になる読み手は「→ [NN]」リンク先で確認できる
   - トピック状態表と「次セッションの推奨トピック」（引き継ぎ論点付き）を更新する
   - **確定した決定ごとに ADR 要否を判定し、要のものをハブの「ADR 引き継ぎ候補」に 1 行で追記する**（判定基準は [docs/adr/README.md](../../../docs/adr/README.md)「ADR に書く判断の線引き」。節が無いハブなら確定事項サマリの直後に作る）。形式は「- {新規 ADR のタイトル案 または 追記先の既存 ADR}（{NN} 決定 M）」で、既存 ADR の方針に対する例外は新規起票せず追記先として挙げる。`docs/design/` は実装後に削除するため、ここで拾い損ねた判断は却下案ごと消える。**起票は実装フェーズのチケットで行う**（決定と実装が同じ PR で main に入る）
   - **今回確定した決定のうち、後続トピックが依存するものは該当トピックファイルの「前提」に再掲を追記する**（次セッションが「ハブ＋対象トピック 1 ファイル」だけで始められる状態を維持するため。これを怠ると読み込み限定ルールが成立しない）。再掲の形式は「- {決定の要約}（{NN} 確定）。」で統一する。出典はトピック番号のみの「NN 確定」表記とする（ファイル間で表記が揃っていると、覆し時の波及箇所を機械的に探せる）。再掲は決定本文にある内容の要約に限り、決定に無い含意を足さない（足したくなった内容は未決事項であり、委譲先トピックの検討事項リストに書く）
   - トピック間で課す制約は「NN から MM への制約」と方向を明記する（双方が相手の決定として参照し合う循環参照を作らない）
   - 既存の確定事項を覆した場合は、元トピック・ハブ・その決定を「前提」に再掲している他ファイルをすべて更新する。覆しの経緯・旧決定の内容は元トピック（却下案・改訂履歴）にのみ残す。ハブのサマリと各ファイルの「前提」には現行の結論だけを書き、旧決定の値や改訂注記を持ち込まない（次セッションはサマリ・前提を現行の真実として読むため。履歴は元トピックと git log で追える）
   - **ハブ更新後にも整合性レビューを再実施する**（サマリと本文の不一致・覆した決定の反映漏れを確認）
   - **トピックを確定させる場合は、コミット前に独立エージェント突き合わせを実施する**（手順・収束条件は「整合性レビュー」の「独立エージェント突き合わせ」節）
6. コミットする（ユーザーに確認してから）。メッセージ形式: `<機能名> 設計: NN <トピック名>を確定`（議論中で終わる場合は `〜の論点を整理` 等、実態に合わせる）
7. コミット後、**次トピックの消費量を簡単に見積もり、対応後のコンテキスト使用量が 200K トークン前後に収まる見込みならユーザー確認なしで次トピックへ進む**（手順 1 から繰り返す。見積もりに迷うなら現在使用量 150K を一律閾値とする）。収まらない見込みなら /clear を案内し、次セッションでそのまま入力できるコマンド（例: `/design-session <機能名>`）を提示する
8. **全トピック確定時（設計完了セッション）**: ハブに `## 実装への引き継ぎ` セクションを追記してから設計シリーズを閉じる。後続のチケット分割スキルが全トピックを読み直さずに開始できるための棚卸しとして、以下を書く:
   - 変更対象の一覧（スキーマ変更・マイグレーション／新規モジュール・ファイル／既存ファイルの変更／UI コンポーネント／既存ドキュメントの記述更新 — 機能が変える挙動・用語に触れる `docs/reference/naming-book.md`・`docs/adr/`・`docs/features/` を grep し、実装後に虚偽・矛盾になる記述を変更対象に含める）。**「ADR 引き継ぎ候補」の各行も ADR ファイル（新規起票・既存への追記）として変更対象に挙げる**（候補が 1 件も無い場合は、判定した上で無しと明記する）
   - 着手順序のヒント（共有基盤 → 機能の依存方向。例: スキーマ → 純関数 → UseCase → UI。並行実装時に競合しやすい共有物を明示する）
   - テスト戦略の要点（チケットの完了条件に転記できる粒度）
   - チケット分割は ticket-split スキルで行う旨のポインタ（チケットの置き場は `docs/plan/<機能名>/`、形式は ticket-split 側で定義）

   追記後は整合性レビュー＋独立エージェント突き合わせを実施してからコミットする（メッセージ例: `<機能名> 設計: 実装への引き継ぎを追記`。手順 5〜6 の終了処理と同時なら 1 コミットでよい）。設計完了時点では PR を作らない（作業ブランチのままチケット分割へ進み、ticket-split 完了時に設計＋計画を一括で PR にする）。ユーザーへの案内はそのまま入力できる形で提示する: `/ticket-split <機能名>`

## 整合性レビュー（必須）

ドキュメントへ記載するたびに、書いた内容を「これから実装する人」の目で読み直し、以下を探す。1 件でも見つかれば修正してから次の論点・終了処理へ進む:

- **成立しない記述**: その情報をどこから得るのか説明できない値・処理がないか（例: セッション状態を持たないのにサーバーで導出するとした値）
- **二重定義・冗長な入力**: 同じ情報を 2 経路で受け取って食い違う余地がないか（例: クライアント指定の範囲と、サーバー計算の実効範囲）
- **決定間の矛盾**: 同一ファイル内の決定同士、および他トピックの確定事項（「前提」の再掲・ハブのサマリ）との矛盾
- **不正確な説明**: 例示・括弧書き・分岐条件が実際の挙動と一致しているか（例: 「競合」と「再送」の分類の取り違え）
- **曖昧なシグネチャ・未定義の用語**: 引数の有無・戻り値・呼び出し回数が一意に読めるか。正常系しか書いていない処理がないか（例: 削除耐性が片方の経路にしか書かれていない）
- **昇格漏れ・反映漏れ**: ハブのサマリ・状態表・他ファイルの「前提」が今回の決定と一致しているか

セキュリティ境界（認証・認可・データ所有・外部入出力）に触れるトピックでは、上記に加えて [docs/reference/security-design-checklist.md](../../../docs/reference/security-design-checklist.md) を通し、前提を破る設計は明示的な決定として記録する。

### 独立エージェント突き合わせ（トピック確定時）

セルフレビューだけでは生成時の思い込みによる見落とし（廃止対象に付随する型・テスト・コメントの列挙漏れ、決定間の表記ずれ等）が残るため、**トピック確定時（コミット前）に、生成コンテキストを持たないエージェントへ成果物だけを渡して突き合わせさせる**:

- Explore エージェントに [templates/review-prompt.md](templates/review-prompt.md) の雛形でレビューを依頼する（対象: ハブ＋確定対象トピックファイル。必要なら「前提」の出典トピックも。指摘には重要度 高/中/低 を付けさせる）
- 削除・廃止を宣言した既存要素（関数・型・画面等）がある場合は、それに付随する要素（派生型・テスト・コメント・呼び出し箇所）の扱いが決定に含まれているかも検証させる
- 指摘が返ったら修正し、再チェックを依頼する。**再チェックは差分検証**とする: 雛形の「差分検証」段落で前回の指摘一覧と修正内容を渡し、検証範囲を「修正の反映確認＋修正で新たに入った記述」に限定する（裏取り済みの事実を全文再検証させない）
- **再チェックは最大 2 回（初回を含め計 3 周）**。指摘が尽きたらコミットへ進む。3 周で尽きない場合は、残る指摘のうち重要度 中以上のみ修正し、低は許容してコミットへ進む。許容した指摘はユーザーに理由とともに報告する

## 後続工程との接続

設計完了後は「ticket-split スキル（PR 単位のチケットを `docs/plan/<機能名>/` に生成、優先順位・依存関係を記載）→ ticket-implement スキル（worktree 並行実装）→ feature-close スキル（ADR 引き継ぎの確認・設計/計画ドキュメントの削除・worktree 撤去）」へ続く。design-session が後続スキルに保証する成果物の契約:

- ハブ（`docs/design/<機能名>/README.md`）が唯一の入口。トピック状態表が全行「確定」かつ「実装への引き継ぎ」セクションがあれば設計完了
- 恒久的に残す判断は「ADR 引き継ぎ候補」に列挙済みで、「実装への引き継ぎ」の変更対象一覧に ADR ファイルとして反映されている
- 確定事項サマリ＋「実装への引き継ぎ」セクションだけでチケット分割を開始できる（詳細が必要な場合のみ該当トピックの「決定 N」を参照する）
- 各決定は `NN-xxx.md` の「決定 N: タイトル」見出しで安定参照できる

## 注意事項

- トピックの途中でコンテキスト使用量が嵩み、確定まで届かない見込みになったら、無理に進めず終了処理をして /clear を促す
- 次セッション・後続工程の案内は、ユーザーがコピーしてそのまま入力できるコマンド形式（`/design-session <機能名>`、`/ticket-split <機能名>`）で提示する。オプションの解説は聞かれるまで並べない
- ハブには結論のみを書く。議論の過程・却下案・採用理由はトピックファイルに残す
- 実装フェーズの計画は `docs/plan/` の管轄。このスキルおよび `docs/design/` では扱わない

## スキル終了時の改善提案

セッションを閉じる報告（最終報告・PR 作成後の報告・/clear 案内）の際、今回の実行で得た学びから本スキルまたはパイプライン隣接スキルの改善候補があれば提案する。提案するのは、個別機能の事情に閉じない汎用性があり、スキルの成果物品質・効率への効果が大きいものだけ（実行手順に落ちない一般論は提案せず、該当が無ければ省略する）。反映はこのセッションでは行わず、ユーザー合意の上で別途スキル改善の PR として行う。
