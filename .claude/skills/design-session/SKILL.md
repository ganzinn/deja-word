# design-session

機能の仕様詰め・設計を、コンテキストを使い切らないよう**セッション単位（原則 1 セッション 1 トピック）**で進めるためのスキル。設計ドキュメントはハブ（README.md）＆スポーク（トピックファイル）構成で `docs/design/<機能名>/` に置き、セッション間の引き継ぎはハブに集約する。

## 引数

対象の機能名: `$ARGUMENTS`

- 機能名は kebab-case で、`docs/design/<機能名>/` のディレクトリ名になる
- 上が空（未指定）の場合: `docs/design/` 配下の各ハブのトピック状態表を確認し、進行状況の一覧（機能名・確定/全トピック数・次の推奨トピック）に「新しい機能の設計を始める」の選択肢を添えて提示し、選んでもらう。新規を選んだ場合は機能名を聞いてから新規立ち上げモードへ進む

## モード判別

`docs/design/<機能名>/README.md` が**存在しなければ「新規立ち上げ」、存在すれば「セッション継続」**。

## 新規立ち上げモード

1. 目的・スコープをヒアリングする（何を作るか、アプリのコンセプトとの関係、MVP の範囲感）
2. トピック分割を提案して合意を取る。標準形は「01 要求 → 02 データモデル → 03 ロジック/アルゴリズム → 04 UI → 05 アーキテクチャ」＋機能固有トピック。**番号順 = 想定確定順**（要求が先、実装構成が後）。テスト戦略はアーキテクチャトピックに含める
3. [templates/hub.md](templates/hub.md) と [templates/topic.md](templates/topic.md) から `docs/design/<機能名>/` を生成する（プレースホルダ: 機能名・目的・トピック一覧）
4. **整合性レビュー（必須）**: 生成したハブ・雛形間でトピック分割の重複や抜け、目的・スコープの記述ブレがないか確認する
5. ハブの「次セッションの推奨トピック」を 01 にセットする。時間があればそのまま 01 の議論に入ってよい（以降はセッション継続モードのフローに従う）

## セッション継続モード

1. ハブを読み、「次セッションの推奨トピック」と引き継ぎ事項を確認する。**読み込みはハブ＋対象トピック 1 ファイルに限定**する。他トピックの決定は対象トピックの「前提」再掲で足りるはずで、足りない場合も自分で全読みせず Explore エージェントに必要箇所の抽出を委譲する
2. 対象トピックの「前提」と「検討事項リスト」を起点に、必要なら Explore エージェントで既存コード・関連資料を並行調査する
3. 論点ごとに進める:
   - 推奨案＋採用理由＋有力な却下案（1〜2 個）を提示する
   - ユーザー判断が必要な分岐（確定事項を覆す・トレードオフが拮抗・好みの問題）は AskUserQuestion で確認する。技術的に明確な答えがあるものは推奨で進めてよい
   - 決定をトピックファイルの「議論・決定」に記録する。**採用理由と却下案も必ず残す**。見出しは「決定 N: タイトル」形式で番号を振る（後続の実装チケットから `NN-xxx.md の決定 N` で安定参照するため）
4. **整合性レビュー（必須）**: 仕様書・設計書に記載した後は、トピックの確定・未確定にかかわらず毎回必ず実施する。「記載 → レビュー → 修正」を独立したステップとして回してから次に進む。観点は後述の「整合性レビュー」セクション
5. セッション終了処理（/clear 前に必ず行う）:
   - トピックの状態行を更新する（`未着手` → `議論中` → `確定`、日付付き）
   - ハブの確定事項サマリに結論を昇格する（各 1〜3 行。議論過程・却下案は昇格しない）
   - トピック状態表と「次セッションの推奨トピック」（引き継ぎ論点付き）を更新する
   - **今回確定した決定のうち、後続トピックが依存するものは該当トピックファイルの「前提」に再掲を追記する**（次セッションが「ハブ＋対象トピック 1 ファイル」だけで始められる状態を維持するため。これを怠ると読み込み限定ルールが成立しない）
   - 既存の確定事項を覆した場合は、元トピック・ハブ・その決定を「前提」に再掲している他ファイルをすべて更新する
   - **ハブ更新後にも整合性レビューを再実施する**（サマリと本文の不一致・覆した決定の反映漏れを確認）
6. コミットする（ユーザーに確認してから）。メッセージ形式: `<機能名> 設計: NN <トピック名>を確定`（議論中で終わる場合は `〜の論点を整理` 等、実態に合わせる）
7. **全トピック確定時（設計完了セッション）**: ハブに `## 実装への引き継ぎ` セクションを追記してから設計シリーズを閉じる。後続のチケット分割スキルが全トピックを読み直さずに開始できるための棚卸しとして、以下を書く:
   - 変更対象の一覧（スキーマ変更・マイグレーション／新規モジュール・ファイル／既存ファイルの変更／UI コンポーネント）
   - 着手順序のヒント（共有基盤 → 機能の依存方向。例: スキーマ → 純関数 → UseCase → UI。並行実装時に競合しやすい共有物を明示する）
   - テスト戦略の要点（チケットの完了条件に転記できる粒度）
   - チケット分割は ticket-split スキルで行う旨のポインタ（チケットの置き場は `docs/plan/<機能名>/`、形式は ticket-split 側で定義）

## 整合性レビュー（必須）

ドキュメントへ記載するたびに、書いた内容を「これから実装する人」の目で読み直し、以下を探す。1 件でも見つかれば修正してから次の論点・終了処理へ進む:

- **成立しない記述**: その情報をどこから得るのか説明できない値・処理がないか（例: セッション状態を持たないのにサーバーで導出するとした値）
- **二重定義・冗長な入力**: 同じ情報を 2 経路で受け取って食い違う余地がないか（例: クライアント指定の範囲と、サーバー計算の実効範囲）
- **決定間の矛盾**: 同一ファイル内の決定同士、および他トピックの確定事項（「前提」の再掲・ハブのサマリ）との矛盾
- **不正確な説明**: 例示・括弧書き・分岐条件が実際の挙動と一致しているか（例: 「競合」と「再送」の分類の取り違え）
- **曖昧なシグネチャ・未定義の用語**: 引数の有無・戻り値・呼び出し回数が一意に読めるか。正常系しか書いていない処理がないか（例: 削除耐性が片方の経路にしか書かれていない）
- **昇格漏れ・反映漏れ**: ハブのサマリ・状態表・他ファイルの「前提」が今回の決定と一致しているか

## 後続工程との接続

設計完了後は「ticket-split スキル（PR 単位のチケットを `docs/plan/<機能名>/` に生成、優先順位・依存関係を記載）→ ticket-implement スキル（worktree 並行実装）」へ続く。design-session が後続スキルに保証する成果物の契約:

- ハブ（`docs/design/<機能名>/README.md`）が唯一の入口。トピック状態表が全行「確定」なら設計完了
- 確定事項サマリ＋「実装への引き継ぎ」セクションだけでチケット分割を開始できる（詳細が必要な場合のみ該当トピックの「決定 N」を参照する）
- 各決定は `NN-xxx.md` の「決定 N: タイトル」見出しで安定参照できる

## 注意事項

- 1 セッションで複数トピックを無理に進めない。コンテキストが嵩んだら、終了処理（ハブ更新＋コミット）をして /clear を促す
- ハブには結論のみを書く。議論の過程・却下案・採用理由はトピックファイルに残す
- 実装フェーズの計画は `docs/plan/` の管轄。このスキルおよび `docs/design/` では扱わない
