# feature-close

`design-session（docs/design）→ ticket-split（docs/plan）→ ticket-implement（実装）→ feature-close（クローズ）` パイプラインの終端。統合 PR のマージ後に実行し、設計・計画ドキュメントを畳んで機能の作業資源を片付ける。

やることは 2 つ: **恒久的な判断が ADR に残っている状態にすること**と、**役目を終えた `docs/design/` / `docs/plan/` を削除すること**。ADR 要否の判定は design-session（決定時）とドキュメントチケット（起票）で済んでいる前提で、本スキルは削除前の安全網として再確認する。

## 引数

対象の機能名: `$ARGUMENTS`

- 機能名は `docs/design/<機能名>/` のディレクトリ名
- 未指定の場合: `git fetch origin main` の上で `git ls-tree --name-only origin/main docs/design/` の各機能について plan ハブ（`git show origin/main:docs/plan/<機能名>/README.md`）のチケット一覧表を読み、全行「完了」のものをクローズ候補として提示し、選んでもらう

## 前提条件チェック

- 統合 PR がマージ済みであること（`gh pr list --state merged --head feature/<機能名>`）
- plan ハブのチケット一覧表が**全行「完了」**であること。未完了なら中断し ticket-implement スキルへ誘導する
- チケット DoD の手動確認が完了していること（各チケットの「実装メモ」で確認する。未実施が残っていればユーザーに実施可否を確認してから進む）

## 作業場所（起点 worktree）

起点 worktree `../deja-word-worktrees/<機能名>` をそのまま使い、クローズフェーズのブランチへ切り替える（worktree スキル「フェーズ移行」）:

```sh
git fetch origin main
git switch -c chore/<機能名>-cleanup origin/main
```

起点 worktree が残っていない場合は `scripts/wt-new.sh <機能名> origin/main --branch chore/<機能名>-cleanup`（worktree スキル）で用意する。`pnpm format` を使うため `--no-install` は付けない。以降の読み書き・コミットはすべて worktree の絶対パス配下で行う。

## 手順

1. **棚卸し**: `docs/design/<機能名>/` と `docs/plan/<機能名>/` の**全ファイル**（チケットの「実装メモ」を含む）を読み、決定を「ADR へ移す / コードで足りる / 既に受け皿がある」に分類する。基準は [docs/adr/README.md](../../../docs/adr/README.md)「ADR に書く判断の線引き」。設計ハブの「ADR 引き継ぎ候補」と実際に起票済みの ADR を突き合わせ、**未起票の候補**と**候補に挙がっていないが基準を満たす判断**を洗い出す
   - 計画にしか無い運用ノウハウ（再現手順・撮影や検証の前提条件）は、コード側のコメント・`docs/ops/` に受け皿があるかを確認する。無ければ受け皿へ移してから削除する
2. **独立エージェント突き合わせ（削除前・必須）**: 生成コンテキストを持たない Explore エージェントに、削除対象のファイル一式と現行のコード・関連 ADR を渡し、次の 2 方向を重要度付きで列挙させる。指摘を手順 1 の分類へ反映してから次へ進む
   - **削除で失われるもの**: 判断・運用ノウハウのうち、コードにも ADR にも他のドキュメントにも残らないもの
   - **削除で壊れる・虚偽のまま残るもの**: 削除対象を指しているコード・ドキュメントの参照と、実装メモが「スコープ外」「後続で直す」として残したまま是正されていない記述
3. **起票**（未起票分がある場合）: `docs/adr/README.md` の運用ルール（採番は `origin/main` で最新 ID を確認）に従って起票し、該当テーマ節の一覧に登録する。「背景」に設計ドキュメントが削除済みで本 ADR が長期の引き継ぎ先である旨、「根拠」に統合 PR 番号を書く。**削除する `docs/design/` へのリンクは張らない**
4. **参照更新（該当があれば）**: 削除対象ディレクトリ外からの参照を**機能名と削除するファイル名の両方**で探し（コードコメントは機能名を含まず、トピックのファイル名だけで参照していることがある）、リンク切れになるものと「削除予定」表記を「削除済み」へ更新する

   ```sh
   grep -rn "<機能名>" --include='*.md' --include='*.ts' --include='*.tsx' . --exclude-dir=node_modules
   grep -rn "<削除するファイル名>" src/ prisma/ scripts/ docs/ .claude/
   ```
5. **削除と PR**: `git rm -r docs/design/<機能名> docs/plan/<機能名>` → `pnpm format` → コミット → push → `gh pr create`。**PR 本文には「何を ADR に移し、何はコードで足りると判断したか」を分類の結果とともに書く**（削除の妥当性はこの言語化でしかレビューできない）。手順 4 の該当有無と、運用ノウハウの受け皿確認の結果も添える
6. **マージ後**: worktree スキル「機能完了時の一括撤去」で起点 worktree と関連ブランチ（`chore/<機能名>-cleanup` / `feature/<機能名>` / `docs/<機能名>-design-plan` と残存物）を撤去する。これがパイプライン全体の終端

## 注意事項

- **ADR 起票と削除は 1 PR にまとめる**。レビュアーが「何が消えて、何が引き継いだか」を同じ diff で見られる状態にする
- 削除するのは機能ディレクトリだけでよい（`docs/design/` / `docs/plan/` 自体が空になってもそのままでよい。git は空ディレクトリを追跡しない）
- 統合 PR に含まれなかった実装上の宿題（別途対応と判断したもの）が実装メモに残っていれば、issue 化してから削除する

## スキル終了時の改善提案

セッションを閉じる報告（PR 作成後の報告・撤去完了報告）の際、今回の実行で得た学びから本スキルまたはパイプライン隣接スキルの改善候補があれば提案する。提案するのは、個別機能の事情に閉じない汎用性があり、スキルの成果物品質・効率への効果が大きいものだけ（実行手順に落ちない一般論は提案せず、該当が無ければ省略する）。反映はこのセッションでは行わず、ユーザー合意の上で別途スキル改善の PR として行う。
