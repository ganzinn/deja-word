# ticket-split

`design-session（docs/design）→ ticket-split（docs/plan）→ ticket-implement（実装）` パイプラインの中間工程。設計完了済み機能のハブ（`docs/design/<機能名>/README.md`）の「確定事項サマリ」＋「実装への引き継ぎ」から、PR 単位のチケット群を `docs/plan/<機能名>/` に生成する。

## 引数

対象の機能名: `$ARGUMENTS`

- 機能名は kebab-case で、`docs/design/<機能名>/` と同名のディレクトリを `docs/plan/` に作る
- 上が空（未指定）の場合: `docs/design/` 配下の各ハブを確認し、機能ごとに「設計完了済みか（トピック状態表が全行確定＋実装への引き継ぎあり）」「`docs/plan/<機能名>/` が存在するか」の一覧を提示して選んでもらう

## 前提条件チェック

設計ハブのトピック状態表が**全行「確定」**かつ**「実装への引き継ぎ」セクションが存在**することを確認する。満たさなければ中断し、design-session スキルで設計を完了させるよう誘導する。

**読み込み範囲の限定**: 設計側で読むのはハブの「確定事項サマリ」＋「実装への引き継ぎ」のみ。トピックファイル（`NN-xxx.md`）は全読みせず、チケット本文の生成時に必要な「決定 N」だけを Explore エージェントで抽出する。

## モード判別

`docs/plan/<機能名>/README.md` が**存在しなければ「新規分割」、存在すれば「見直し・追加」**。

セッションモデルは**原則 1 セッション完結**（チケット分割は分割案全体を一度に眺めないと粒度・依存・抜けを判断できないため、トピック積み上げ型にしない）。途中でコンテキストが嵩んだ場合のフォールバックは「注意事項」を参照。

## 新規分割モード

1. 設計ハブの「確定事項サマリ」「実装への引き継ぎ」を読む（変更対象の一覧・着手順序のヒント・テスト戦略の要点が分割の素材）
2. **分割案ドラフトを表で提示する**: チケット名・概要 1 行・作成/変更ファイル・依存チケット・規模感。粒度は「チケット粒度ガイドライン」に従う
3. 合意を取る。分割の切り方・順序などトレードオフが拮抗する点は AskUserQuestion で確認する。技術的に明確な点は推奨で進めてよい
4. [templates/plan-hub.md](templates/plan-hub.md) から `docs/plan/<機能名>/README.md` を生成する
5. チケットごとに、本文に必要な「決定 N」の詳細を Explore エージェントで設計トピックから抽出し、[templates/ticket.md](templates/ticket.md) から `NN-<チケット名>.md` を生成する（記載ルールは「チケット自己完結の記載ルール」）。記載のたびにセルフレビュー（観点は「整合性レビュー」）を回す
6. **全体整合性チェック（必須）**: チケット一式＋plan ハブの生成が終わったら、独立エージェントによる突き合わせチェックを実施する（手順は「整合性レビュー」の「全体整合性チェック」）。指摘ゼロ（または意図的に許容すると判断した指摘のみ）になるまで「修正 → 再チェック」を繰り返してから次へ進む
7. コミットする（ユーザーに確認してから）。**設計シリーズの作業ブランチ `docs/<機能名>-design-plan` 以外のブランチ（main 含む）にいる場合は、同ブランチを checkout（無ければ作成）してからコミットする**（main へ直接コミットすると、マージ前に main が進んで別作業がブロックされるため）。メッセージ形式: `<機能名> 計画: チケット分割（N 件）`
8. **PR を作成する（ユーザーに確認してから）**: チケット分割の完了で設計〜計画のドキュメントシリーズが閉じるため、作業ブランチを push して設計＋計画を一括レビューする PR を作成する。マージ後の実装着手の案内は、そのまま入力できる形で提示する: `/ticket-implement <機能名>`（オプションの解説は聞かれるまで並べない）

## 見直し・追加モード

用途: (a) 未生成チケットの続き生成、(b) 実装中に発覚した追加チケット、(c) 設計改訂（design-session で確定事項が覆った場合）の反映、(d) 依存・順序の組み替え。

1. plan ハブ（`docs/plan/<機能名>/README.md`）を読む
2. 影響チケットを特定する（チケット一覧表の依存列から逆引き。設計改訂の反映なら、覆った決定を「前提」に再掲しているチケットを探す）
3. 修正・追加する（記載のたびにセルフレビューを回す）
4. **全体整合性チェック（必須）**: 変更が複数チケットや plan ハブに及ぶ場合は新規分割モードと同じ独立エージェントチェックを実施する。1 チケット内に閉じる軽微な修正はセルフレビューのみでよい
5. コミットする（ユーザーに確認してから）。**main にいる場合は作業ブランチ（`docs/<機能名>-design-plan` がマージ済みで消えていれば例: `docs/<機能名>-plan-update`）を作成してからコミットし、PR を作成する**（main へ直接コミットしない。実装フェーズの統合ブランチ上で計画を見直している場合はそのブランチのままでよい）。メッセージ形式: `<機能名> 計画: チケット NN を追加` 等、実態に合わせる

ステータス更新（着手・PR 作成・マージ）だけの作業は本スキルを起動せず、実装セッション側が plan ハブの運用ルールに従って行う。

## チケット粒度ガイドライン（PR 単位）

- **1 チケット = 1 PR = 1 ブランチ**。依存チケットのマージ後、単独でマージ可能であること。ticket-implement のデフォルト（単一ブランチ統合モード）では「1 チケット = 統合ブランチへの 1 squash コミット」「PR は機能全体で 1 つ」と読み替える — 粒度・依存・自己完結の判断基準は両モードで同じ
- レビュー 1 回で読み切れるサイズ（目安: テスト込みで差分数百行）
- 各チケットはテストを内包する。設計ハブの「テスト戦略の要点」を該当チケットの完了条件に転記する（テスト規約は AGENTS.md）
- マージ後の中間状態でもアプリを壊さない（未参照モジュールの先行追加は可。UI への最終配線は終端チケットに寄せる）
- 依存方向は設計ハブの「着手順序のヒント」に従う
- **同一ファイルを複数チケットが触る分割は避ける**。避けられない共有物は plan ハブの「共有物・競合点」に明示し、直列依存にするか着手順序を指定する

## 優先順位と依存関係の表現

- **ファイル名番号 = 推奨着手順（優先順位）**。別軸の優先度フィールドは持たない（依存関係がほぼ順序を決めるため）
- **依存関係は plan ハブのチケット一覧表＋依存関係図が一次情報**。各チケットの「依存チケット」セクションに再掲する（ハブ＋スポーク再掲の二重化。整合性レビューで一致を検査する）
- 後続の並行実装スキルは plan ハブだけで「依存が解決済みの未着手チケット集合」を判定できる状態を保つ

## チケット自己完結の記載ルール

原則: **実装セッションは「plan ハブ＋対象チケット 1 ファイル」だけで実装を完結できる**。

- **再掲するもの（具体値で書く）**: スキーマ定義の具体形、関数シグネチャ、エッジケース・縮退仕様、enum 値、エラーマップ、テストの検証観点。各再掲項目の末尾に出典参照を必ず付ける: `（[02-data-model.md](../../design/<機能名>/02-data-model.md) 決定 3）` — design-session が保証する「決定 N」見出しへの安定参照を使う
- **参照のみで済ませるもの**: 採用理由・却下案・議論過程（実装に不要。必要なら参照先を読む）
- 設計書の全文転記はしない（設計改訂時の同期コストとチケット肥大を避ける。再掲は「実装に必要な決定内容」に限る）

## ステータス運用（実装フェーズの規約）

- 状態遷移: `未着手` → `実装中` → `完了`（日付付き）。状態値はこの 3 つから増やさない。「実装中」「完了」の詳細な意味と PR 列の記載タイミングは実装モードで異なり、plan ハブの「ブランチ・PR 運用」に両モードの読み替えを定義する（単一ブランチ統合モード: 完了 = 統合ブランチへのマージ、PR 列は統合 PR 作成時に一括記載。チケット単位 PR モード: PR 作成済み・未マージは「実装中」＋PR リンク、完了 = PR マージ）
- 更新責務: **実装セッション（通常は ticket-implement スキル）が、着手時・PR 作成時・マージ時に、plan ハブの一覧表とチケット冒頭の状態行の両方を更新する**。本スキルは規約を定義するだけで、日常のステータス更新では起動しない
- 実装セッションは、計画との差分・後続チケットへの申し送りをチケットの「実装メモ」に記入してよい

## 整合性レビュー（必須）

2 段階で行う。**セルフレビュー**は記載のたびに、**全体整合性チェック**はチケット一式の生成・修正が終わったあとに実施する。

共通の観点:

- **網羅性（抜け漏れ）**: 設計ハブ「実装への引き継ぎ」の変更対象一覧の各項目が、いずれか 1 つのチケットに割り当てられているか。確定事項サマリの各決定が然るべきチケットに反映されているか
- **重複**: 同一ファイルの作成を 2 チケットが宣言していないか。共有ファイルの変更が plan ハブの「共有物・競合点」に載っているか
- **依存の健全性**: 循環がないか。依存先の成果物を本当に使うか（過剰依存は並行性を殺す）。使うのに依存宣言がない抜けがないか。番号順と依存関係が矛盾していないか
- **設計との不一致（矛盾）**: チケットに再掲した決定内容が参照元の「決定 N」と一致するか（転記ミス検査）。チケット間で同じ事項の記載が食い違っていないか
- **自己完結性**: 「これから実装する人」の目で、チケット単体（＋plan ハブ）だけで着手できるか。未定義の用語・出典不明の値がないか
- **二重化の同期**: plan ハブの一覧表とチケットの「依存チケット」「状態」が一致するか
- **削除・廃止の後始末**: チケットが削除・廃止を宣言した識別子の残存参照（import・テストの describe・派生型・陳腐化するコメント）に対する削除・更新指示が、いずれかのチケットにあるか

### セルフレビュー（記載のたび）

チケット・ハブへ記載するたびに「記載 → レビュー → 修正」を独立したステップとして回す。上記観点のうち、書いたファイルとその突き合わせ先（再掲の出典「決定 N」・plan ハブの対応行）だけで検査できるもの（設計との不一致・自己完結性・二重化の同期）を中心に確認する。

### 全体整合性チェック（生成完了後・独立エージェント）

生成した本人のセルフレビューでは思い込みによる見落としが残るため、**生成コンテキストを持たないエージェントに成果物だけを渡して突き合わせさせる**。観点が異なる 3 つのチェックを並行で依頼する:

1. **網羅性・重複チェック**（Explore エージェント）: 設計ハブの「確定事項サマリ」「実装への引き継ぎ」と `docs/plan/<機能名>/` 全ファイルを読み、(a) 変更対象一覧の各項目 → 担当チケットの対応表を作らせて未割当・二重割当を検出、(b) 確定事項のうちどのチケットにも反映されていないものを列挙、(c) 依存の循環・番号順との矛盾・plan ハブ一覧表とチケット記載の不一致を検出
2. **転記一致・自己完結チェック**（Explore エージェント）: 各チケットの「前提（設計決定の再掲）」の出典参照（`0X-xxx.md` 決定 N）を実際に開き、再掲内容が参照元の決定と一致するか・出典のない値がないかを検証する。あわせて「これから実装する人」の目で各チケットを読み、チケット単体（＋plan ハブ）だけで着手できない箇所（未定義の用語・欠けた前提）を列挙する（自己完結性）
3. **削除・廃止対象の参照残りチェック**（Explore エージェント）: チケットが削除・廃止を宣言している識別子（関数・型・スキーマ・enum 値等）をリポジトリ全体で grep し、検出された全参照箇所（import・テストの describe・派生型・陳腐化するコメントを含む）に対して、いずれかのチケットに削除・更新指示が対応しているかを検証。指示のない参照残りは担当チケットへの追記漏れとして扱う

指摘が返ったら修正し、修正が複数ファイルに及んだ場合は再チェックする。**指摘ゼロ（または意図的に許容すると判断した指摘のみ）になるまで繰り返してから**コミットへ進む。許容した指摘がある場合はユーザーに理由とともに報告する。

## 後続工程との接続

ticket-split が ticket-implement スキルに保証する成果物の契約:

- plan ハブ（`docs/plan/<機能名>/README.md`）が唯一の入口。チケット一覧表の依存・状態列だけで「今並行着手できるチケット集合」を判定できる
- チケット一覧表に「ファイル未作成」行が無いこと（分割完了＝設計＋計画 PR 作成の時点で保証する。コンテキスト肥大の中断で残す場合は「注意事項」に従い、見直し・追加モードで解消してから実装に引き渡す）
- 各チケットは単体読込（＋plan ハブ）で実装が完結する
- ステータス・PR リンク・実装メモの更新規約は plan ハブの「ステータス運用ルール」に定義済み。ticket-implement スキルはこれに従う

## 注意事項

- チケット生成の区切りごとに、残りの生成の消費量を見積もり、対応後のコンテキスト使用量が 200K トークン前後を超えそうなら無理に続けない（見積もりに迷うなら現在使用量 150K を一律閾値とする）。plan ハブ＋生成済みチケットをコミットし、ハブの一覧表に未生成チケットをリンクなし行（状態: ファイル未作成）として残して /clear を促す。続きは見直し・追加モードが拾う。次セッションの案内は、そのまま入力できる形で提示する: `/ticket-split <機能名>`
- 分割の過程で設計の矛盾・未決事項を発見した場合は、チケット側で勝手に補完せず、design-session での設計改訂を提案する
- 分割案の検討過程はチケットにもハブにも残さない（結論のみ記載。過程はコミットメッセージと会話で十分）
