# ADR-0030: dummy-pool の上限フェッチとプレビュー軽量化（実測駆動の設計改訂）

- ステータス: 提案
- 確信度: 高
- 起票日: 2026-07-04

> **注意**: 本 ADR はコード・コミット履歴からの事後的な推定であり、当時の意思決定の記録ではない。
> 当時を知るメンバーのレビューを経てステータスを更新すること。

## 背景

当初の設計（quiz-05 決定 8）は「プレビューと生成が同じ `fetchQuizSource` を共有し、コーパス全体を 1 クエリで取得する」だった。実測でターゲット1900 相当のデータ（約 1900 語）を毎回取得し、アプリケーションコードで約 1063ms を要することが判明した。

## 決定内容

実測に基づき段階的に改訂した（元設計の決定 8 は取り消し線 + 改訂注記付きで記録されている）:

1. 範囲抽出を SQL 側へ移し、ダミープールに上限を設ける（Option B、commit `876561a`）
2. ダミー候補プールは「出題対象自身もダミー候補」とし、不足分だけを優先順で追加取得する（範囲内件数 + 上限、commit `4907166`）
3. **テスト開始画面のプレビューを件数のみの軽量経路に分離**し、プレビューと生成のクエリ共有を終了する（commit `c8f2c9b`）。形式の出題可否チェックは開始時のサーバ検証へ移動
4. のちに `DUMMY_POOL_SIZE` を 100 → 50 に縮小（commit `7c7137a`）

## 採らなかった代替案

- **全コーパス 1 クエリ取得の維持（当初設計）** — 実測 1063ms で却下。設計不変条件「プレビューと生成の共有（決定 8）」を意図的に破り、supersede として設計文書と JSDoc の両方に記録された
- プレビューでの形式グレーアウト表示（改訂前 UI）— 軽量化に伴い開始時チェックへ移動（quiz-04 に改訂記録）

## 影響

- 「設計の不変条件も実測が出れば破ってよい。ただし supersede を元文書と実装コメントの両方に記録する」という改訂プロセスの先例になっている
- ダミー優先順（同一掲載箇所優先、[ADR-0026](0026-dummy-choices-same-occurrence-first.md)）は維持されたまま取得方法だけが変わった
