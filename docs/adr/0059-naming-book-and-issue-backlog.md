# ADR-0059: naming-book を用語の権威とし、バックログは GitHub Issues に起票する

- ステータス: 提案
- 確信度: 高
- 起票日: 2026-07-04

> **注意**: 本 ADR はコード・コミット履歴からの事後的な推定であり、当時の意思決定の記録ではない。
> 当時を知るメンバーのレビューを経てステータスを更新すること。

## 背景

英語コード名と日本語 UI 名・ドキュメント用語の対応（quiz/テスト、Occurrence/掲載箇所、残数、うろ覚え等）に揺れが蓄積し、AI エージェントが命名判断に迷う状態だった。また「作業中に見つけた別対応」をその場で直すスコープ肥大も問題だった。

## 決定内容

- **`docs/reference/naming-book.md` をドメイン用語（英語コード名 ⇔ 日本語名・定義・使ってはいけない類義語）の権威**とする。構成は「確定本文 / ブレ一覧（正規化待ち）/ 要確認リスト」の 3 部で、解決したら本文へ昇格させる
- **着手未定の対応意向・アイデアは GitHub Issues に起票**する。作業中に別対応が見つかっても、その場で直さず issue 化して現在の作業に戻る（スコープ肥大の防止）
- 線引き: ドキュメントの理解に必須な情報（用語の定義・確定した経緯）は issue に逃がさずリポジトリ内文書に残す。issue に置くのは「やる意向」と着手時のタスクだけ（issue はクローンに含まれず、閉じると見えにくくなるため、と理由明記）

## 採らなかった代替案

- 将来意向も含めて文書内に TODO として蓄積 — issue へ逃がす方針が明文化されており、文書は確定事項に保つ（naming-book 冒頭・AGENTS.md バックログ節）

## 影響

- 命名判断は naming-book 参照が必須の前提になり、「ブレ」も削除ではなく対応表として管理される（例: GAVE_UP/うろ覚え、例文四択/TG四択）
- 意図的に残している未対応（MP 例文の出題化 #96、`Occurrence.location` の改名 #97 等）が issue として追跡される
