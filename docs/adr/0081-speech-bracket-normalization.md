# ADR-0081: 読み上げの括弧は意味で出し分ける（`(…)` は中身を読む／`[…]` は中身ごと落とす）

- ステータス: 提案
- 確信度: 高
- 起票日: 2026-08-04

## 背景

自動音声は読み上げの直前に `toSpokenText`（`src/lib/speech.ts`）で表示用の記号を落としてから合成へ渡す（[ADR-0078](0078-speech-text-normalization.md)）。現行の対象は装飾記法・注記 `【…】`・プレースホルダ（チルダ・省略記号）の 3 種で、**括弧は未対応**だった。

例文の読み上げ（[ADR-0079](0079-example-pronunciation-audio.md)）を足すと、括弧を含む英文が読み上げ経路に入る。本番データ（2026-08-03 時点）で括弧を含む TG例文は 5 行あり、丸括弧 4 件はすべて「省略可能な語」、角括弧 1 件は「言い換え候補」で、辞書の慣習どおりに使い分けられていた。

| 例文 | 括弧の意味 |
| --- | --- |
| `(be) similar to 〜` | 省略可能 |
| `consider A (to be) B` | 省略可能 |
| `demand that A (should) do` | 省略可能 |
| `suggest (to 〜) that ...` | 省略可能 |
| `compare A with [to] B` | 言い換え候補（`with` または `to`） |

加えて、表示側 `TgExampleText` の `TG_TEXT_PATTERN`（プレースホルダの体裁を変えるハイライト）は**半角括弧しか見ていなかった**。

## 決定内容

**`toSpokenText` に括弧規則を足し、括弧の種類で扱いを変える**。

- **丸括弧 `(…)` は記号だけ落として中身を読む**（`consider A (to be) B` → `consider A to be B`）。中身は前後と繋げても英文として成立し、省略可能＝読まなくてよいではない。
- **角括弧 `[…]` は中身ごと落とす**（`compare A with [to] B` → `compare A with B`）。中身は直前の語と入れ替える候補なので、並べて読むと `compare A with to B` という非文になる。
- `A` / `B` / `do` / `doing` は落とさず英語として読ませる（骨組みだけ残ると文として聞けない）。
- **半角・全角の両字形を対象にする**（`(` `)` `[` `]` `（` `）` `［` `］`）。あわせて表示側 `TG_TEXT_PATTERN` にも全角括弧を足し、ハイライト対象と読み上げ対象を揃える。
- 実装は 2 段。①`[…]` のペアが取れる箇所を中身ごと除去する（開き／閉じの字形混在も 1 ペアとして扱う）。②残った括弧記号を記号単体で除去する。**ペアが取れない角括弧・入れ子は②に倒れ、「記号だけ落として中身は読む」になる**。除去範囲を推測して語を丸ごと落とすより、非文になる方が失敗として軽い。
- 除去順序は「装飾記法 → `【…】` → `[…]` → 残存括弧記号 → プレースホルダ → 空白畳み込み」。**中身ごと落とす処理を記号だけ落とす処理より先**に置かないと、括弧記号が先に消えて除去範囲を見失う。プレースホルダを後に置くのは、括弧内に残ったチルダ・省略記号を拾うため（`suggest (to 〜) that ...` → `suggest to that`）。
- 除去は空文字ではなく**空白 1 個への置換**（`A(B)` → `AB` の語結合を防ぐ）。既存 2 規則と同じ形。
- 規則は `toSpokenText` の 1 箇所にだけ足し、例文専用の分岐・引数は設けない。見出し語・関連語を含む読み上げ全経路に同じ規則が効く。
- **スラッシュ・引用符など括弧以外の記号は今回扱わない**（本番の英文データに 0 件）。用途を確定できない記号を推測で落とすと、`don't` のアポストロフィのように壊してはいけないものまで巻き込む。

## 採らなかった代替案

- **丸括弧も角括弧も記号だけ落として中身を読む** — 情報は落とさないが `compare A with to B` と非文になり、誤った語順を耳から覚えさせる。
- **丸括弧も角括弧も中身ごと落とす** — 最短だが `consider A (to be) B` が `consider A B` になり、覚えるべき `to be` が消える。
- **ペアが取れない括弧記号はそのまま残す**（`【…】` の既存実装と同じく閉じが無ければ何もしない） — 孤立した `[` が合成エンジンによっては「ブラケット」と読まれ、ADR-0078 が解決した問題がそのまま残る。
- **角括弧のペア不一致時は行末まで落とす** — `compare A with [to B` が `compare A with` になり、語が消える（最も重い失敗）。
- **ネストを厳密に対応付けるパーサを書く** — 実データにネストは無く、正規表現 2 本で足りる問題に対して過剰。
- **保存データ側から括弧を消す** — 括弧は表示としては必要な情報（省略可能・言い換え可能であること）。表示と読み上げで要求が違うだけなので保存物は変えない（ADR-0078 と同じ判断）。
- **正規化だけ全角対応し、表示ハイライトは別件にする** — 「読み上げでは落ちるが表示ではハイライトが付かない」非対称が残り、入力者に「この括弧は認識されていない」と誤読させる。追加は正規表現 1 行なので分ける利点がない。
- **括弧規則を例文だけに適用する（`toSpokenText(raw, { kind })`）** — 呼び出し元ごとに正しい種別を渡す責務が生まれ、ADR-0078 が一本道に集約した意味が失われる。

## 影響

- 括弧を含むテキストの読み上げが変わる。既存テストが固定していた `suggest (to 〜) that ...` の期待値は `suggest (to ) that` → `suggest to that` に更新した。
- 規則は見出し語・関連語にも効く。本番の見出し語・関連語の見出しに括弧を含むものは現時点で無いため、既存の読み上げが変わる実害は無い。
- **登録済み音源（mp3）の再生と画面表示には影響しない**（正規化するのは合成へ渡す文字列だけ）。表示側の変更は TG例文ハイライトの全角括弧追加だけで、これは読み上げ規則と対象字形を揃えるためのもの。
- 全角括弧が英文に混入しても読み上げ・ハイライトの両方で扱えるようになった（和訳側は全角丸括弧が 713 件と入力癖が強く、英文側への混入は起こりうる）。
- 新しく「読み上げたくない記号」が見つかったら、引き続き `toSpokenText` に 1 規則足す。「中身ごと落とす」か「記号だけ落とす」かで置き場が決まる。
