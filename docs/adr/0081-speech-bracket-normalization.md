# ADR-0081: 読み上げの括弧は意味で出し分ける（`(…)` は中身を読む・`[…]` は落とす）

- ステータス: 提案
- 確信度: 高
- 起票日: 2026-08-03

## 背景

[ADR-0078](0078-speech-text-normalization.md) で、読み上げ用テキストの正規化（`toSpokenText`）が
装飾記法・注記 `【…】`・プレースホルダ（チルダ・省略記号）を落とすようにした。そこでは
「例文の読み上げ（#170）を足した時点で TG 例文のプレースホルダを踏む」と予告していたが、
**括弧は未対応のまま**だった（当時は例文が読み上げ対象でなかったため）。

例文の読み上げ（[ADR-0079](0079-example-pronunciation-audio.md) /
[ADR-0080](0080-tg-example-audio-over-headword.md)）を入れると括弧が合成に流れ込む。本番データ
（2026-08-03 時点）で括弧を含む TG 例文は次の 5 行:

| 例文 | 括弧の意味 |
| --- | --- |
| `(be) similar to 〜` | 省略可能 |
| `consider A (to be) B` | 省略可能 |
| `demand that A (should) do` | 省略可能 |
| `suggest (to 〜) that ...` | 省略可能 |
| `compare A with [to] B` | 言い換え候補（`with` または `to`） |

丸括弧と角括弧は**意味が違う**。丸括弧の中身は前後と繋げて読んでも英文として成立するが、
角括弧の中身は直前の語と入れ替える候補なので、並べて読むと非文になる（「compare A with to B」）。

## 決定内容

`toSpokenText`（`src/lib/speech.ts`）で括弧を意味に沿って出し分ける。

- **`(…)`（省略可能）— 括弧記号だけ落として中身は読む**
  - `(be) similar to 〜` → 「be similar to」
  - `consider A (to be) B` → 「consider A to be B」
  - `demand that A (should) do` → 「demand that A should do」
- **`[…]`（言い換え候補）— 中身ごと落とす**
  - `compare A with [to] B` → 「compare A with B」
- **`A` / `B` / `do` / `doing` は落とさない**。英語として読ませる（教師が板書を読み上げるときと同じ）。
  落とすと「consider B」のように語が欠けて意味が壊れる。

落とした後に連続空白を 1 つへ畳んで trim するのは ADR-0078 の既存処理をそのまま通す。半角・全角の
両字形を対象にする（入力元で字形が揺れるため。チルダ 3 種を全部対象にしたのと同じ方針）。

本 ADR は ADR-0078 を**廃止せず追補する**（落とす記号を 1 種類足す判断であって、正規化の方針自体を
覆すものではない）。

## 採らなかった代替案

- **括弧の中身を両方とも読む（記号だけ落とす）** — 情報は落とさないが `compare A with to B` と非文に
  なる。聞き手に誤った語順を覚えさせるリスクがある。
- **括弧の中身を両方とも落とす** — 最短だが `consider A (to be) B` が「consider A B」になり、
  覚えるべき `to be` が消える。省略可能＝読まなくてよい、ではない。
- **`A` / `B` / `do` / `doing` もプレースホルダとして落とす** — 「compare with」のように骨組みだけが
  残り、文として聞けない。ADR-0078 が「原文に無い語を足さない／意味の分かっている記号だけ落とす」と
  したのと同じ理由で、語そのものは触らない。
- **表示側のデータから括弧を消す** — 括弧は表示として必要な情報（省略可能・言い換え可能であること）。
  表示と読み上げで要求が違うだけなので保存物は変えない（ADR-0078 と同じ判断）。

## 影響

- 自動音声の読みが変わるのは括弧を含む行だけ（本番 5 行）。**登録済み音源（mp3）の再生には影響しない**
  （正規化は TTS 経路だけ）。
- 表示は一切変わらない（正規化するのは合成へ渡す文字列だけ）。TG 例文の括弧ハイライト
  （`TgExampleText`）もそのまま。なお表示側のハイライトは半角括弧のみを対象にしているため、
  全角括弧は「読み上げでは落ちるが表示のハイライトは付かない」非対称になる。本番データに全角括弧は
  無く実害は無いが、揃えるなら `TG_TEXT_PATTERN` 側に足す（表示の変更なので別判断）。
- 見出し語・関連語の見出しにも同じ正規化が掛かる（`toSpokenText` は読み上げの一本道）。現時点で
  括弧を含む見出し語・関連語は本番に無いが、今後入っても同じ規則で読まれる。
