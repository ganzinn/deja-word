# ADR-0084: 単語検索はキーワード側のアクセント記号を落として照合する（保存データは正規化しない）

- ステータス: 提案
- 確信度: 高
- 起票日: 2026-08-06

## 背景

単語検索の入口は 2 つあり、どちらも `Word.headword` に対する部分一致で引く。

- 単語一覧（単語ビュー／掲載箇所ビュー、および掲載箇所ビューの前後ナビ） — `src/lib/words-list.ts`
- 単語登録・編集フォームの関連語「既存単語からリンク」 — `src/lib/words-search.ts`

保存データの実態として、**見出し語（`headword`）はアクセント記号（`ó` などのダイアクリティカルマーク）を持たない**が、**関連語の見出し（`RelatedWord.term`）は書籍の表記どおりアクセント記号付きで登録されている**（`péssimist` / `suscèptibílity` / `implícit` など。target1900 の関連語一括登録 [ADR 相当の運用手順](../ops/import-related-words.md) 由来）。

このため、関連語からリンク先の既存単語を探すとき、term をそのまま検索窓へ入れると 0 件になる。「既存単語からリンク」は関連語の term を検索窓の初期値に使う（`LinkedWordPicker`）ので、**この経路はアクセント記号付きの語で必ず空振りする**。一覧検索でも、書籍から見出し語を書き写す・関連語表示からコピーすると同じことが起きる。

## 決定内容

**検索キーワード側だけを正規化し、保存データ（`headword` / `term`）は変更しない。**

- 正規化は純関数 `normalizeSearchKeyword`（`src/lib/search-keyword.ts`）に集約する。処理は「NFD 分解 → 結合文字（`\p{M}`）除去 → trim」。合成済み（`é`）・分解済み（`e` + `́`）のどちらの入力でも同じ結果になる。
- 大文字小文字は変換しない。既存の照合が Prisma の `mode: "insensitive"` で吸収しており、正規化側で二重に持たない。
- 適用箇所は検索キーワードを受け取る **2 モジュールの入口**（`words-list.ts` の `searchKeyword` ヘルパ経由の 2 呼び出し、`words-search.ts` の `searchWordsForLink`）。一致方法（prefix / contains / suffix）による分岐は持たせない。
- **正規化の結果が空文字になる入力（結合文字だけ等）は「キーワード指定なし」に倒す**。既存の `q.length > 0` 判定を正規化後の値で行うことで、`contains: ""` による全件一致を防ぐ。
- URL の `q` パラメータ・検索窓の表示・件数ラベル（`「〜」の検索結果`）は**入力されたまま**を保持する。正規化するのは DB へ渡す照合値だけで、ユーザーには自分が打った文字列が見えるようにする。

## 採らなかった代替案

- **保存時に見出し語のアクセント記号を落とす（入力の正規化）** — 照合は対称になるが、ユーザーが打った文字列を黙って書き換えることになる。書籍の表記を残したい入力者の意図を壊す。関連語の term は表記としてアクセント記号が必要なので、いずれにせよ term 側は正規化できず、片手落ちになる。
- **正規化済みの検索用カラム（`headwordSearch` 等）を持ち、両側を正規化する** — アクセント記号付きの見出し語が登録された場合にも対称に引ける。ただし migration・backfill に加えて全書き込み経路（正規パス・一括登録・seed）に維持責務が増える。**現時点で見出し語にアクセント記号付きは存在せず、非対称による実害が無い**ため、コストが釣り合わない。将来アクセント記号付きの見出し語が入るなら、そのとき本案へ移る。
- **Postgres の `unaccent` 拡張を使い、`unaccent(headword) ILIKE ...` で引く** — DB 側で対称に照合できるが、Prisma の `where` では表現できず一覧の照合を raw SQL へ落とす必要がある。一覧は件数取得・ネスト select・掲載箇所リレーション条件・前後ナビと絡んでおり、書き換え範囲に対して得るものが小さい。拡張の作成が migration に入る（Neon 側の依存も増える）。
- **アクセント記号以外の表示用記号（`【米】` の注記、`〔〜s〕` のプレースホルダ等）も同時に落とす** — 関連語の term にはこれらも含まれ、「既存単語からリンク」では同じく空振りする。ただし落とし方は読み上げ正規化（`toSpokenText`、[ADR-0078](0078-speech-text-normalization.md) / [ADR-0081](0081-speech-bracket-normalization.md)）と同じ議論を検索の文脈でやり直すことになり、判断材料が別物。今回のアクセント記号とは分けて起票する（issue #197）。
- **読み上げ正規化 `toSpokenText` を検索キーワードにも流用する** — 記号除去の規則は近いが、目的が違う（読み上げは「合成が読める文字列にする」、検索は「保存データと突き合わせる」）。共有すると片方の都合での規則追加がもう片方の挙動を変える。純関数を分けて持つ。

## 影響

- アクセント記号付きのキーワードが、記号なしの見出し語に一致するようになる（`thóught` → `thought`）。記号を含まない従来のキーワードの挙動は変わらない。
- 「既存単語からリンク」で、関連語の term を初期値のまま検索して既存単語が見つかるようになる（この機能の主な使われ方）。
- 見出し語にアクセント記号付きの語が登録された場合、記号なしのキーワードでは引けない（非対称）。上の代替案のとおり、その状況が生まれたときに正規化カラムへ移る判断をする。
- 検索窓・URL・件数ラベルの見え方は変わらない。
