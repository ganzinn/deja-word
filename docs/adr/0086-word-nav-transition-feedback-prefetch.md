# ADR-0086: 前後ナビに遷移中フィードバック（淡色化＋方向スライド）とプリフェッチを追加する（ADR-0085 追補）

- ステータス: 提案
- 確信度: 高
- 起票日: 2026-08-06

## 背景

ADR-0085 で前後ナビの横フリックを導入した際、「視覚的なページめくりアニメーションは付けない」とした。また影響節に「同じ href の `<Link>` が prefetch 済みのため、ボタン押下と同じ速さで表示される」と記した。

しかし本番環境（Neon 往復あり）では操作から次の単語表示まで待ち時間があり、操作が効いたか分からず同じ操作を繰り返してしまう問題が報告された（issue #200）。調査の結果、`/words/[id]` は dynamic ルートで `loading.tsx` が無いため、`<Link>` のデフォルト prefetch は**一切働いていない**ことが判明した（Next.js 16.2.9 同梱 docs `01-app/01-getting-started/04-linking-and-navigating.md`: dynamic ルートは loading 境界が無ければ prefetch スキップ。かつ prefetch は production のみ）。0085 影響節の当該記述は誤りだった。

## 決定内容

word-nav-feedback 設計シリーズ（`docs/design/word-nav-feedback/`。実装完了に伴い削除済みのため、要点を本 ADR に残す）で以下を確定した。

1. **遷移中フィードバック**: 操作を受け付けたら、前の単語を残したままコンテンツを淡色化（150ms 程度のフェードで開始。速い遷移では実質見えない）し、到着時にコンテンツ領域のみを操作方向へ一方向スライドで差し替える。ボタン押下・フリックとも同じ演出。ページと単語詳細ダイアログで体験の文法を統一し、ダイアログの「読み込み中…」差し替えは廃止する。`prefers-reduced-motion` ではスライド無効・淡色化のみ。
2. **実装方式**: スライドは自前 CSS（tw-animate-css + key 差し替え）。`experimental.viewTransition` は有効化しない。ページの遷移経路は `startTransition` + `router.push` に単一化し（淡色化トリガは `useTransition` の `isPending`）、`<Link>` は prefetch と anchor semantics のために維持して intercept する。共通化は表示コンポーネント（淡色化＋スライド）1 つに限定する。
3. **プリフェッチ**: ページは前後ボタンの `<Link>` に `prefetch={true}`（dynamic ルートのフルプリフェッチ・クライアントキャッシュ既定 5 分）。フリックも同一 href 文字列のためキャッシュを共有し、`router.prefetch` の手動呼び出しはしない。ダイアログは詳細＋隣接ナビの Server Action を前後 1 件先読みし、ダイアログが開いている間だけの Map キャッシュに保持する（先読み応答はキャッシュにのみ書き、最後勝ちの鮮度照合と干渉させない）。先読みは両者とも前後 1 件・連続送りの追い越しは許容。
4. **鮮度の前提整備**: 単語データを変更する Server Action（`updateWord`・音源アップロード/削除系・`deleteWord`・`createWord`）に `revalidatePath` を追加し、プリフェッチ済みペイロードの編集後 stale を防ぐ。`toggleBookmark` は楽観的更新の現行方針のまま（ブックマーク初期表示の最大 5 分 stale は許容）。

0085 の決定のうち「視覚的なページめくりアニメーションは付けない」は本 ADR で置き換える（指追従はせず、到着時スライドのみ。フリックの判定条件 — 閾値・エッジ除外・window リスナ — は変えない）。0085 影響節の「`<Link>` が prefetch 済み」の記述も本 ADR の調査結果で訂正する。

## 採らなかった代替案

- **触覚フィードバック（バイブレーション）** — ユーザー判断で対象外（2026-08-06。候補として再提案しない）。
- **指追従アニメーション** — 0085 却下案のとおり、縦スクロールとの調停（`preventDefault`）リスクが大きい。
- **`loading.tsx` の追加による部分プリフェッチ** — loading fallback がコンテンツを置き換え、「前の単語を残して淡色化」と衝突する。
- **View Transitions API（`experimental.viewTransition`）** — この演出だけのために experimental フラグをアプリ全体に有効化するリスクが釣り合わない。
- **`router.prefetch` の手動呼び出し** — `<Link prefetch={true}>` とキャッシュキー（URL）共有で足り、二重管理になる。

## 影響

- 本番の前後移動は、プリフェッチ命中時はほぼ即時（スライドのみ知覚）、未命中時は淡色化が「操作を受け付けた」ことを示す。
- 単語詳細 1 表示につき前後 2 ページ分のサーバーレンダリング（Neon クエリ含む）が追加で走る（連続送りでは実質 +1 件/ステップ。待ち時間短縮の対価として許容）。
- `<Link>` の自動プリフェッチは production のみ有効。dev・E2E はプリフェッチに依存しない（E2E は `data-*` 属性の DOM 確認のみ）。
- 単語の編集・削除・作成のたびにクライアントルーターキャッシュが全クリアされ再プリフェッチが走る（低頻度のため許容）。
- 実装で確定した挙動（PR #204）:
  - ページ側の淡色化・スライドの対象は本文（`WordDetailView`）のみで、上部の `ScreenHeader`（見出し語・ブックマーク・編集/削除）は含まない。このため**遷移中はヘッダのタイトルだけ先に新しい単語へ切り替わり、本文は前の単語のまま淡色**になる。前後ナビ行を固定する方針との整合を優先した結果で、気になる場合は別途扱う。
  - ダイアログで先読み中の単語へ追い越して移動すると、詳細取得が二重に飛ぶ（先読みはキャッシュにしか書かないため表示用の取得を別途投げる必要がある）。「追い越し時は通常の待ち」の範囲内として許容。
