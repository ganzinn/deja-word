# ADR-0090: 前後ナビのフルプリフェッチを廃止し毎回サーバー取得にする（ADR-0086 決定 3・4 の部分置き換え）

- ステータス: 提案
- 確信度: 高
- 起票日: 2026-08-07

## 背景

ADR-0086 決定 3 で、単語詳細ページの前後ナビの `<Link>` に `prefetch={true}`（dynamic ルートのフルプリフェッチ・ルーターキャッシュ既定 5 分保持）を追加した。issue #200（操作が効いたか分からず同じ操作を繰り返す）への対策として、待ち時間そのものの短縮を狙ったものだった。

しかしフルプリフェッチは前後ページのスナップショットをルーターキャッシュに最大約 5 分保持するため、別端末で削除された単語の詳細が閲覧中端末で表示され続ける・古いスナップショットに残ったナビリンク経由で 404 に到達する、という「一覧の表示順との不同期」を生んでいた（issue #229）。また詳細 1 表示につき前後 2 ページ分の追加サーバーレンダリング（Neon クエリ含む）のリソースコストも伴っていた。

## 決定内容

word-nav-no-prefetch 設計シリーズ（`docs/design/word-nav-no-prefetch/`。実装完了に伴い削除済みのため、決定の要点は本 ADR に残す）で以下を確定した。**ADR-0086 決定 3 のうちページ側 `prefetch={true}` を本 ADR で置き換える**。ADR-0086 決定 1（淡色化＋方向スライドの遷移中フィードバック）・決定 2（`startTransition` + `router.push` への遷移経路単一化、`<Link>` intercept）は維持する。

1. **`prefetch={false}` を明示して先読みを全廃する**: `adjacent-word-nav.tsx` の前後 2 つの `<Link>` を `prefetch={false}` にする（プロパティ削除でデフォルト `auto` に戻すのではない）。`prefetch={false}` は「viewport 進入・hover のいずれでも一切プリフェッチしない」ことが同梱 docs（16.2.9 `link.md`）で保証され、周辺条件に依存しない。デフォルト `auto` でも現状（dynamic ルート＋`loading.tsx` 無し）は同挙動だが、それは部分プリフェッチ対象が無いことによる暗黙のスキップで、将来 loading 境界を追加すると挙動が変わるため明示に倒す。`<Link>` 自体は維持する。詳細ページの他の `<Link>`（戻る・編集・関連語）は prefetch 未指定（デフォルト `auto`）のままとする。
2. **毎回サーバー取得により一覧の表示順と常に同期する**: クライアント遷移（前後ナビの `router.push`・戻る等のリンククリック。ブラウザ back/forward の履歴復元を除く）は `staleTimes` 既定の dynamic 0 秒により毎回サーバー取得となり、隣接が一覧と同じ where で毎リクエスト計算される前提（ADR-0089 決定 3・4）と合わせて「一覧の表示順と常に同期した隣接移動」が追加実装なしで成立する。残るのは (a) 描画〜タップ間に別端末で削除された場合の 404 到達と (b) back/forward キャッシュ復元経由の stale 表示・404 到達（いずれも許容。リンク遷移で開き直せば解消）。共有レイアウトセグメント（`src/app/layout.tsx`）は partial rendering によりナビゲーション毎には再取得されないが、単語データ・隣接ナビを含まないため本件の鮮度問題には無関係。
3. **遷移待ちの体感は遷移中フィードバックが単独で担う**: 廃止後は前後移動が毎回サーバー往復になり淡色化がほぼ常に知覚されるが、「操作を受け付けた」ことはフィードバック（ADR-0086 決定 1・2、維持）が示すため、issue #200 の再発防止もフィードバック側で担う。フリックの判定条件（ADR-0085）も変更しない。
4. **`<Link>` 維持の根拠は anchor semantics と `onNavigate` intercept のみになる**: ADR-0086 決定 2 の「`<Link>` は prefetch と anchor semantics のために維持」のうち prefetch 側の根拠は本 ADR で失効する。
5. **テスト結果ダイアログ側の詳細先読みは対象外・維持**: 現行仕様は ADR-0088 決定 6（ADR-0086 決定 3 のうちダイアログの隣接ナビ先読みは同決定で既に廃止済みで、本 ADR はページ側を置き換える切り分け）。変更する場合は別 issue で扱う。
6. **`revalidatePath` 群（5 箇所）は維持し、維持理由を再定義する（ADR-0086 決定 4 の置き換え）**: createWord / deleteWord / updateWord・音源アップロード / 削除系の `revalidatePath` は呼び出し・unit テストとも維持する。維持理由は「プリフェッチ済みペイロードの stale 防止」から「**変更（作成・編集・削除・音源変更）を実行した同一タブ（同一ルーターインスタンス）で、back/forward 履歴復元により変更前の内容が出るのを防ぐ**」に再定義する（ページは既定でルーターキャッシュに残らないが back/forward では再利用されるため、廃止後も dead code ではない。同一タブでの変更直後の stale は「自分の操作が失われたように見える」点で他端末由来の stale と質が異なり、許容に含めない）。注意: Server Action からの `revalidatePath` のクライアントキャッシュ全パージは docs 上「暫定挙動（将来は指定パスのみに狭める）」であり、5 箇所が渡すパスはいずれも `/words/<id>`（詳細）で `/words`（一覧）を渡す呼び出しは無いため、挙動が狭められた場合に確実に残るのは「変更した単語自身の詳細ページ」の効果のみ。特に createWord が渡すのは作成直後の新規 ID の詳細パスで、狭められた時点で効果が残らないため、その時点で `/words` の revalidate 追加（createWord は追加または削除）を再検討する。
7. **`toggleBookmark` は現行方針のまま**（楽観的更新・`revalidatePath` なし。`src/app/words/actions.ts` 冒頭コメント）。ブックマーク初期表示の stale 窓は「最大 5 分の stale は許容」（ADR-0086 決定 4）から縮む: リンク遷移では毎回サーバー取得となり、残るのは back/forward 復元経由のみ。
8. ADR-0085 影響節の「同じ href の `<Link>` が prefetch 済みのため、ボタン押下と同じ速さで表示される」（ADR-0086 が誤りと訂正済み）は、本置き換えで速度差の前提自体が消え最終的に無効となる。

## 採らなかった代替案

- **プロパティ削除でデフォルト `auto` に戻す** — 現状は結果的に同挙動だが、無効化が周辺条件（dynamic ルート・loading 境界の有無）依存の暗黙になる。prefetch 挙動の暗黙依存は ADR-0085 影響節の誤記（「prefetch 済み」と誤認）を生んだ経緯があり、明示に倒す。
- **`staleTimes` の明示設定や `router.refresh` の追加** — 既定値（dynamic 0 秒）で目的が達成されるため不要。設定を足すと experimental フラグへの依存が増えるだけ。
- **`loading.tsx` 追加による部分プリフェッチで体感を補う** — loading fallback がコンテンツを置き換え、「前の単語を残して淡色化」と衝突する（ADR-0086 却下案の再確認）。
- **`revalidatePath` 群の全削除** — back/forward 復元の stale のうち、同一タブの変更直後の stale は操作の成否を疑わせる点で質が異なる。削除で得られるのは 5 行＋テストアサーションの削減のみで釣り合わない。
- **`revalidatePath` の一部削除（createWord のみ削除等）** — 現行の全パージ挙動の下では createWord にも「作成後に back/forward で一覧へ戻ったとき新単語が見える」効果が残っており、切り分ける根拠がない。
- **ADR-0086 を直接書き換える** — ADR は不変の決定記録であり、置き換えは新 ADR ＋改訂注記で表す（ADR-0088 決定 6 の前例に倣う）。

## 影響

- 前後移動は毎回サーバー往復となり、淡色化フィードバックがほぼ常に知覚される（待ちの体感は決定 3 のとおりフィードバックが担う）。
- 別端末で削除された単語の stale 表示（最大約 5 分）と、プリフェッチキャッシュ由来のナビリンク経由 404 到達窓が解消する。残るのは描画〜タップ間の削除競合と back/forward 履歴復元経由の stale・404（許容）。
- 詳細 1 表示につき前後 2 ページ分の追加サーバーレンダリング（Neon クエリ含む）が消える。
- `<Link>` の自動プリフェッチは production のみ有効だったため、従来はプリフェッチ命中時の挙動を本番でしか確認できなかった。廃止後は dev と production の遷移経路が一致し（どちらも毎回サーバー取得）、dev ＋ CDP throttling の確認が本番の体感を代表する。
- 単語の編集・削除・作成のたびに走っていた再プリフェッチ（ADR-0086 影響節）は無くなる（`revalidatePath` の全パージ自体は決定 6 のとおり残る）。
