# ADR-0093: 掲載箇所の単語コンテンツは中間 JSON を挟む 2 段構成で別環境から取り込む

- ステータス: 提案
- 確信度: 高
- 起票日: 2026-08-08

## 背景

本番の共有マスタでは、単語の意味・例文・関連語・注記が画面から継続的に育っている。一方ローカル開発 DB は [`import-words`](../ops/import-words.md) の CSV 由来で「単語 + 意味 1 件」しか無く、発音音源だけが [`import-audio`](../ops/import-audio.md) で登録済み、という状態だった。これでは本番と同じ見え方での動作確認ができない。

以前は使い捨てスクリプト（git 管理外）で一度だけ対応した。その実装は「本番から SQL で JSON を吸い出し、開発 DB へ反映する」という形で、掲載箇所名はハードコード、JSON は手作業で用意する前提だった。本番へは今後も継続的にデータを投入していくため、**掲載箇所と掲載番号を指定すれば追随できる汎用ツール**として作り直す必要が生じた。

制約として、**取り込み元（本番）の接続情報をツール本体・ドキュメント・コミットに一切含めない**ことが求められた。

## 決定内容

1. **中間 JSON を挟む 2 段構成にする（1 コマンドで 2 DB に繋がない）**: `pnpm db:export-occurrence`（読み取り専用）が掲載箇所配下の単語コンテンツを JSON に書き出し、`pnpm db:sync-occurrence` がそれを反映先 DB に取り込む。取り込み元の接続情報はエクスポート側にしか渡らず、**反映側は構造的に本番へ書き戻せない**。あわせて、書き込む前に人が中身をレビューできる中間物が残る（複雑な入力を「レビュー可能な中間ファイル + 単純なツール」に分解する既存方針。[import-related-words](../ops/import-related-words.md) の中間 CSV と同じ考え方）。
2. **エクスポートの接続先は `SOURCE_DATABASE_URL` 限定とし、`DATABASE_URL` にフォールバックしない**: 他の運用スクリプトは `DIRECT_URL → DATABASE_URL_UNPOOLED → DATABASE_URL` の順で解決するが、この 1 本だけ専用変数を要求する。フォールバックさせると、変数の設定漏れに気付かないまま手元の DB をエクスポートしてしまい、それが「本番から取った JSON」として反映まで通ってしまう。接続文字列は gitignore 済みの env ファイルに置き `pnpm dotenv -e <file> -- ...` で渡す（手順は [sync-occurrence](../ops/sync-occurrence.md)）。起動時にホスト名だけを表示して取り違えを目視できるようにする。
3. **反映先はローカル DB に限定する**: `db:sync-occurrence` は接続先が localhost / 127.0.0.1 / ::1 でなければ何もせず中止する。判定は既存の `isLocalDatabaseUrl`（`src/lib/blob-driver-guard.ts`）を再利用する。使い捨てスクリプトが使っていた「接続文字列にホスティング事業者名が含まれるか」の正規表現は、事業者を変えると素通りするため採らない。
4. **掲載箇所は「所有ユーザー + 掲載箇所名」で選ばせる**: 掲載箇所名は `@@unique([ownerId, location])` で所有者内一意でしかなく、別ユーザーに同名が存在しうる。対話モードは所有ユーザー（ユーザー名 + email）ごとにグループ化した一覧から選ばせ、非対話では `--email`（省略時 system）で所有者を指定する。この用途のために `listOccurrences`（`occurrence-purge.ts`）へ `ownerName` を追加し、反映先ユーザーの選択用に `listImportOwners`（`import-owner.ts`）を新設して、対話 UI 用の列挙を 1 箇所に保つ。
5. **コンテンツは丸ごと置き換える（部分マージはしない）**: 対象単語の意味・訳語・注記・例文・関連語・メモ・掲載番号詳細を削除してから JSON の内容で作り直す。目的は「取り込み元と同じ状態で確認すること」であり、追加のみのマージでは取り込み元で修正・削除された内容が残って一致しない。
6. **単語本体・ブックマーク・解答履歴・drill には触らない**: 置き換えるのは単語の子テーブルだけで `Word` 行は消さない。そのため cascade の巻き添えが起きず、手元の学習データが失われない。
7. **反映先に掲載箇所・単語が無ければ作る**: 掲載箇所ごと丸ごと取り込めるようにして、まだ手元に無い掲載箇所にも同じ手順を使えるようにする。掲載箇所の新規作成は `bulkImportWords` と同じ手順（scoped の同名衝突チェック → 作成 → **オーナー本人ぶんだけプリセット ON**）に揃える。
8. **同じ掲載番号に別の見出し語がある場合は上書きせずスキップする**: 掲載番号のズレは取り違えの兆候であり、黙って上書きすると誤った単語に別の内容が入る。スキップして報告し、判断を人に返す。同じ見出し語が同一掲載箇所の別番号に既にリンク済みの場合も同様にスキップする（`@@unique([wordId, occurrenceId])` 違反の回避を兼ねる）。
9. **発音音源は同期せず、置き換え前に反映先の URL を退避して付け直す**: 音源の実体は環境ごとに別（本番 = Vercel Blob の絶対 URL / dev = ローカルディスクの相対 key、ADR-0079 / `blob-client-impl.ts`）で、URL をそのまま持ち込むと解決できない行になる。これは 2026-08-03 に本番で実害を出した失敗モード（`pronunciationAudioUrl` が非 NULL のまま 404 になり TTS フォールバックも効かない）と同型なので、原理的に起こさない。退避の同定キーは 意味 = `sortOrder` / 例文 = 本文 / 関連語 = `term`。JSON には参考として URL を含めるが、反映側は常に無視する。音源の投入は `import-audio` の責務のまま。
10. **単語の突合は掲載番号、関連語の内部リンクは見出し語で行う**: DB をまたぐと id は一致しない。`RelatedWord.linkedWordId` は `linkedHeadword` として書き出し、反映先の同一オーナーの見出し語から引き直す。同じ取り込みで後から作られる単語への参照（前方参照）に対応するため、全件を書き終えてからまとめて解決し、解決できなかったものはリンク無しで登録して報告する。掲載番号を持たない単語は突合キーが無いため対象外とし、件数だけ報告する。
11. **単語 1 件 = 1 トランザクションの非原子方式**: `bulk-word-import` / `audio-import` と同じ方針（リモートへの往復が長く長大トランザクションを避ける）。置き換えなので再実行が冪等になり、中断時のリカバリは「同じコマンドの再実行」で済む。
12. **repo に残す文書・テストに実データの掲載箇所名を書かない**: ツールもドキュメントも掲載箇所名を持たず、具体的な掲載箇所・掲載番号は実行時にだけ渡す。ドキュメントは `<掲載箇所名>` のプレースホルダで書く（「ドキュメントに実データの件数を書かない」（AGENTS.md）と同じ理由で、実データの固有名も書いた時点で古くなり、外部にも出る）。

## 採らなかった代替案

- **1 コマンドで取り込み元と反映先の両方に接続する（直結同期）** — 反映側のプロセスが本番の接続情報を持つことになり、「反映側は本番へ書き戻せない」という構造的な保証が失われる。レビュー可能な中間物も残らない。
- **エクスポートも `DATABASE_URL` へフォールバックさせる** — 変数の設定漏れで手元の DB をエクスポートしても気付けず、それが「本番から取った JSON」として反映まで通る。決定 2 の理由そのもの。
- **接続先の判定にホスティング事業者名の正規表現を使う**（使い捨てスクリプトの実装） — 事業者や接続経路を変えると素通りする。ローカルかどうかの許可リスト判定（決定 3）のほうが確実で、既存関数を再利用できる。
- **追加のみのマージ（反映先に無い行だけ足す）** — 取り込み元で修正・削除された内容が反映先に残り、目的の「同じ状態で確認する」が達成できない。似た訳語が二重に並ぶ・`sortOrder` が衝突するといった副作用も出る。
- **対象単語を `Word` ごと削除して作り直す** — 実装は単純になるが、ブックマーク・解答履歴・drill が cascade で消える。子テーブルだけの置き換えで同じ結果が得られるので採らない。
- **発音音源も同期する（本番 Blob からダウンロードして手元に保存する）** — 手元には音源が登録済みで、同期しても得られるものが無い。実装（ダウンロード・key の決定的導出・冪等化）と実行時間だけが増える。将来必要になれば別 ADR で扱う。
- **掲載箇所名だけで反映先を決める** — 同名の掲載箇所が別ユーザーに存在しうるため判別できない（決定 4）。
- **見出し語が食い違う掲載番号を強制的に上書きするオプションを付ける** — 取り違えを黙って通す口を作ることになる。必要なら反映先を先に手で直す。

## 影響

- ローカルで、指定した掲載番号の範囲だけを取り込み元と同じ内容にできるようになり、単語詳細・単語テストの見え方を実データで確認できる。範囲外の単語と、手元に登録済みの発音音源は影響を受けない。
- 取り込み元の接続情報は「エクスポートを実行する 1 コマンド」にしか渡らず、コミット対象にも入らない。
- `ResolvedOwner`（`import-owner.ts`）に `ownerName` が増え、`OccurrenceListItem`（`occurrence-purge.ts`）に `ownerName` が増える。いずれも追加のみで既存の呼び出し（`db:import-*` / `db:purge-occurrence`）の挙動は変わらない。
- 取り込みは非原子（決定 11）なので、途中で失敗すると一部の単語だけが新しい内容になる。壊れてはおらず、同じコマンドの再実行で揃う。
- 掲載番号を持たない単語は同期できない。必要になったら別の突合キーの検討が要る。
