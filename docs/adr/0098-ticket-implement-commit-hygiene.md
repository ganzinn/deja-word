# ADR-0098: ticket-implement の「実装中」ステータス更新は独立コミットにせず、チケット取り込みコミットへ同梱する

- ステータス: 提案
- 確信度: 高
- 起票日: 2026-08-15

## 背景

ticket-implement のマージは 2 階層ある。

| 階層 | 方式 | 目的 |
| --- | --- | --- |
| チケットブランチ → 統合ブランチ（ローカル） | `git merge --squash` | 実装エージェントの作業コミットを潰し「1 チケット = 検証済みの 1 コミット」にする |
| 統合ブランチ → main（GitHub PR） | merge commit | チケット単位のコミットを main に残す |

この 2 段構成自体は粒度の異なる階層への意図的な使い分けで、各チケットコミットは `format` / `lint` / `typecheck` / `test` を通した自己完結した単位のため、bisect・blame の刻みとして価値がある。

問題は、実装フロー手順 2 の「実装中」ステータス更新が**チケットに紐づかない独立コミット**として統合ブランチに積まれ、外側が merge commit のためそのまま main の履歴に流出することにある。実測では word-view-nav（3 チケット）が main に残したのは実装 3 コミットに対し記帳 4 コミットで、ほぼ同数の記帳が混ざっている。

## 決定内容

1. **「実装中」のステータス更新（ハブ一覧表＋チケット冒頭の状態行）は独立コミットにしない**。統合ブランチの作業ツリー上の未コミット変更として保持し、最初に完了したチケットの取り込みコミットへ同梱する
2. 「完了」更新と実装メモの転記は現行どおりチケット取り込みコミットへ同梱する（変更なし）
3. **PR 列の一括記載は独立コミット 1 本として残す**（統合 PR 作成後にしか URL が確定しないため。機能あたり 1 本）
4. 中断・再開時の状態復元は既存の「前回の残骸の扱い」（worktree の実在と統合ブランチのコミットの有無）で行う。未コミットの「実装中」表示が失われても ready 判定には影響しない
5. **2 階層のマージ方式（内側 squash / 外側 merge commit）は維持する**

## 採らなかった代替案

- **統合 PR も squash に統一する** — マージ方式が全階層で揃い、ブランチ削除の `-d` / `-D` ルールも統一される。しかし main の履歴が機能あたり 1 コミットになり、チケット単位の bisect・blame 粒度を失う。各チケットコミットは検証を通した自己完結単位で刻みとしての情報量が大きく、ルールの統一性と引き換えにするには損失が大きい
- **PR 作成前に interactive rebase で記帳コミットを畳む** — Claude Code 環境では `git rebase -i` が使えない。非対話 rebase での自動化は失敗時の復旧が重く、実装差分を巻き込む事故のリスクがある
- **「実装中」の表示自体をやめる** — 並行 wave 中にどのチケットが実装エージェントに渡っているかをハブで追えなくなる。未コミットでも作業ツリー上では見えるため、表示は残したまま履歴への流出だけを止められる

## 影響

- 機能あたりの記帳コミットは「PR リンク記載」1 本に減る（word-view-nav 相当なら 4 本 → 1 本）
- wave 実行中は統合ブランチの working tree が dirty になる。前提条件チェックの「working tree が clean であること」は**セッション開始時のみの条件**として維持する
- チケット worktree は統合ブランチのコミットから分岐するため、未コミットの状態更新は worktree へ伝播しない。実装エージェントはハブを読むが担当チケットは委譲プロンプトで指定されるため、状態列の表示が古くても実装には影響しない
- ブランチ削除の `-d` / `-D` の使い分けはブランチ族ごとに異なるまま（チケットブランチは squash のため `-d` 不可、統合ブランチは PR の merge commit で main に入る）。判断材料は worktree スキル「撤去」節に集約する
