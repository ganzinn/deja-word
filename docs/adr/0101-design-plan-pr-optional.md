# ADR-0101: 設計＋計画 PR の作成は選択制にし、作らない場合は統合ブランチを作業ブランチから分岐する（0096 追補）

- ステータス: 提案
- 確信度: 高
- 起票日: 2026-08-15

## 背景

[ADR-0096](0096-feature-origin-worktree-model.md) 決定 1 は、起点 worktree のフェーズ移行を「`docs/<機能名>-design-plan` →〔設計＋計画 PR マージ後〕`feature/<機能名>`」と定め、ticket-split はチケット分割の完了時に設計＋計画を一括レビューする PR を必ず作ることになっていた。実務上の根拠は 2 つ — 統合ブランチを `origin/main` から切る以上、計画が main に入っていないと各チケットの実装セッションが plan を読めないこと、および設計・計画のドキュメントと実装コードを別の diff でレビューできることだった。

一方で、設計・計画の内容は design-session / ticket-split のセッション中にユーザーが随時確認しており、第三者レビューとしての設計段階の PR は形式的になっていた。quiz-first-meaning-only ではこの PR を作らず、統合ブランチを作業ブランチから分岐して実装フェーズを回した（issue #268）。

## 決定内容

1. **設計＋計画 PR を作るかは、ticket-split の完了時にユーザーへ確認する**。判断材料は「ドキュメントだけを独立してレビューしたいか」。

2. **作らない場合、実装フェーズの統合ブランチは作業ブランチ `docs/<機能名>-design-plan` から分岐する**（[ADR-0096](0096-feature-origin-worktree-model.md) 決定 1 の追補）。設計・計画のコミットが統合 PR の先頭に入り、機能あたりの PR は統合 PR とクローズ PR の 2 本になる。作る場合は従来どおり `origin/main` から分岐する。

3. **どちらの運用かの判定は「作業ブランチがマージ済みか」で行う**。ticket-split の見直し・追加モードの作業場所（起点 worktree の作業ブランチ / 統合ブランチ / 臨時 plan-update worktree）は、統合ブランチの有無と作業ブランチのマージ状態で決まる。main 起点の計画見直し（plan-update）が要るのは、設計＋計画 PR をマージ済みかつ統合ブランチ作成前の区間だけになる。

## 採らなかった代替案

- **設計＋計画 PR を必須のまま維持する** — 会話中に随時確認している運用では独立レビューの実益が薄く、PR 作成・マージの往復とマージ待ちの停止時間だけが残る。
- **設計＋計画 PR を廃止して常に統合 PR 1 本にする** — ドキュメントだけを独立してレビューしたい機能（設計の分量が大きい、レビュアーを分けたい）で退路が無くなる。分岐元の切替は 1 行の差なので、選択制のコストは小さい。
- **統合ブランチを常に作業ブランチから分岐し、設計＋計画 PR は base を統合ブランチに向けて作る** — PR が 2 本とも同じコミットを含み、レビュー範囲の重複と PR の順序依存（先にどちらをマージするか）が生まれる。

## 影響

- 統合 PR の diff に設計・計画のドキュメントが混ざる（作らない運用を選んだ場合）。PR 本文でその旨に触れ、チケット別サマリと分けて読めるようにする。
- 設計＋計画 PR を作らない運用では、計画が main に入るのは統合 PR のマージ時になる。実装セッションは統合ブランチ上の plan を読むため支障はないが、他機能のセッションから `origin/main` の `docs/plan/<機能名>/` は見えない（ハブの参照は作業ブランチ・統合ブランチ側を見る — 各スキルの機能一覧の走査は既にブランチ側を見る作りになっている）。
- ticket-implement の再開判定は、`docs/plan/<機能名>/README.md` の所在を「統合ブランチ / 作業ブランチ / origin/main」の 3 か所で探す形になる。
