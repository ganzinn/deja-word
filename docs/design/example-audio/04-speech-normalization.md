# 04. 読み上げ正規化（括弧）

状態: **確定**（2026-08-04）

## 前提（確定事項の再掲）

このトピックが依存する決定。覆す場合はハブ（README.md）と決定元の両方を更新すること。

- 読み上げ対象は例文の英文（`Example.text`）のみで、和訳は読み上げない（01 確定）。
- 例文にも発音音源（mp3）を登録でき、未登録のときだけ TTS にフォールバックする（01 確定）。
- 対象は全例文種別（TARGET / PHRASE / MINIMAL / SENTENCE）（01 確定）。
- TTS 読み上げ時のテキスト正規化に括弧規則を追加することはスコープに含む（01 確定）。

## 前提（既存実装・本番データ）

- `toSpokenText`（`src/lib/speech.ts`）は純関数で、読み上げの一本道 `speakEnglish` の入口 1 箇所からのみ呼ばれる。ブラウザ `speechSynthesis` 経路と Android ネイティブブリッジ経路（ADR-0073）の両方に効く。
- 現行の除去規則は 3 つ（ADR-0077 / ADR-0078）: 装飾記法（`stripRichTextMarkup`）→ 注記 `【…】` を中身ごと → プレースホルダ（`...` 3 個以上・`…`・チルダ 3 字形）。その後に連続空白を 1 つへ畳んで trim。**括弧は未対応**。
- 本番データ（2026-08-03 時点）で括弧を含む TG 例文は 5 行のみ。丸括弧 4 件はすべて「省略可能な語」、角括弧 1 件は「言い換え候補」。

| 例文 | 括弧の意味 |
| --- | --- |
| `(be) similar to 〜` | 省略可能 |
| `consider A (to be) B` | 省略可能 |
| `demand that A (should) do` | 省略可能 |
| `suggest (to 〜) that ...` | 省略可能（中にチルダを含む） |
| `compare A with [to] B` | 言い換え候補（`with` または `to`） |

- 本番の見出し語・関連語の見出しに括弧を含むものは現時点で無い。
- 表示側 `TgExampleText`（`src/components/tg-example-text.tsx`）の `TG_TEXT_PATTERN` は括弧を含むプレースホルダ記号の体裁を変えるが、**半角括弧のみ**を対象にしている。

## 検討事項リスト

- [x] `(…)` は括弧記号だけ落として中身を読む / `[…]` は中身ごと落とす → 決定 1
- [x] 全角括弧・ネスト・閉じ括弧欠落など変則入力の扱い → 決定 2、全角と表示の整合 → 決定 3
- [x] 既存の除去規則（ADR-0077 / 0078）との順序・干渉 → 決定 4
- [x] 除去後の空白・句読点の整形 → 決定 4（既存処理をそのまま通す）
- [x] 正規化の適用範囲（例文のみか、見出し語・関連語にも効かせるか） → 決定 5
- [x] 正規化は TTS 経路にのみ効き、登録済み音源には影響しないことの明示 → 決定 5
- [x] スラッシュ・引用符など括弧以外の記号を今回扱うか → 決定 6

## 議論・決定

### 決定 1: 括弧は意味で出し分ける（`(…)` は記号だけ落として中身を読む / `[…]` は中身ごと落とす）

`toSpokenText` に括弧規則を追加する。読み上げ結果:

| 入力 | 読み上げ |
| --- | --- |
| `(be) similar to 〜` | `be similar to` |
| `consider A (to be) B` | `consider A to be B` |
| `demand that A (should) do` | `demand that A should do` |
| `suggest (to 〜) that ...` | `suggest to that` |
| `compare A with [to] B` | `compare A with B` |

`A` / `B` / `do` / `doing` は落とさず英語として読ませる（naming-book のプレースホルダ語）。

採用理由: 丸括弧の中身は前後と繋げて読んでも英文として成立するが、角括弧の中身は直前の語と入れ替える候補なので、並べて読むと `compare A with to B` という非文になる。本番データの用途は丸括弧 4/4 件が「省略可能」、角括弧 1/1 件が「言い換え候補」で、辞書の慣習どおりに使い分けられている。記号の意味が確定しているので、ADR-0078 の原則「意味が分かっている記号だけ落とす」に沿って規則化できる。

却下した代替案:
- **両方とも記号だけ落として中身を読む**: 情報は落とさないが `compare A with to B` と非文になり、誤った語順を耳から覚えさせる。
- **両方とも中身ごと落とす**: 最短だが `consider A (to be) B` が `consider A B` になり、覚えるべき `to be` が消える。「省略可能＝読まなくてよい」ではない。
- **`A` / `B` / `do` / `doing` もプレースホルダとして落とす**: `compare with` のように骨組みだけが残り、文として聞けない。
- **保存データ側から括弧を消す**: 括弧は表示としては必要な情報（省略可能・言い換え可能であること）。表示と読み上げで要求が違うだけなので保存物は変えない（ADR-0078 と同じ判断）。

### 決定 2: ペアが取れない括弧・ネストは「記号だけ落として中身は読む」に倒す

実装は 2 段で行う。

1. `[…]`（半角・全角）のペアが取れる箇所を**中身ごと**除去する。
2. 残った括弧記号 `(` `)` `[` `]` `（` `）` `［` `］` を**記号単体で**除去する。

この結果、変則入力は次のように扱われる:

| 入力 | 読み上げ | 経路 |
| --- | --- | --- |
| `consider A (to be B` | `consider A to be B` | 丸括弧はそもそもペア判定しない（2 のみ） |
| `compare A with [to B` | `compare A with to B` | 1 が不一致 → 2 で記号のみ除去 |
| `(a (b) c)` | `a b c` | 丸括弧は入れ子でも記号が全部落ちる |
| `compare A with (to [or] from) B` | `compare A with to from B` | 1 で `[or]` が消え、2 で丸括弧の記号が落ちる |

採用理由: 丸括弧は「記号だけ落とす」規則なので、そもそもペアを判定する必要がない（2 の一律除去だけで決定 1 を満たす）。角括弧はペアが必要だが、ペアが崩れた入力で除去範囲を推測して文末まで落とすと語が丸ごと消え、情報の損失という最も重い失敗になる。読み上げが非文になるのは入力ミスの結果として許容できるが、語が消えるのは許容できない。孤立した記号を読ませないことは 2 で担保される。

却下した代替案:
- **ペアが取れない括弧記号はそのまま残す**（`【…】` の既存実装と同じく、閉じが無ければ何もしない）: 孤立した `[` が合成エンジンによっては「ブラケット」と読まれる。ADR-0078 が解決しようとした「記号が読まれる」問題がそのまま残る。
- **角括弧のペア不一致時は行末まで落とす**: 除去範囲を推測することになり、`compare A with [to B` が `compare A with` になって語が消える。
- **ネストを厳密に対応付けるパーサを書く**: 実データにネストは存在せず、正規表現 2 本で足りる問題に対して過剰。

### 決定 3: 括弧は半角・全角の両字形を対象とし、表示側のハイライトにも全角括弧を足して揃える

`toSpokenText` は `(` `)` `[` `]` に加えて `（` `）` `［` `］` を対象にする。あわせて `TG_TEXT_PATTERN`（`src/components/tg-example-text.tsx`）の括弧にも全角字形を追加し、同一チケットで揃える。

採用理由: 入力元で字形が揺れるため両方対象にするのは、チルダ 3 字形をすべて対象にした ADR-0078 と同じ方針。表示を揃えないと「読み上げでは落ちるが表示ではハイライトが付かない」非対称が残り、入力者に「この括弧は認識されていない」と誤読させる。和訳側（`meaning_text`）は全角丸括弧が 713 件と入力癖が強く、英文側へ混入する可能性は高い。追加コストは正規表現 1 行。

却下した代替案:
- **正規化のみ全角対応し、表示ハイライトは別件にする**: example-audio のスコープを読み上げに閉じられるが、非対称を残したまま「本番に全角は 0 件だから実害なし」と先送りすることになる。ハイライトへの追加が正規表現 1 行である以上、分ける利点がない。
- **半角のみ対象**: 非対称は生じないが、全角が混入したとき括弧記号がそのまま読まれる。ADR-0078 で字形の揺れを吸収した方針と逆行する。

表示側の変更を伴うため、機能紹介ドキュメント（`docs/features/`）の再撮影要否は 06 で棚卸しする。

### 決定 4: 除去順序は「装飾記法 → `【…】` → `[…]` → 残存括弧記号 → プレースホルダ → 空白畳み込み」

`toSpokenText` の既存 3 規則の間に括弧処理を挟み、最後の `\s+` 畳み込みと `trim()` はそのまま通す。除去は既存と同じく空文字ではなく**空白 1 個への置換**とし、語の結合（`A(B)` → `AB`）を防ぐ。

この順序で既存規則との干渉が解決される:

- `suggest (to 〜) that ...` — 丸括弧は中身を読むので、括弧処理の後にプレースホルダ処理が走り `suggest to that` になる。既存テストが固定している現行の期待値 `suggest (to ) that` は本決定で更新される。
- `[…]` を `【…】` と同じ「中身ごと」グループとして先に処理するため、角括弧の中にチルダや省略記号があっても中身ごと消える。
- 丸括弧の中に角括弧がある場合（`(with [to])`）、角括弧が先に消えてから丸括弧の記号が落ちる（決定 2 の表のとおり）。

採用理由: 「中身ごと落とす」処理を「記号だけ落とす」処理より先に置かないと、先に括弧記号が消えて除去範囲を見失う。プレースホルダ処理を括弧処理より後に置くのは、括弧内に残ったチルダ・省略記号を拾うため。空白置換は既存 2 規則がすでに採っている形で、揃えない理由がない。

却下した代替案:
- **括弧処理をプレースホルダ処理の後に置く**: `(to 〜)` のチルダが先に消えて `(to )` になり、そこから括弧を落としても結果は同じだが、角括弧内の記号が先に消える分だけ中間状態が読みにくくなる。順序の意味を「中身ごと → 記号だけ」で説明できる現案のほうが、規則を足すときの置き場が迷わない。

### 決定 5: 正規化は `toSpokenText` の 1 箇所に足し、読み上げ全経路（見出し語・関連語を含む）に効かせる。登録済み音源には影響しない

括弧規則は `toSpokenText` にのみ追加し、例文専用の分岐や引数（種別・フィールドの区別）は設けない。結果として見出し語（`Word.headword`）・関連語の見出し（`RelatedWord.term`）の読み上げにも同じ規則が掛かる。

登録済み mp3 の再生経路（`<audio>` / `preloadAudio`）は正規化を通らないため、音源がある行の聞こえ方は一切変わらない。正規化するのは合成へ渡す文字列だけなので、正規化の追加によって表示が変わることもない（表示側の変更は決定 3 のハイライト対象拡張のみで、これは別の変更）。TTS フォールバックが効くのは音源未登録かつ設定 ON のときだけ（ADR-0046）という既存条件もそのまま。

採用理由: ADR-0078 が「呼び出し側で正規化すると新しい呼び出し元で漏れて静かに劣化する」として一本道に集約した判断を踏襲する。例文だけ別規則にすると `toSpokenText` に対象種別の引数が必要になり、呼び出し元ごとに正しい種別を渡す責務が生まれて漏れの余地が復活する。本番の見出し語・関連語に括弧を含むものは無いため、既存の読み上げが変わる実害も現時点では無い。

却下した代替案:
- **括弧規則を例文だけに適用する（`toSpokenText(raw, { kind })` のような引数を足す）**: 見出し語に括弧が入ったときに読まれてしまい、しかもそれが「例文には効くのに見出し語には効かない」という説明しにくい非対称になる。

### 決定 6: スラッシュ・引用符など括弧以外の記号は今回扱わない

`/`（`with/to` のような並列表記）、`"` `'` `“` `”` は本番の英文データに 0 件のため、規則を追加しない。将来必要になったら `toSpokenText` に 1 規則足す（ADR-0078 の想定どおり）。

採用理由: ADR-0078 の原則は「意味が分かっている記号だけ落とす」。実データが無い記号は用途を確定できず、推測で規則を作ると `don't` のアポストロフィのように壊してはいけないものまで巻き込むリスクがある。

却下した代替案:
- **`/` を角括弧と同じ「言い換え候補」とみなして後半を落とす**: `with/to` なら妥当だが、`and/or` や日付・分数表記など別用途もありうる。実データで用途を確認してから決めるべき。
