# 02. 設定モデルと移行

状態: **確定**（2026-08-15）

## 前提（確定事項の再掲）

このトピックが依存する決定。覆す場合はハブ（README.md）と決定元の両方を更新すること。

- 訳語の表示制御は形式ごとに別設定を持たせず、1 つの共通設定に統合する（ユーザー合意、設計開始時）。
- 共通設定は出題データの生成時に反映し、四択（英→日）の選択肢と日→英 3 形式（四択・自己判定・スペル確認）の問題文にだけ効かせる。結果一覧はその再表示なので該当列（四択（英→日）の正解列と「自分の回答」列、日→英 3 形式の問題文列）にも同じ内容が出る（結果一覧向けの分岐は作らない）（01 確定）。
- 多義語選択の選択肢・自己判定（英→日）の解答表示とその正解列・TG 例文形式 4 種・訳語が出る他の画面には効かせない（01 確定）。
- ON は最初の Meaning の先頭 MeaningText 1 つ、OFF は最初の Meaning の MeaningText を「; 」連結（01 確定）。
- 既定値は未設定＝ON を維持し、デフォルト設定の既存保存値は変換せずそのまま引き継ぐ。進行中 drill に保存済みの値の扱いはこのトピックで決める（01 確定）。
- 自己判定（英→日）の解答表示と結果一覧のその正解列で、先頭 Meaning の先頭訳語をアプリが常時（設定非連動で）赤字にする。赤字は生成データの内容を変えない表示側の体裁だが、結果一覧の正解列は現在「; 」連結済みの文字列のため渡し方の見直しが要る（01 確定）。
- 先頭の訳語だけでは答えが一意に定まらない問題文は許容する。四択（日→英）のダミー選択肢の緩和策の採否はこのトピックで決める（01 確定）。

## 議論・決定

### 決定 1: コード名・DB 列名とも `firstMeaningTextOnly` / `first_meaning_text_only` へ改名する

`choiceFirstMeaningTextOnly` を `firstMeaningTextOnly` に、DB 列 `choice_first_meaning_text_only`（`quiz_default_setting` / `drill` の 2 テーブル）を `first_meaning_text_only` に改名する。マイグレーションは `ALTER TABLE ... RENAME COLUMN` を手書きする（2 テーブル分。データのコピーは不要）。

採用理由: 適用先が四択（英→日）だけでなくなるため、`choice` を冠したままでは設定の適用範囲を誤読させる。Prisma のマイグレーション生成は列のリネームを検出できず drop / add になるため手書きにするが、この repo には手書き SQL で移行を書いた前例がある（`prisma/migrations/20260614020615_split_quiz_sound_settings`）。`RENAME COLUMN` はデータコピーを伴わずロックも短い。

運用上の注意: リネームは旧コードとの後方互換が無く、マイグレーション適用から新コード配備までの間に旧コードが動くとテスト開始・drill 生成が落ちる。新旧を両立させるには「新列追加 → 二重書き → 旧列 DROP」を別々のリリースに分ける必要があるが（引用した前例は 3 段を 1 本の SQL で実行しており、段階移行の前例ではない）、個人利用規模の短時間の不整合として許容し、段階移行は採らない。この列を参照する raw SQL・ops スクリプトは無く（Prisma 経由のみ）、リネーム漏れの隠れ経路はない。

却下した代替案:

- Prisma の `@map` で旧列名のまま、コード名だけ汎用化する: マイグレーション不要でリスクは最小だが、DB を直接見たとき（ops スクリプト・本番調査）に列名と適用範囲が食い違ったまま残る。
- 新列を追加して値をコピーし旧列を DROP する（`split_quiz_sound_settings` と同じ手法）: 列の意味が分割・変化する場合には要るが、今回は同じ値をそのまま使うため冗長。

### 決定 2: 既定値の非対称は現状のまま残す

既定を持つ層は 4 つあり、いずれも現状の値を維持する。

| 層 | 未設定・未指定のときの値 |
| --- | --- |
| デフォルト設定（`QuizDefaultSetting`、nullable） | null = ON（アプリ既定） |
| 画面の初期値・「デフォルト設定に戻す」の推奨値（`DEFAULT_QUIZ_SETTINGS`、両フォームの `?? true`） | true（明示値として保存されうる） |
| drill 列（`NOT NULL @default(false)`） | false（既存行の backfill 値。作成時は常に明示値が入る） |
| 生成オプション（`BuildQuizOptions`、optional） | false（従来どおりの「; 」連結） |

採用理由: 「未設定」の意味が層ごとに違う。ユーザーが設定していないことを表す設定側は機能としての推奨値（ON）へ倒すのが自然で、画面の初期値もそれに合わせる。一方、生成側の未指定は入力の取りこぼしであり、表示を減らす側へ倒すと問題文が黙って短くなるため OFF へ倒す。本番の呼び出し経路では必ず値が渡る（テスト開始は zod スキーマで必須、drill のラウンド生成・再テスト生成は `Drill` の NOT NULL 列から読む）が、`buildQuiz` / `checkFormatAvailability` のデフォルト引数自体は残るため、テストや将来追加する呼び出しでは未指定に到達しうる。決定 3 で適用先が 4 形式へ広がる分、取りこぼし時の影響範囲も広がる点は許容する。

却下した代替案:

- 4 層すべて「未指定＝ON」に揃える: drill 列の default 変更にマイグレーションが必要で、生成側の取りこぼしが表示の縮小として現れるようになる。揃うのは字面だけで、役割の違いは消えない。
- 生成オプションを必須フィールドにして既定を無くす: 取りこぼしを型で防げるが、`BuildQuizOptions` は出題順の指定と同じ optional な袋で、1 項目だけ必須にすると呼び出し側（テストを含む）すべてに影響する。

### 決定 3: 表示文字列の切替は共通ヘルパ 1 つに集約し、生成オプションから各ビルダーへ boolean で渡す

- `src/lib/quiz/generation/material.ts` に「設定に従って最初の Meaning の表示文字列を作る」関数 `firstMeaningDisplayText(word, firstMeaningTextOnly): string` を置く（既存の `firstMeaningText` / `firstMeaningHeadText` を分岐で選ぶ形。実体は四択（英→日）の `choiceDisplayText` の移設・改名で、引数・戻り値は同じ）。
- `BuildQuizOptions` のフィールド名は `firstMeaningTextOnly` に改名し、`buildQuestions` の `CHOICE` に加えて `CHOICE_JA_EN` / `SELF_JUDGE_JA_EN` / `SPELLING` の各 case からビルダーへ boolean で渡す（引数の形は既存 `buildChoiceQuestions(material, rng, firstMeaningTextOnly)` に揃える）。
- 四択（英→日）の重複排除キー（`choiceCandidateTexts`）と成立判定での使われ方は変えない。

採用理由: 「ON なら先頭の訳語 1 つ、OFF なら『; 』連結」は 4 形式で同一の規則で、実装が分かれると片方だけ直す事故が起きる。オプションを options オブジェクトのまま各ビルダーへ渡さないのは、ビルダーが必要とするのは boolean 1 つで、options 全体を渡すと出題順など無関係な項目にも依存できてしまうため。

却下した代替案:

- 日→英 3 形式それぞれのビルダー内で `firstMeaningTextOnly ? firstMeaningHeadText(w) : firstMeaningText(w)` を書く: 呼び出しは短いが同じ分岐が 4 箇所に散る。
- 問題文の生成をやめ、payload に訳語配列を持たせて表示側で連結する: 表示側の自由度は上がるが、成立判定・重複排除が生成側にある構造と食い違い、形式ごとの payload 型が揺れる。

### 決定 4: 四択（日→英）は、設定 ON のとき先頭の訳語が正解と衝突する単語をダミーから外す。そのためにダミー候補のキーを 2 種類に分ける

ダミー選定（`src/lib/quiz/generation/dummy-pool.ts`）の候補は現在 `texts` 1 つで「正解と一致するものを除外する」判定と「選定済みダミー同士の重複排除」の両方を担っている。四択（日→英）では選択肢の表示が headword なので、後者は headword で行うのが正しい。そこで候補に**正解一致判定にだけ使うキー**を足し、次のようにする。

- 四択（日→英）で設定 ON のとき: 正解側のキーに target の先頭訳語を加え、候補側の正解一致判定用キーにも候補単語の先頭訳語を加える。重複排除は従来どおり headword で行う。
- 設定 OFF のとき、および四択（英→日）: 現状と同じキー（四択（英→日）の `choiceCandidateTexts` の使われ方は変えない）。
- 空文字（訳語が未登録の単語）はキーに載せない（空文字同士を衝突と判定しないため）。
- キーの作り方は生成と成立判定（`checkFormatAvailability`）で共有する（四択（英→日）が `choiceCandidateTexts` を共有しているのと同じ形）。
- 追加するキーは**任意フィールドとし、省略時は従来のキーと同じ**として扱う。候補を組み立てている箇所は生成側 5 形式＋成立判定側 4 箇所あり、必須にすると今回関係しない形式まで touch することになるため。

これにより四択（日→英）は初めて「ダミーを確保できず成立しない」経路を持つ。テスト開始時は成立判定で弾いて理由を表示できるが、drill のラウンド生成・再テスト生成は成立判定を経ずに `buildQuiz` を直接呼ぶため、候補が尽きた場合は生成時のエラーになる。プールが足りないだけなら既存の縮退規則（最低 2 択）に従うので、実際にエラーへ至るのは、ダミー候補（同一掲載箇所＋全登録単語）がすべて headword か先頭訳語で正解と衝突するとき—登録語数がごく少ないか、先頭訳語が極端に偏っているとき—に限られる。このリスクを受け入れる。

採用理由: 01 決定 5 で「答えが一意に定まらない問題文」は許容したが、四択（日→英）は選択肢を生成側で選べるため、同じ問題文に対して正解と等価な選択肢が並ぶ事態だけは低コストで避けられる。自己判定・スペル確認には選択肢が無く、同じ緩和は適用できない。キーを 2 種類に分けるのは、1 つのキーに先頭訳語を混ぜると「先頭訳語が同じダミー同士」まで相互排他になり、表示（headword）は重複しないのにダミー候補だけが減るため。

却下した代替案:

- 緩和策を入れない: 実装は減るが、四択で「どちらも正しいのに一方だけ正解」という体験が残る。設定 ON を既定にする以上、既定の体験の質に直結する。
- 正解側のキーにだけ先頭訳語を足す: 候補の形を変えずに済むが、除外判定は候補側のキーを見る実装なので何も起きない（機能しない）。
- 候補の単一キーに先頭訳語を混ぜる: 変更は最小だが、上記のとおりダミー同士の重複排除まで巻き添えになる。
- 設定 OFF のときも先頭訳語をキーに含める: OFF では問題文が全訳語なので、先頭だけ同じ単語をダミーから外す理由が無く、ダミー候補を不必要に減らす。

### 決定 5: 赤字強調は、解答表示は表示コンポーネントの引数で、結果一覧は正解列を構造化して渡す

- 自己判定（英→日）の解答表示: payload（`MeaningDisplay[]`）は変えない。表示コンポーネント（`MeaningBlocks`）に「先頭 Meaning の先頭訳語を強調するか」の引数を足し、自己判定（英→日）の解答表示から ON で呼ぶ。
- 赤字の当て方は、`MeaningText` にベース体裁を渡す口を開ける形にする（`renderPlaceholders` がプレースホルダの体裁とユーザー記法を合成しているのと同じ経路にベースとして載せ、ユーザー記法を後勝ちにする）。呼び出し側でラッパー要素を足す形は採らない。
- 結果一覧の正解列: `ResultRow.correctDisplay` を文字列から「表示要素の配列＋先頭を強調するか」を持つ構造へ変え、形式別の導出（`correctAnswerDisplay`）でどちらを立てるかを決める。自己判定（英→日）だけ配列（最初の Meaning の訳語）＋強調ありとし、他形式は単一要素・強調なし。
- 描画は正解列専用の関数を入口として設け、**強調なしのときは既存のヘルパ（形式の種別で 4 分岐し、文字列を受け取る関数）へ委譲する**。形式による分岐の実装は 1 箇所に保ち、専用関数が持つのは「強調ありのときに配列を組み立てて先頭を赤字にする」経路だけとする。強調ありになるのは自己判定（英→日）だけであり、専用関数はその前提（種別は訳語表示のもの 1 つ）で書く。他形式へ強調を広げるなら、この前提から見直す。「自分の回答」列は従来どおり、そのヘルパを文字列で呼ぶ。
- 配列の描画は要素ごとに訳語の描画コンポーネントを通し、区切りの「; 」は要素の間に置く。装飾記法の解釈単位が「連結後の文字列全体」から「訳語 1 件ごと」に変わるが、記法は訳語 1 件の中で閉じるのが本来の使い方なので許容する。

採用理由: 解答表示は payload に訳語が配列のまま届いており、強調は体裁の問題なので表示側で完結する。結果一覧だけは導出時に連結してしまっているため、先頭訳語を切り出すには構造を保つしかない。強調の要否を形式別の導出（既に形式網羅 switch がある場所）で決めることで、形式追加時の更新漏れを型で検出できる状態を保つ。既存ヘルパを 2 形（文字列と構造）受けにせず入口を分けるのは、「自分の回答」列は構造化しないと決めた以上、共用のままだと使わない分岐を全形式に配ることになるため。委譲にするのは、専用関数の中で形式分岐を再実装すると同じ 4 分岐が 2 箇所に散るため。

却下した代替案:

- 結果一覧でも文字列のまま渡し、描画側で最初の「; 」までを先頭訳語とみなす: 構造変更は不要だが、訳語自体が「; 」を含む場合に破綻し、表示ロジックが文字列の形に依存する。
- 既存ヘルパに構造も受けさせる（オーバーロード）: 入口を増やさずに済むが、構造を扱わない「自分の回答」列からも構造を渡せるように見え、形式分岐の中に強調の分岐が混ざる。
- `MeaningBlocks` を自己判定（英→日）専用に分岐させる: 引数を足さずに済むが、共用の想定で作られたコンポーネント（docstring 上は日→英の問題文とも共用の想定）に呼び出し元の事情を埋め込むことになる。
- 呼び出し側で `<span className="text-red-500">` を巻く: 実装は最短だが、ユーザーの装飾記法との合成が既存経路から外れ、記法で色を上書きできなくなる。

### 決定 6: 進行中 drill の保存値は移行せず、新しい適用範囲をそのまま適用する

既存の drill 行（日本語→英語形式を含む）の値は書き換えない。実装後は進行中 drill の次ラウンドから、保存値が ON の日→英 drill の問題文が先頭の訳語 1 つになる。「同じ範囲でもう一度テストする」へ値が伝播する既存経路もそのまま使う。

採用理由: 日→英 drill に保存されている値は、開始フォームのトグルが四択（英→日）選択時しか表示されない一方で値は形式によらず送られるため、ほとんどの場合デフォルト設定の値（未設定なら ON）がそのまま流れたものになる（四択を選んでトグルを操作したあと形式を切り替えて開始した場合だけ、その操作値が入る）。いずれもそのユーザーが選んだ／受け入れた値であり、共通設定として読み替えても設定の意図と食い違わない。drill は短命なデータで、移行のために形式で絞った backfill を書くと、その SQL 自体が「日→英だけ OFF」という説明の付かない状態を作る。

却下した代替案: 既存の日→英 drill 行だけ false へ backfill する: 進行中の見え方は変わらないが、その drill は以後「共通設定 OFF」として振る舞い、ユーザーのデフォルト設定と食い違う。

### 決定 7: ドメイン用語は改名に追随し、訳語の色に関する記述も更新する

`docs/reference/naming-book.md` を次のとおり更新する。

- `QuizDefaultSetting` エントリのフラグ列挙を新名 `firstMeaningTextOnly` へ差し替える。
- `orderByOccurrenceNumber` エントリと同じ書式で `firstMeaningTextOnly` の単独エントリを立てる（DB 列名・保持先（`QuizDefaultSetting` / `Drill` / テスト開始入力）・適用先の形式を書く）。
- 「訳語には色を付けない」旨の記述 2 箇所（訳語エントリの混同注意と、プレースホルダの斜体エントリの混同注意）に、自己判定（英→日）の解答表示と結果一覧の正解列では先頭の訳語だけアプリが赤字にする例外を書く。

「描画は `MeaningText` に集約し」という記述（訳語エントリ）は更新しない。決定 5 で赤字も `MeaningText` 経由に載せるため、集約自体は壊れないため。画面によって体裁が変わる点（ADR-0083 の「訳語が出る全画面で同じ体裁」）は用語集ではなく ADR 側で扱う。

採用理由: 改名後の名前と、既存記述と矛盾する挙動（訳語への着色）を残すと、用語集が実装と食い違ったまま参照され続ける。壊れていない記述まで注記を足すと、更新の必要な箇所が埋もれる。
