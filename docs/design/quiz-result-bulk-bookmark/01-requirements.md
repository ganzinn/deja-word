## 議論・決定

### 決定 1: ユースケース — 結果画面で「間違えた問題だけ表示」チェック ON のときだけ、明示ボタンで一括ブックマークできる

テスト結果で間違えた単語をまとめてブックマークし、後からブックマーク絞り込み（一覧・テスト範囲指定）で復習できるようにする。実行はユーザーがボタンを押したときだけで、テスト完了やチェック ON による自動登録は行わない。チェック OFF（全問題表示）の状態では一括操作を提供しない（ボタンを出さない）。

- 採用理由: ユーザー要求そのもの（「チェックを入れたときだけ」「必ずブックマークするわけではない」）。チェック ON は「間違えた単語に注目している」意図の表明であり、対象が画面上で見えている状態でのみ一括操作を許すことで誤操作と対象の不透明さを防ぐ。
- 却下した代替案: 常時表示のボタン（チェック OFF 時は対象が画面の表示と一致せず、何が登録されるか不透明になる）。テスト完了時の自動ブックマーク（ユーザー要求に反する）。

### 決定 2: 対象モードは全モード共通（TEST / DRILL / DRILL_RETRY）

結果画面（`ResultList`）を使う全モードで同じ仕様・挙動とする。「共通」は仕様・挙動の話であり、実装上の判定源が送信状態の変種（`success` / `drill-success`）で分かれることは妨げない。

- 採用理由: 結果画面と「間違えた問題だけ表示」チェックは全モード共通のコンポーネントで、共通のまま乗せるのが実装・仕様ともにシンプル。定着モード・再テストでも「間違えた単語を後で復習したい」需要は同質。
- 却下した代替案: TEST のみ（モード分岐の実装が増え、定着モード・再テストの結果画面だけ機能が欠ける非一貫が生じる）。

### 決定 3: 対象単語 = チェック ON 時に表示されている行の単語（削除済みを除く）

対象の定義の正は「間違えた問題だけ表示」の絞り込み条件そのもの（`result !== "CORRECT"`）とする。結果種別の列挙（現状の内訳: INCORRECT / VAGUE / GAVE_UP / TIMEOUT）は例示であり、絞り込み条件の側が正。あいまい（VAGUE）も絞り込みで表示される以上、復習対象として含める。付帯条件:

- **削除済み単語の除外**: 判定源は履歴送信の応答（TEST / DRILL_RETRY は `skippedWordIds` = 保存されなかった wordId 群（削除済みのほか scoped 外も含む）、DRILL は応答の残数一覧 `remaining` に該当 wordId の行が無いこと）。削除済み単語は参照先が無く登録できないため除外する。行の表示自体は変えない（対象から除くだけ。削除済み行は「削除済み」表示付きで一覧に残る）。この判定は送信応答時点のスナップショットであり、押下時点までに削除された単語は検知できない（混入時のサーバー側の扱いは 02 で決める）。除外により表示行数と登録件数が乖離し得るため、その見せ方は 03 で決める。
- **一括操作は履歴送信の成功後のみ実行可能**: 理由は 2 つ。(a) 削除済みの判定情報が送信成功後にしか存在しない（前項のとおり best-effort の除外源だが、押下時点で得られる唯一の除外源）。(b) 結果画面の他の前進導線（定着モード開始・再テスト・次のラウンド）が一律に送信成功でゲートされており、その一貫性に合わせる。このゲートは UI 上の要件であり、サーバー側は削除済み混入を前提に設計する（02）。「成功」は `success`（TEST / DRILL_RETRY）と `drill-success`（DRILL）の両方を指す（DRILL のみ別変種のため、`success` 一本ではゲートしない）。送信中・送信失敗時の見せ方は 03 で決める。
- **対象 wordId 群はクライアントから渡す**: 結果行はクライアント状態にのみ存在し、サーバーはテストセッションを持たないため再導出できない（ADR-0024。画面遷移をクライアント状態で持つ決定は ADR-0031）。受け渡しのシグネチャは 02 で決める。
- **対象 0 件時の扱いは 03 で決める**: ケースの分類（誤答 0 件のチェック ON・全行削除済み等）と見せ方は、ボタン配置とあわせて 03 の検討事項に一本化する。
- 同一単語が複数行に出ることは無い前提（1 回の出題 — TEST / DRILL の各ラウンド / 再テスト — で同一単語は 1 問。結果一覧の行 key が `wordId` であることと整合）。

補足: ADR-0088（結果ダイアログの前後ナビ）は削除済み行を「ナビからスキップしない」と決めているが、それは表示・ナビゲーションについての決定。本件は書き込み先が存在しないための除外であり、矛盾ではなく別判断。

- 採用理由: ユーザーが画面で見ている行と一括登録の対象が一致し、対象が自明になる。削除済み単語は登録先が無く、行トグルでも操作不能なので除外が自然。
- 却下した代替案: INCORRECT のみ等の独自の「間違い」定義（チェックボックスの絞り込み条件と食い違い、見えている行と登録対象がズレる）。

### 決定 4: 既ブックマーク済みの単語も対象に含め、冪等に扱う

対象単語のうち既にブックマーク済みのものも除外せず、一括登録に含める（結果は変わらない）。

- 採用理由: 既存の 1 件トグル（`setBookmarkForUser`）が冪等 set（ON = upsert）方針であり、同じ方針なら「対象 = 表示行」の単純な定義を保てる。事前除外しても最終状態は同じで、除外ロジックの分だけ複雑になる。
- 却下した代替案: 既ブックマーク済みを事前除外して未登録分だけ送る（最終状態が同じなのに UI 側の対象計算が増える）。

### 決定 5: 一括操作は登録のみ（一括解除・Undo はスコープ外）

- 採用理由: 対象は高々テスト 1 回分の誤答数で、誤って押した場合も既存の行トグル（`RowBookmarkButton`）で個別に外すのが現実的。登録のみなら、テスト前から存在する既存ブックマークを誤って外す事故が構造的に起きない。
- 却下した代替案: Undo 付き登録（直前操作で新規登録された分だけ解除する状態管理が必要になり、得られる回復手段は個別トグルで代替可能）。一括解除ボタンの併設（既存ブックマークを巻き込んで外す誤爆の設計が別途必要になる）。

### スコープ外

- 一括解除・Undo（決定 5）
- 結果画面以外（単語一覧・単語詳細など）での一括ブックマーク操作
- ブックマーク機能自体の仕様変更（データモデル・絞り込み・既存トグルの挙動）
