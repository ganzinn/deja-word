# 03. UI

状態: **確定**（2026-08-08）

## 前提（確定事項の再掲）

このトピックが依存する決定。覆す場合はハブ（README.md）と決定元の両方を更新すること。

- 一括ボタンは「間違えた問題だけ表示」チェック ON のときだけ提供し（チェック OFF ではボタンを出さない）、明示押下で実行する（自動登録なし）（01 確定）。
- 全モード共通（TEST / DRILL / DRILL_RETRY）で仕様・挙動を分けない（判定源が送信状態の変種で分かれる実装分岐は妨げない）（01 確定）。
- 対象単語 = チェック ON 時の表示行（`result !== "CORRECT"`）から削除済み行（判定源は送信応答: TEST / DRILL_RETRY は `skippedWordIds` = 保存されなかった wordId 群（削除済みのほか scoped 外も含む。本トピックでは「削除済み」と総称）、DRILL は応答の残数一覧 `remaining` に行が無いこと）を除いたもの。既ブックマーク済みも含む（01 確定）。
- 一括操作は履歴送信の成功後（TEST / DRILL_RETRY の `success`・DRILL の `drill-success`）のみ。送信中・失敗時・対象 0 件時の見せ方は本トピックの検討事項で決める（01 確定）。
- 一括解除・Undo はスコープ外（誤操作時は既存の行トグルで個別解除）（01 確定）。
- 一括登録 action は `addBookmarks({ wordIds })`。成功時は `bookmarkedWordIds`（操作後に ON 状態の wordId 群）と `skippedWordIds`（削除済み・範囲外で弾かれた wordId 群）が返る。全件スキップ時も `ok: true`＋`bookmarkedWordIds` 空になり得る（02 確定）。
- エラーは `unauthorized | invalid | unknown`（`forbidden` なし）で日本語 message 付き。失敗は常に全体失敗（部分適用なし）で、操作は冪等のため再実行が安全（02 確定）。
- `revalidatePath` は呼ばれない（楽観的更新方針）。02 から本トピックへの制約: 対象 0 件では action を呼ばない UI にする（空配列は `invalid` に落ちる）（02 確定）。

## 議論・決定

### 決定 1: ボタンは「間違えた問題だけ表示」チェックボックスの直下・行リストの上に置く

チェック ON かつ誤答行が 1 件以上あるときだけ、チェックボックス行の直下（行リスト `<ul>` の上）に一括ブックマークボタンを表示する。誤答 0 件のチェック ON（行リストが「間違えた問題はありません。」に置き換わる状態）ではボタンも表示しない。

採用理由: ボタンはチェック ON で出現するため、チェックボックスの直下に置くと出現の因果と「対象 = 表示されている行」の関係が視覚的に伝わる。誤答 0 件時は対象が存在し得ないため、disabled で残すより非表示が自然（AskUserQuestion でユーザー確定）。

却下した代替案:

- 画面下部のボタン群（「定着モードをはじめる」等）の最上段に追加する案 — 操作系は 1 箇所に集まるが、チェックボックスから遠く、行リストをスクロールしないと見えない。下部ボタン群は「次の行動」への導線であり、表示中リストへの操作とは性質が異なる。
- チェックボックスと同じ行の右端に置く案 — モバイル幅（`max-w-sm`）で件数入りラベルが窮屈になる。

### 決定 2: ラベルは件数入り「N語をまとめてブックマーク」

ラベルは `N語をまとめてブックマーク`（`BookmarkIcon` 付き）。N は対象単語数 = チェック ON 時の表示行から削除済み行を除いた数。削除済み判定は行表示と同じ計算（TEST / DRILL_RETRY は `skippedWordIds`、DRILL は `remaining` に無いこと）を使う。履歴送信の成功前は削除済み判定が確定しないため N は誤答行数のままとなるが、その間ボタンは disabled（決定 3）のため押下されることはなく、成功時に確定値へ更新される。外観は `variant="outline"` `size="sm"` の小型ボタン。配置先の親は `flex flex-col`（stretch）のため `self-start` を付けて内容幅・左寄せにする（下部ボタン群のような全幅 lg にはしない）。

採用理由: 削除済み行は削除済みであることの表示付きで一覧に残る（TEST / DRILL_RETRY は見出し行の「削除済み」バッジ、DRILL は残数バッジ枠の「削除済み」表示 — 機構は別だが文言は同じ）ため、表示行数と登録件数は乖離し得る。件数をラベルに含めることで、実際に登録される数が押下前に分かり、乖離ケースの見せ方を追加 UI なしで兼ねられる（AskUserQuestion でユーザー確定）。

却下した代替案: 件数なしの固定ラベル「まとめてブックマーク」 — シンプルだが、削除済み行がある場合に何語登録されるか押すまで分からない。

### 決定 3: 表示条件は「チェック ON かつ誤答行あり かつ bookmarkStates 取得済み」、disabled 条件は「送信未成功 or 対象 0 件 or 実行中」

- **非表示**: チェック OFF（01 確定）／誤答行 0 件（決定 1）／`bookmarkStates === null`（取得前・取得失敗）。取得失敗時は全行のブックマークトグルが非表示になる既存挙動と同じ条件でボタンも出さない（トグルが見えないのに一括登録だけできる不整合を避ける。取得失敗時のリトライは既存どおり行わない）。
- **disabled**: 履歴送信が成功状態でない（`sending` / `error`。TEST / DRILL_RETRY は `success`、DRILL は `drill-success` が成功）／対象 0 件（全行削除済みで N = 0。02 から 03 への制約「対象 0 件では action を呼ばない」を満たす）／一括登録の実行中（決定 6 の実行中フラグ）。
- 対象が全件既ブックマーク済みであることは disabled 条件に**含めない**。冪等な登録（01 確定）のため押下は無害で、その場合も決定 5 の成功 toast が出る（実際には状態が変わらなくても仕様どおり）。

採用理由: 下部ボタン群の既存パターン（`submitState.status` による disabled）と一貫し、送信完了と同時にボタンが突然出現してレイアウトが動くのを避ける（AskUserQuestion でユーザー確定）。`bookmarkStates` 未取得は「現在のブックマーク状態が分からない = 楽観的更新の起点が無い」状態のため、disabled ではなく非表示に倒す。

却下した代替案: 押せない間（送信中・対象 0 件）も非表示にする案 — 画面はすっきりするが、送信完了時のボタン出現でレイアウトシフトが起き、機能の存在にも気づきにくい。

### 決定 4: 押下後は既存パターンと同型の楽観的更新で行トグルへ即時反映する。実行本体は `QuizFlow` 側に置く

役割分担: `ResultList` は対象 wordId 群（決定 2 の N の内訳）の算出とボタン描画だけを担う。一括実行の本体（スナップショット・`useTransition`・action 呼び出し・ロールバック・toast・実行中フラグ）は、`bookmarkStates` Map を所有する `QuizFlow` 側に置き、`ResultList` へは「実行用コールバック（対象 wordId 群を渡す）」と「実行中フラグ」を新規 props で渡す。Map への先行反映は、既存の 1 件用 `onBookmarkChange` の繰り返しではなく、1 回の Map コピーで対象全件を更新する一括更新とする。

押下時の流れは既存 `BookmarkButton`（スナップショット + `useTransition` + 失敗時ロールバック）と同型:

1. 押下時に対象 wordId 群の現在のブックマーク状態をスナップショットする
2. `bookmarkStates` Map 上で対象全 wordId を ON に一括更新する（先行反映）。行の `RowBookmarkButton` は `bookmarkStates` の値変化（key 再マウント）で ON 表示になる — 行の表示反映に新規機構は不要
3. `startTransition` 内で `addBookmarks({ wordIds: 対象 })` を呼ぶ
4. 成功応答の `skippedWordIds` に入った wordId（押下直前に削除された等）はスナップショット値へ戻す
5. 失敗時は対象全 wordId をスナップショット値へ戻す（決定 6）

実行本体が常時マウントの `QuizFlow` 側にあるため、実行中に表示条件が変わってボタンが消えても（チェック OFF 等）、実行・ロールバック・toast は失われず継続する（決定 6）。

採用理由: 既存の個別トグルと同じ楽観的更新パターンのため、行の表示機構（`bookmarkStates` Map → key 再マウント）をそのまま使え、ユーザーには押下と同時に全行のトグルが ON になる一貫した体験になる。実行状態を state の所有者側に置くことで、ボタンの unmount で処理が失われる実装依存を避ける。`revalidatePath` を呼ばない方針（02 確定）とも整合する。

却下した代替案:

- 応答を待ってから反映する案 — 実装は単純だが、既存トグルの即時反映と体験が揃わず、待ち時間中に画面が無反応に見える。
- 既存の 1 件用 `onBookmarkChange` を対象件数分呼んで反映する案 — 呼び出しごとに Map の全コピーが走り、対象数に対して二乗のコピーになる。
- 一括ボタンのコンポーネント内で実行を完結させる案（既存 `BookmarkButton` の構造をそのまま流用）— チェック OFF 等でボタンが unmount されると実行中フラグ（コンポーネント内部 state）が失われ、実行中の再表示で disabled を復元できない。実行状態が state 所有者（`QuizFlow`）と別の場所に散る。

### 決定 5: 成功時は toast で件数を通知する（一部スキップは除外件数も通知）

成功時（`ok: true`）は応答内容で 3 分岐する:

- **全件登録**（`skippedWordIds` が空）: `toast.success("N語をブックマークしました")`
- **一部スキップ**（`bookmarkedWordIds`・`skippedWordIds` とも 1 件以上）: `toast.success("N語をブックマークしました（M語は登録できませんでした）")`。スキップ分の行トグルは決定 4 手順 4 で元に戻るため、この文言がその理由の通知を兼ねる（スキップされた行は送信応答時点では生きていたため「削除済み」バッジを持たず、toast 以外に理由が出ないため）
- **全件スキップ**（`bookmarkedWordIds` が空）: 成功 toast を出さず `toast.info("ブックマークできる単語がありませんでした")`。楽観的更新は決定 4 手順 4 で全件スナップショットへ戻る

toast の N はサーバー応答 `bookmarkedWordIds` の件数（= 操作後 ON になった数。既ブックマーク済みを含む）、M は `skippedWordIds` の件数。ラベルの N（決定 2、クライアント算出）とは別の値で、押下と登録の間に削除が起きた分だけずれ得る（ずれは M として通知される）。

採用理由: 一括操作は画面外の行も対象になり結果が見えにくいため、明示通知する（AskUserQuestion でユーザー確定）。件数をクライアント計算値でなくサーバー応答から取ることで、押下と登録の間に削除が起きたケースでも正確な数を伝えられる。押下前の乖離は件数入りラベル（決定 2）、押下後の乖離は toast の M が受け持ち、乖離の通知が非対称にならない。

却下した代替案: 既存の個別トグルと同じ無音（行トグル反映のみ）とする案 — 個別トグルは押した行が目の前で変わるため無音で足りるが、一括では画面外の行の変化が伝わらない。

### 決定 6: 失敗時は toast + 全件ロールバック、リトライは再押下、多重押下は実行中フラグで防止

- 失敗（`ok: false`）時は `toast.error(result.message)` を出し、対象全 wordId をスナップショットへロールバックする。エラー種別（`unauthorized | invalid | unknown`）で挙動は分けない（message はサーバーが日本語で返す）。
- 専用のリトライ導線は設けない。操作は冪等（02 確定）のため、ボタンを再押下すれば安全に再実行できる。
- 多重押下は実行中フラグ（`QuizFlow` 側 `useTransition` の `isPending`。決定 4）でボタンを disabled にして防ぐ。フラグが `QuizFlow` 側にあるため、実行中にチェック OFF→ON でボタンが再マウントされても disabled は維持される。
- 実行中も各行の個別トグルは既存どおり操作可能のままとする。一括実行と個別トグルの操作が重なると表示とサーバー状態がずれ得る（一括側の失敗ロールバックが個別操作の表示を上書きする、個別 OFF の後に一括登録がサーバーへ着弾する、一括の先行反映で Map 値が変わった行のトグルが key 再マウントされ実行中の個別トグルの内部 state（pending 表示・disabled）が破棄される等）が、操作が重なった場合のみの稀な競合であり、ずれても行トグルの再操作（冪等な set）で正せるため許容する。

採用理由: 失敗 = 全体失敗（部分適用なし、02 確定）のため、表示も全件戻すのが実状態と一致する。リトライ導線・行トグルのロックを追加しない分だけ UI が単純になり、冪等性がその安全性を担保する。

却下した代替案:

- toast にリトライボタンを付ける案 — ボタンが画面に残っており再押下で足りる。履歴送信失敗のインラインバナー＋再送は「画面の主目的（結果の保存）の失敗」だから重い導線を出しているのであり、補助操作の失敗はより軽い toast + 再押下で釣り合う。
- 一括実行中に個別トグルも disabled にする案 — 競合ウィンドウは短く、全行のトグルを一時ロックする実装・体験コストに見合わない。
