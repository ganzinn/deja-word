# 02. UI・導線

状態: **確定**（2026-08-15）

## 前提（確定事項の再掲）

このトピックが依存する決定。覆す場合はハブ（README.md）と決定元の両方を更新すること。

- 対象は単語ビューの検索のみ。掲載箇所ビュー・関連語ピッカーはスコープ外（01 確定）。
- 発動条件は「有効な検索語（正規化後キーワードが空でない。空になる入力では導線を出さない）あり、かつ可視範囲（system＋自分）に検索語と完全一致する headword なし」。部分一致ヒットがあっても表示し、表示上の絞り込み（ブックマーク・ページング）には依存しない（01 確定）。
- 完全一致は「正規化後キーワード（ADR-0084）と headword の等値比較・大文字小文字を区別しない」。一意制約・重複警告（自分の単語のみ・大文字小文字を区別する完全一致）とのズレは許容済みの帰結（01 確定）。
- 検索仕様・登録フォーム項目・重複警告の照合仕様は変更しない。追加は導線と受け口（検索語プリフィル＋戻り先）のみ（01 確定）。
- プリフィル値の選定と、プリフィル値に対する重複警告の発火タイミング（初期チェックの要否）は 02 に委譲。プリフィル値選定の判断材料（アクセント付き入力時の副作用）は 01 決定 2 の「許容する帰結」を参照（01 確定）。
- 発動条件は一致方法に依存せず、「を含む」「で終わる」のブラウズ用途検索でもヒット多数のまま導線が出続ける（許容済み）。目立ちすぎない表示位置の工夫は 02 に委譲（01 確定）。

## 検討事項リスト

## 議論・決定

### 決定 1: 導線は件数行の直下に 1 箇所、＋アイコン付きの小さなテキストリンク

発動条件成立時のみ、検索結果の件数行（「「run」の検索結果: n 件」）の直下に「＋ 「{表示語}」を登録」のテキストリンクを表示する。ゼロ件・部分一致ヒットありのどちらも同じ位置とし、ゼロ件時の空状態（「該当する単語はありません」）の表示は変更しない。発動条件はページ・絞り込みに依存しないため、2 ページ目以降でも同様に表示される。リンク先は登録フォーム（`/words/new`）に検索語と戻り先コンテキストを渡す URL（パラメータ設計は 03）。表示形態は控えめなテキストリンク（大きなバナー・ボタンにしない）とし、ブラウズ用途の検索（01 の許容済み帰結）でも邪魔にならないようにする。01 が委譲した「目立ちすぎない工夫」へは、位置（件数行直下＝リスト最上部）ではなく形態（小さなテキストリンク）で控えめさを担保する整理で応える。

採用理由: ユーザー選択。ゼロ件・部分一致ありを 1 箇所・1 実装で賄え、件数行の直後という「探した結果を確認する視線」の位置に置ける。
却下した代替案:
- ゼロ件は空状態内ボタン＋部分一致ありは件数行直下 — 表示箇所が 2 つになり実装・文言の二重管理になる。ゼロ件時も件数行直下で視認性は足りる。
- リスト末尾（最終ページの下） — ページングがあると埋もれ、ゼロ件時の位置としても不自然。

### 決定 2: 表示語・プリフィル値は正規化後キーワードで統一する

導線に表示する語と、登録フォームの headword にプリフィルする値は、どちらも完全一致判定に用いた正規化後キーワード（ADR-0084 の `normalizeSearchKeyword` を通した値）とする。導線で見た語がそのままフォームに入る一貫性を保つ。正規化はアクセント記号の除去と trim のみで、大文字小文字は保持する（例: 「RUN」で検索すれば表示・プリフィルとも「RUN」。完全一致判定が大文字小文字を区別しないことと混同して小文字化しない）。

本決定は、ADR-0084 の「ユーザーには入力したままの文字列を見せる（正規化するのは DB へ渡す照合値のみ）」という方針に対し、正規化後キーワードを画面表示・プリフィルに用いる初の例外となる。実装 PR で ADR-0084 に例外を追記する（03 の変更対象一覧に含める）。

採用理由: 判定・表示・プリフィルを同じ値に揃えることで、01 が挙げた 2 つの副作用（判定値との乖離による重複、アクセント付き headword が新規登録されてアクセントなしキーワードで引けなくなる経路）がどちらも生じない。通常の英語入力では trim 済み入力値と同一であり、差が出るのはアクセント付き入力時のみ。

許容する帰結: 件数行の表示（「「{q}」の検索結果」）は従来どおり trim 済み入力値のままのため、アクセント付き入力時のみ件数行の語と導線の語が見た目上異なる（例: 「Café」の検索結果 ／ ＋「Cafe」を登録）。検索表示の変更はスコープ外（01）であり許容する。
却下した代替案: trim 済み入力値（URL の `q`）をそのまま使う — 入力した綴りを保てるが、アクセント付き入力時に判定値と乖離し、ADR-0084 が非対称正規化の根拠とした「見出し語にアクセント記号付きは存在しない」前提を崩す経路になる。プリフィルは編集可能な初期値にすぎず、アクセント付きで登録したい場合は手で直せる。

### 決定 3: 重複警告は既存の blur 発火のまま（初期表示時のチェックは追加しない）

プリフィルされた headword に対して、フォーム初期表示時の重複チェックは行わない。既存の blur 発火はそのまま残る。blur は値の編集有無に関わらず発火するため、プリフィル値のままでも headword からフォーカスが外れれば既存どおりチェックが 1 回走るが、発動条件により警告は通常表示されない。

採用理由: 発動条件が「可視範囲に大文字小文字を区別しない完全一致なし」を保証しており、区別する完全一致（重複警告・一意制約の照合）はその部分集合のため、プリフィル値のまま登録して重複になる通常経路が無い。まれな競合（導線表示後に別タブで同語を登録）や手打ち URL は、blur 時の既存チェック、または送信時に `duplicate` エラーとして headword フィールドへ表示される既存実装（`word-form.tsx` の `form.setError("headword", ...)`）で拾える。
却下した代替案: プリフィル時に初期チェックを 1 回発火する — 通常経路では警告が表示されることがなく、フォーム挙動の追加に見合う実益が無い。

### 決定 4: 登録完了後の遷移は既存のまま

登録フォームの送信成功後は、既存どおり登録した単語の詳細（`/words/{wordId}`）へ遷移する。検索一覧へ戻す等の変更はしない。

採用理由: 登録直後は内容確認が自然で、既存フォームの挙動を変えない（01 決定 3 のスコープ最小化と一貫）。
却下した代替案: 元の検索一覧へ戻す — 送信成功後の遷移先としては実益が薄い（戻っても完全一致が生まれて導線が消えた一覧が出るだけで、登録内容の確認に一手間増える）。

### 決定 5: 導線経由時の「戻る」は元の検索結果へ戻れるようにする

導線経由で登録フォームへ入った場合、ヘッダの「戻る」（登録せず離脱）で元の検索条件（`q` / `sort` / `match` / `bookmarked` / `page`）の一覧へ戻れるようにする。edit モードには戻り先を引き継ぐ `returnHref` の前例があり（create モードの戻り先は現状固定の `/words`）、これに倣う。送信成功後の遷移は決定 4 のとおり詳細へで変えない。受け渡しの具体設計（`returnHref` の create 対応か別の方式か・検証）は 03 で決める。

本決定により、登録フォームへ追加する受け口は「検索語プリフィル＋戻り先」となる（01 決定 3 はこの範囲へ改訂済み。照合仕様・フォーム項目は引き続き変更しない）。

採用理由: 本機能で初めて「検索文脈から登録フォームへ入る」経路が生まれる。戻ったときに検索条件が失われて全件一覧に着地すると、「登録をやめて検索に戻る」自然な往復が壊れる。戻り先の受け口はキャンセル経路のみの最小改修であり、スコープ最小化の範囲内と判断した。
却下した代替案: 既存のまま固定 `/words` へ戻す — 実装は最小だが、導線の起点である検索結果へ戻れず、検索のやり直しの手間が導線の価値を削る。
