# 03. アーキテクチャ

状態: **確定**（2026-08-15）

## 前提（確定事項の再掲）

このトピックが依存する決定。覆す場合はハブ（README.md）と決定元の両方を更新すること。

- 発動条件は「有効な検索語（正規化後キーワードが空でない）あり、かつ正規化後キーワードが headword 最大長（100 文字）以内、かつ可視範囲（system＋自分）に検索語と完全一致する headword なし」。表示上の絞り込み（ブックマーク・ページング）には依存しない（01 確定）。
- 完全一致は「正規化後キーワード（ADR-0084）と headword の等値比較・大文字小文字を区別しない」。照合規則は検索と一貫させる（01 確定）。
- 検索仕様そのもの（照合規則・一致方法・並び順・ページング）は変更しない（01 確定）。
- 導線は単語ビューの件数行直下に 1 箇所、発動条件成立時のみ表示。リンク先は登録フォーム（`/words/new`）に検索語と戻り先コンテキストを渡す URL で、パラメータ設計は 03 で決める。件数行（ResultCount）の表示は従来どおり trim 済み入力値のままで変更しない（02 確定）。
- 導線の表示語と登録フォームへのプリフィル値は正規化後キーワードで統一する。大文字小文字は保持（正規化はアクセント記号除去と trim のみ。小文字化しない）（02 確定）。
- この画面表示は ADR-0084「入力のまま見せる」方針の例外のため、実装 PR で ADR-0084 に例外を追記する（変更対象一覧に含める）（02 確定）。
- プリフィル値に対する初期表示時の重複チェックは追加しない（既存の blur 発火のまま）。登録完了後の遷移も既存のまま（02 確定）。
- 導線経由時の「戻る」は元の検索条件（`q` / `sort` / `match` / `bookmarked` / `page`）の一覧へ戻す。受け渡しの具体設計（`returnHref` の create 対応か別方式か・検証）は 03 で決める（02 確定）。

## 議論・決定

### 決定 1: 完全一致判定は `src/lib/words-list.ts` の新関数で行い、一覧取得と並列に実行する

サービス層 `src/lib/words-list.ts` に完全一致有無を返す関数 `hasExactHeadwordForUser(userId: string, keyword: string): Promise<boolean>` を追加する。引数 `keyword` は **`normalizeSearchKeyword` 適用済みの正規化後キーワード**（正規化は呼び出し側の責務。防御として空文字なら DB を見ずに `false` を返す）。実装は `ownerId: { in: scopedOwnerIds(userId) }` かつ `headword: { equals: keyword, mode: "insensitive" }` の存在チェックで、ブックマーク・ページングの条件は入力に持たない（01 の定義どおり絞り込み非依存）。

呼び出し側 `src/app/words/page.tsx` の `WordView`（RSC）は、`const keyword = normalizeSearchKeyword(q)` を 1 回だけ計算して以下に使い回す:

- **導線の表示条件**: `keyword` が空でない、かつ `keyword.length` が headword 最大長（`SHORT_TEXT_MAX_LENGTH` = 100）以内、かつ `!(await hasExactHeadwordForUser(userId, keyword))`。前 2 条件を満たすときのみ判定関数を呼び、`listWordsForUser` と `Promise.all` で並列に実行する。
- **導線の表示語**: 同じ `keyword`（02 決定 2。プリフィルも `/words/new` 側で同じ正規化から導出されるため 3 者が一致する）。

補足: `src/lib/words-duplicate.ts` は一意制約 `@@unique([ownerId, headword])` と挙動を揃えるため意図的に大文字小文字を区別する equals を使っている。本関数は目的が異なり（書き込みガードではなく検索の照合規則に合わせた表示判定。01 決定 2）、`mode: "insensitive"` を使う。この使い分けを新関数のコメントに残す。

採用理由: 検索キーワード正規化・`scopedOwnerIds` を既に扱う words-list に置くのが凝集度が高い。専用クエリなら 01 の「絞り込み・ページング非依存」定義をそのまま満たし、並列実行でレイテンシ増を打ち消せる（テスト結果ダイアログの並列化と同じ流儀）。
却下した代替案:
- `listWordsForUser` の戻り値に `hasExactMatch` を追加する — 一覧取得は `bookmarkedOnly` / `skip` / `take` を受けるため、絞り込み非依存の判定と関心が混ざる。既存の全呼び出し箇所（掲載箇所ビュー等）にも波及する。
- 取得済みの一覧結果から導出する — 1 ページ分（20 件）しか手元に無く、2 ページ目以降やブックマーク絞り込みで 01 の定義とずれる。

### 決定 2: 導線リンクは一覧コンテキストのみを渡し、プリフィル値と戻り先 URL はサーバ側で導出・再構築する

導線リンクは `/words/new?<一覧コンテキスト>` とする。一覧コンテキストは単語ビューの検索条件（`q` / `sort` / `match` / `bookmarked` / `page`）をそのまま渡す。`q` に入れる値は URL・件数行と同じ **trim 済み入力値**であり、導線の表示語（正規化後キーワード）とは別値になりうる（正規化後を載せると、アクセント付き入力時に戻り先 URL が元の一覧と別の検索になるため）。プリフィル専用のパラメータ（`headword=` 等）は設けず、生の戻り先 URL（`return=/words?...` のような値）も渡さない。

`/words/new`（`src/app/words/new/page.tsx`）側:

- searchParams を受ける口を追加する（現状 props 無し）。
- プリフィル: `q` に `normalizeSearchKeyword` を適用した値が `headwordSchema`（trim・1〜100 文字）の safeParse に通った場合のみ `defaultValues.headword` に設定する。通らなければプリフィルなし（従来どおり空）。導線の表示語・完全一致判定と同じ関数・同じ入力からの導出であり、発動条件の長さ上限（01 決定 2）により導線経由では常に検証を通るため、表示語・判定値・プリフィル値の 3 者は一致する。safeParse は手打ち URL 等への防御。
- 戻り先: 検索コンテキストの有無は「`q` の trim 後が非空か」で判別する（既存の `(params.q ?? "").trim()` 流儀。導線は検索語のある文脈でのみ生成されるため、`view` 等の判別子は追加しない）。`q` が非空なら `q` / `sort` / `match` / `bookmarked` / `page` をパースし、`buildWordsHref("word", ...)` で一覧 URL を再構築して `WordForm` の `returnHref` に渡す。`q` が無ければ `returnHref` を渡さない（従来どおり `/words`）。パースは `src/app/words/_lib/search-params.ts` の既存パーサを再利用し、不足分は同ファイルへ追加する（`page` の解釈は現在 `page.tsx` ローカルの `parsePage` のため、search-params.ts へ移設して両所から使う）。不正値は既存流儀どおりデフォルトへフォールバックする。
- `src/app/words/new/word-form.tsx`: create モードの `backHref` を `returnHref ?? "/words"` に変更する（現状は edit のみ `returnHref` を使用）。送信成功時の遷移は変更しない（`isEdit && returnHref` ガードのまま詳細へ）。

採用理由: 編集画面の既存流儀（コンテキストを受け、サーバ側で内部相対パスを組み立てる。生 URL を受け付けない）と同型で、オープンリダイレクトを構造的に排除できる（セキュリティ設計チェックリストの外部入力観点）。プリフィル値を `q` から導出することで、同じ情報を 2 パラメータで受けて食い違う余地を作らない。プリフィル値は既存の `headwordSchema` で検証し、未検証の外部入力がフォーム初期値に入らない。
却下した代替案:
- プリフィル値を専用パラメータ `headword=` で別途渡す — 一覧コンテキストの `q` と同じ情報の二重受け渡しになり、手打ち URL で食い違わせる余地が生まれる。
- 生の戻り先 URL を searchParams で渡す — 内部パス限定の検証を新設する必要があり、既存流儀（コンテキスト渡し＋再構築）から外れる。

### 決定 4: テスト戦略

- **integration**（`src/lib/words-list.integration.test.ts` に追加）: 完全一致判定関数を対象に、(a) 自分の単語に一致 → true、(b) system 単語に一致 → true、(c) 一致なし（部分一致のみ）→ false、(d) 大文字小文字差でも一致扱い、(e) 空文字を渡すと false を返す（実装契約としては DB を見ない防御ガード。テストで検証するのは戻り値のみ）、(f) 他ユーザーの単語は対象外、を検証する（ブックマーク・ページング非依存は関数がそれらを入力に持たないことで構造的に担保されるため、テストケースにはしない）。アクセント正規化は関数の入力前提（正規化は呼び出し側の責務）のため integration では扱わず、正規化関数自体の既存 unit テスト（`search-keyword.unit.test.ts`）と手動観点（アクセント付き入力）で担保する。
- **unit**: `search-params.unit.test.ts` に `parsePage` 移設分・ヘルパ追加分のケースを追加。`/words/new` のプリフィル導出（`q` → 正規化 → `headwordSchema` 検証）・returnHref 再構築を純関数に切り出せる場合は unit でカバーする。切り出した純関数の置き場は `src/app/words/_lib/`（一覧 URL・検索語と関心が同じため `search-params.ts` と同居させ、同ファイルの unit テスト前例に倣う）。
- **UI（.tsx）**: テスト runner の include は `.ts` のみのため自動テスト対象外。導線の表示分岐・プリフィル・戻る遷移は e2e-verify スキルの手動確認を実装チケットの完了条件に含める（確認観点: ゼロ件で表示・部分一致ありで表示・2 ページ目以降でも表示・完全一致ありで非表示・記号のみ等の正規化後空の検索語で非表示・101 文字以上の検索語で非表示・ブックマーク絞り込み中（完全一致が結果に出ない状態）でも非表示・アクセント付き入力で表示語とプリフィルが正規化後の値で一致・「戻る」の検索条件維持）。

採用理由: 発動条件のロジックは DB 照合そのものなので integration が本体。UI は既存規約上自動化できないため、手動確認の観点を完了条件として明文化する。
却下した代替案: `.test.tsx` の導入 — テスト設定の変更（include 拡張）が必要でスコープ外。

### 決定 5: docs/features/word-management.md の更新範囲

「単語一覧（単語ビュー）」節に、検索で見つからなかったときの登録導線（発動条件の概要・検索語がプリフィルされること・戻るで検索結果に戻れること）を追記する。「重複登録の警告」節は変更しない。スクリーンショットは、既存ショットの構図（検索語なしの一覧・登録フォーム）に導線が写らなければ再撮影不要とし、導線が表示された検索状態のショットを 1 枚追加する（`pnpm e2e:capture-docs --only words` で再生成。ショット追加はスクリプトの words セクションに定義を足す）。

採用理由: ユーザー向け機能の追加は同一 PR で機能紹介を更新する規約（AGENTS.md）。導線は検索体験の説明に属するため単語ビュー節が適切。
却下した代替案: 「単語の登録」節への追記 — 導線の起点は検索であり、登録フォーム自体の仕様（プリフィル以外）は変わらないため、検索側の節で説明するほうが読者の動線に合う。
