# 03. プリフェッチ（待ち時間短縮）

状態: **確定**（2026-08-06）

## 前提（確定事項の再掲）

このトピックが依存する決定。覆す場合はハブ（README.md）と決定元の両方を更新すること。

- 遷移中フィードバックは「前の単語を残した淡色化＋到着時の方向スライド」。淡色化はフェード開始のため、プリフェッチが命中して待ちが無い場合は実質見えず、スライドのみが知覚される（01 確定）。
- 遷移中の多重操作はブロックせず最後勝ち（連続送りで先読みを追い越すケースの検討が必要）（01 確定）。
- ページの前後ナビは遷移経路を `startTransition` + `router.push` に単一化。ボタンの `<Link>` はビューポート prefetch と anchor semantics のために維持し、`onNavigate` で intercept する。フリックは `<Link>` を経由しない（02 確定）。
- スライドは自前 CSS（tw-animate-css + key 差し替え）で実装し、`experimental.viewTransition` は有効化しない（02 確定）。
- ダイアログは最後の ready 応答を保持して淡色化表示。データ取得は Server Action + 応答鮮度の key 照合（最後勝ち）の現行構造を維持（02 確定）。

## 議論・決定

### 決定 1: ページ側は前後ボタンの `<Link>` に `prefetch={true}` を指定してフルプリフェッチする

`AdjacentWordNav`（`src/app/words/[id]/_components/adjacent-word-nav.tsx`）の前後 `<Link>` に `prefetch={true}` を付ける。手動の `router.prefetch` 呼び出しは書かない。

採用理由:

- `/words/[id]` は dynamic ルートで `loading.tsx` が無いため、デフォルト（`prefetch` 未指定 = auto）では**プリフェッチが一切行われない**（Next 16.2.9 同梱 docs `01-app/01-getting-started/04-linking-and-navigating.md`: dynamic ルートは "prefetching is skipped, or the route is partially prefetched if `loading.tsx` is present"）。本番でボタン遷移が Neon 往復をまるごと待つのはこれが原因。ADR-0085 影響節の「`<Link>` が prefetch 済み」という記述は誤りだった。
- `prefetch={true}` は dynamic ルートでもフルルートをプリフェッチし、クライアントルーターキャッシュに static 扱い（既定 5 分）で保持される（同梱 docs `staleTimes.md`）。stale 期間内の遷移はサーバー往復なしで即時表示になる。
- 前後ナビは常時ビューポート内にあるため、ページ表示直後に前後分のプリフェッチが自動発火する。発火専用のコードが不要。
- フリック（`router.push(prevHref/nextHref)`）はボタンの `<Link href>` と**同一の href 文字列**（`buildWordDetailHref` の出力）を使うため、キャッシュキー（URL）が一致し、`<Link>` 経由でなくてもプリフェッチ結果で遷移できる。

負荷の受容: プリフェッチ 1 件 = ページ表示 1 回分のサーバー処理（Function 起動・セッション確認・ページ内の全 Neon クエリ・RSC シリアライズ）であり、SQL だけが走るのではない。倍率は閲覧パターンで変わる:

- 単語を 1 つ見て離脱する場合: 表示 1 ＋捨てられる前後 2 で **×3**（最悪ケース）。
- 連続で読み進める場合: 移動先はプリフェッチ済みで遷移自体のリクエストは 0、到着後の先読みも「来た方向」はキャッシュ済みのため新規は 1 件のみ。**1 ステップあたり約 1 レンダリングで現状と同等**（取得タイミングが操作後から操作前に前倒しされるだけ）。

主用途は掲載順に読み進める使い方（ADR-0085 の背景）のため実効の増分は小さい。Next 16 の incremental prefetching（layout 重複排除）で転送量も抑えられる。待ち時間短縮の対価として許容する。

戻しやすさ: プリフェッチをやめたくなった場合は `prefetch={true}` を 2 箇所削除するだけで済む（スキーマ・URL・データに触れない付加機能であり、外しても遷移・フィードバックの挙動は変わらず、遅くなるだけ）。

注意: `<Link>` の自動プリフェッチは **production ビルドのみ**で動作する（同梱 docs `link.md`: "Prefetching is only enabled in production"）。dev で効かないのは仕様であり、効果確認は `pnpm build && pnpm start` で行う（決定 5）。

却下した代替案:

- `router.prefetch` を `useEffect` で手動呼び出し — `<Link>` の宣言だけで足りる。二重管理になり、stale 時の再プリフェッチ（hover 時の再取得等）を自前で面倒見ることになる。`<Link>` を持たないフリック経路も同一 href でキャッシュを共有できるため不要。
- `loading.tsx` を追加して部分プリフェッチ — 遷移時に loading fallback がコンテンツを**置き換える**ため、「前の単語を残して淡色化」（01 確定）と衝突する。かつ shell だけでは本文の待ちは解消しない。
- `experimental.staleTimes` の調整 — 既定値（static 5 分）で要件を満たす。experimental 設定を増やさない。
- intent 発火（hover / touchstart で初めてプリフェッチ）— 主対象のモバイルでは操作意図の検知から遷移までの間隔が短すぎ、待ち時間短縮にならない。

### 決定 2: プリフェッチ範囲は前後 1 件・連続送りの追い越しは許容する

ページ・ダイアログとも、先読みするのは現在の単語の前後 1 件のみ。連続送りで未プリフェッチの単語に到達した場合は通常の待ち（淡色化フィードバックが可視化される）とする。

採用理由: 到着のたびに次の前後分のプリフェッチが走るため、読むペースの連続送りなら深さ 1 でもほぼ追いつく。深さ 2 以上は隣接計算（`findAdjacentWordsByOccurrence` / `findAdjacentWordsByOccurrenceNumber`）の拡張とキャッシュ管理の複雑化が必要で、追い越し時も多重操作は最後勝ち（01 確定）で操作が失われない以上、見合わない。

却下した代替案: 深さ 2 の先読み（隣接取得の拡張が必要・負荷倍増）、一覧全件の先読み（負荷が非現実的）。

### 決定 3: 単語データを変更する Server Action に `revalidatePath` を追加する（`toggleBookmark` は除外）

対象: `updateWord`・音源のアップロード/削除系（`src/app/words/[id]/edit/actions.ts`）、`deleteWord`（`src/app/words/[id]/actions.ts`）、`createWord`（`src/app/words/new/actions.ts`）。成功時に該当単語の詳細パス（`/words/<id>`）へ `revalidatePath` を呼ぶ。

採用理由: Server Action からの `revalidatePath` はクライアントルーターキャッシュ**全体**を即時クリアする（同梱 docs `cacheLife.md`）。これが無いと「単語を編集 → 詳細へ戻る」時に、編集前にプリフェッチされた最大 5 分 stale のページ本文が表示され得る。現状は dynamic ページが一切クライアントキャッシュされないため顕在化していないだけで、`prefetch={true}` 導入（決定 1）の前提整備として必要。編集・削除は低頻度のため、キャッシュ全クリア → 再プリフェッチの負荷は問題にならない。

`toggleBookmark` を除外する理由: 楽観的更新の現行方針（`src/app/words/actions.ts` 冒頭コメント「楽観的更新の方針のため `revalidatePath` は呼ばない」）を維持する。トグルは高頻度で、そのたびに全キャッシュクリア → 再プリフェッチが走るとプリフェッチが実質無効化される。副作用として、プリフェッチ済みペイロード由来のブックマーク初期表示が最大 5 分古いことがあり得るが、アイコン 1 個の表示のみで、次のフレッシュ取得で自己修復するため許容する。

補足: この決定はプリフェッチを将来やめた場合でも**戻す必要がない**。あって害がなく、本来あるべきデータ整合の処理である（現状は dynamic ページがクライアントキャッシュされないため、偶然問題が顕在化していないだけ）。

却下した代替案: 全 mutation で `revalidatePath`（ブックマークの高頻度トグルでプリフェッチが無効化され本末転倒）、何も追加しない（編集後の stale がデータ本文に及ぶため許容できない）。

### 決定 4: ダイアログは詳細＋隣接ナビを前後 1 件先読みし、開いている間の Map キャッシュに保持する

- キャッシュ: `WordDetailDialog` 内の `useRef` に Map を 2 本持つ（`wordId → 詳細応答（word + bookmarked）`、`` `${occurrenceId}:${wordId}` → 隣接応答 ``）。コンポーネントは常時マウントのため、**ダイアログが閉じたとき（`wordId` が null になったとき）に明示的に破棄**する。エントリ数の上限は設けない（1 エントリは単語 1 件分で、閉じれば消える）。
- 先読みの発火: 表示中単語の詳細・隣接の**両方**が ready かつ現在キーに一致（= settled）したとき、隣接応答の `prev` / `next` について未キャッシュ分の `getWordDetailForDialog` と `getAdjacentWordsForDialog` を呼び、応答をキャッシュへ入れる。連続送り中は中間単語が settle しないため、無駄な先読みは自然に抑制される。
- **先読み応答は表示 state に直接触れず、キャッシュにのみ書く**。表示への反映は単語切替時のキャッシュ参照経由に限られるため、鮮度照合（最後勝ち、02 確定）と干渉しない。
- 表示: 単語切替時にキャッシュヒットなら即 ready（淡色化は実質見えず、スライドのみ）。ミス時は現行どおり前の単語を淡色化して応答を待つ。隣接のみミスした場合は前後ボタンが応答まで disabled になるだけで、本文表示は妨げない。
- ブックマーク整合: ダイアログ内でトグルしたら、既存の `onBookmarkChange` 通知に加えて**キャッシュ該当エントリの `bookmarked` も更新**する。ダイアログはモーダルで、表示中に一覧側のトグルは発生しないため、これで整合が保たれる。
- 関連語をたどった先（スタック深さ 2 以上）は前後ナビ非表示（`occurrenceId` null）のため先読みしない。詳細キャッシュのヒットは通常どおり効く（例: 深い階層から前後移動でルートへ戻るときは即表示）。

採用理由: ダイアログの遷移は `getWordDetailForUser` を含む重い Server Action 往復そのものが待ち時間であり、先読み＋キャッシュで「進んで戻る」「先読み済みへ進む」の両方が即時になる。キャッシュ寿命をダイアログ表示中に限定することで、単語データの鮮度管理（編集との整合）を考えなくてよい（quiz フロー中に単語編集は起き得ない。別タブ編集は許容範囲の edge）。

戻しやすさ: 先読みをやめたくなった場合は settled 時の先読み発火（純関数＋呼び出し 1 箇所）を消すだけでよい。キャッシュ（Map 2 本）は残してよく（先読みなしでも「戻る」移動が即時になる利得が残る）、消す場合も ref と参照箇所の削除で完結する。表示 state・鮮度照合とは独立に隔離されているため、外しても遷移の挙動は変わらない。

却下した代替案:

- 詳細＋隣接を 1 つの Server Action に統合して往復を半減 — キャッシュヒット時は往復ゼロになるため統合の利得が小さく、02 で確定した現行構造（2 action + key 照合）を変えるリスクに見合わない。
- キャッシュを親（QuizFlow）や localStorage に持つ — 寿命管理・鮮度管理が複雑化する。ダイアログセッション内で目的を達せる。
- 先読み応答を表示 state に直接流す — 最後勝ちの鮮度照合と競合する。キャッシュ経由に一本化する方が単純。

### 決定 5: テスト戦略の追補

- ダイアログ: 先読み対象の決定（settled 判定・未キャッシュ判定 → 発行すべき取得のリスト）とキャッシュ参照込みの表示 state 導出を純関数に切り出し、unit テストする（02 の「表示 state 導出を純関数 unit」の延長）。
- ページ: プリフェッチは production のみのため **E2E では検証しない**。プリフェッチはあくまで高速化で、無くても遷移・フィードバックの挙動は同一のため、既存・新規 E2E を prefetch に依存させない。効果確認は `pnpm build && pnpm start` で network タブを目視する。
- `revalidatePath` 追加により、対象 action の既存 unit テストで `next/cache` のモックが必要になり得る（実装時に確認）。

採用理由: アニメーション・プリフェッチとも「無くても機能する」付加要素であり、自動テストは決定的に検証できる純関数と DOM 属性（02 確定）に限定する方針を維持する。

却下した代替案: production ビルドを起動する E2E でプリフェッチの network を検証 — ハーネスが複雑化する割に、Next.js 本体の挙動（docs 記載）を再検証するだけになる。
