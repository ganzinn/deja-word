# 01. プリフェッチ廃止方式

状態: **確定**（2026-08-07）

## 前提（確定事項の再掲）

このトピックが依存する決定。覆す場合はハブ（README.md）と決定元の両方を更新すること。

- 前後ナビの遷移中フィードバック（淡色化＋方向スライド）と遷移経路の単一化（`startTransition` + `router.push`、`<Link>` は intercept）は維持する（ADR-0086 決定 1・2。issue #229 の対応意向）。ただし決定 2 が `<Link>` 維持の根拠とする「prefetch と anchor semantics のため」のうち prefetch 側は本トピックで失効する（決定 1・4 で扱う）。
- フリックの判定条件（閾値・エッジ除外・window リスナ）は変更しない（ADR-0085。issue #229 関連節）。
- 詳細ページの隣接（prev / next）は一覧と同じ where を共有する隣接クエリで取得される（ADR-0089 決定 3・4。集合外なら隣接 null でナビ非表示は決定 5。`findAdjacentWordsByOccurrence` / `findAdjacentWordsInWordView`）。詳細ページは dynamic ルートのため、この隣接クエリはリクエスト毎に評価される。プリフェッチ廃止後に「常に最新の一覧順で隣接移動できる」のはこの前提による。

## 検討事項リスト

- [x] `prefetch={true}` の外し方: プロパティ削除（デフォルト挙動に戻す）か `prefetch={false}` の明示か（issue の ADR 判断事項）→ 決定 1

- [x] 廃止で解消される問題の範囲整理: 別端末削除の stale 表示（最大 5 分）・stale ナビ経由の 404 到達窓のうち、何が消え何が残るか（描画〜タップ間の競合は原理的に残る）→ 決定 2
- [x] issue #200（操作が効いたか分からない）の再発防止が遷移中フィードバックのみで成立することの整理 → 決定 3

## 議論・決定

### 決定 1: `prefetch={false}` を明示して先読みを全廃する

`adjacent-word-nav.tsx` の前後 2 つの `<Link>` の `prefetch={true}` を `prefetch={false}` に変更する。`router.prefetch` の手動呼び出しは元々存在しない（ADR-0086 決定 3 で不採用）ため、これで**前後ナビ**の先読みは全廃となる。`<Link>` 自体（anchor semantics と `onNavigate` intercept）は維持する。なお詳細ページの他の `<Link>`（戻る・編集・関連語リンク）は prefetch 未指定（デフォルト `auto`）のままとし、現状（dynamic ルート＋`loading.tsx` 無し）では先読みされない。将来 loading 境界を追加する場合はこれらの部分プリフェッチ再開も再確認する。

採用理由: `prefetch={false}` は「viewport 進入・hover のいずれでも一切プリフェッチしない」ことが Next.js 同梱 docs（16.2.9 `link.md`）で保証され、周辺条件に依存しない。プロパティ削除（デフォルト `auto`）でも現状は同挙動だが、それは「dynamic ルートかつ `loading.tsx` が無いため部分プリフェッチ対象が無い」ことによる暗黙のスキップであり、将来 loading 境界を追加すると挙動が変わる。プリフェッチの有無はこの機能の明示的な設計判断（鮮度・リソースコスト）なので、コード上でも明示する。

却下した代替案:

- **プロパティ削除（デフォルト `auto` に戻す）** — 現状は結果的に同挙動だが無効化が暗黙になる。prefetch 挙動の暗黙依存は ADR-0085 影響節の誤記（「prefetch 済み」と誤認）を生んだ経緯があり、明示に倒す。

### 決定 2: 廃止で解消される問題と残る挙動の線引き

解消されるもの:

- 別端末で削除された単語の詳細が閲覧中端末で最大約 5 分表示され続ける挙動（`prefetch={true}` によるルーターキャッシュ static 5 分保持が消滅する）
- 隣接ページの古いスナップショットに残った削除済み単語へのナビリンク経由の 404 到達窓（プリフェッチキャッシュ由来のもの）
- 詳細 1 表示につき前後 2 ページ分の追加サーバーレンダリング（Neon クエリ含む）のリソースコスト

残るもの（許容）:

- 表示中ページのナビリンクはレンダリング時点の隣接計算のため、描画〜タップ間に別端末で削除されると 404 に到達しうる（issue #229 で対象外と明示済み）
- ブラウザ履歴の back/forward キャッシュは `staleTimes` の対象外のため従来どおり残る（レイアウトシフト・スクロール位置保持のための仕様）。ブラウザバック / OS の戻るジェスチャで一覧・詳細に戻った場合はキャッシュ復元となるため、別のタブ・端末（別のルーターインスタンス）で削除済みの単語がその画面に残って見え、そこからのタップで 404 に到達しうる（リアルタイム反映は issue #229 の対象外であり許容。リンク遷移で開き直せば解消する）
- 共有レイアウトセグメント（`src/app/layout.tsx`）は partial rendering によりナビゲーション毎には再取得されない（同梱 docs `staleTimes.md`）。ただしレイアウトに載るデータ取得は `SiteHeader` のセッション参照のみで単語データ・隣接ナビを含まないため、本トピックの鮮度問題には無関係

採用理由: `staleTimes` の既定は dynamic 0 秒（フルプリフェッチでないページはルーターキャッシュで再利用されない。同梱 docs `staleTimes.md`）。よって `prefetch={false}` にするだけで、**クライアント遷移（前後ナビの `router.push`・戻る / 詳細リンク等の `<Link>` クリック。ブラウザ back/forward の履歴復元を除く）による**前後移動・一覧との往復は毎回サーバー取得となり、隣接が一覧と同じ where で毎リクエスト計算される前提（前提節参照。ADR-0089 決定 3・4 の where 共有＋dynamic ルート）と合わせて「一覧に戻れば常に見えている順番で隣接移動できる」（issue #229 の対応意向）が追加実装なしで成立する。

却下した代替案:

- **`staleTimes` の明示設定や `router.refresh` の追加** — 既定値（dynamic 0 秒）で目的が達成されるため不要。設定を足すと experimental フラグへの依存が増えるだけ。

### 決定 3: 遷移待ちの体感は遷移中フィードバックが単独で担う

ADR-0086 決定 1（淡色化＋方向スライド）・決定 2（`startTransition` + `router.push` への遷移経路単一化、`<Link>` intercept）は変更しない。廃止後は前後移動が毎回サーバー往復になり淡色化がほぼ常に知覚されるようになるが、「操作を受け付けた」ことはフィードバックが示すため、issue #200（操作が効いたか分からず同じ操作を繰り返す）はフィードバック側で再発を防ぐ整理とする。フリックの判定条件（ADR-0085）も変更しない。

採用理由: issue #200 の本質は「無応答に見える待ち時間」であり、待ち時間そのものの短縮（プリフェッチ）は対策の一つに過ぎない。フィードバックで応答を即時に見せる対策が既に入っており、鮮度・コストを犠牲にする短縮策を重ねる必要がない。

却下した代替案:

- **`loading.tsx` 追加による部分プリフェッチで体感を補う** — loading fallback がコンテンツを置き換え「前の単語を残して淡色化」と衝突する（ADR-0086 却下案の再確認）。

### 決定 4: ADR 起票の骨子（ADR-0086 決定 3 の部分置き換え）

新 ADR を 1 本起票し、以下の構成とする:

- ADR-0086 決定 3 のうち**ページ側 `prefetch={true}` を置き換える**（本トピック決定 1〜3 の内容）。ADR-0086 決定 1・2（遷移中フィードバック・遷移経路）は維持と明記する。ただし決定 2 の「`<Link>` は prefetch と anchor semantics のために維持」のうち prefetch 側の根拠は失効するため、新 ADR に「`<Link>` 維持の根拠は anchor semantics と `onNavigate` intercept のみになる」と明記する
- テスト結果ダイアログ側の詳細先読み（現行仕様は ADR-0088 決定 6。ADR-0086 決定 3 のうちダイアログの隣接ナビ先読みは同決定で既に廃止済み）は**対象外・維持**（issue #229 の対象外節。変更する場合は別 issue）
- ADR-0086 決定 4（`revalidatePath` 群）の扱いはトピック 02 の結論を新 ADR に含める（02 決定 1 で「維持理由の再定義 = 決定 4 の置き換え」と確定したため、ADR-0086 決定 4 にも改訂注記を入れる）
- ADR-0086 側への改訂注記は、決定 3（ページ側は新 ADR で置き換え）に加えて、**決定 2 の「prefetch と」の句**と**影響節の 3 項目**（プリフェッチ命中時はほぼ即時 / 前後 2 ページ分の追加レンダリング / 編集のたびに再プリフェッチ）にも入れる（影響節のうち「自動プリフェッチは production のみ」の項目は、記述自体が無効にならないため対象外）
- ADR-0085 影響節の「同じ href の `<Link>` が prefetch 済みのため、ボタン押下と同じ速さで表示される」は本置き換えで最終的に無効となる旨を新 ADR に 1 行記す（ADR-0086 が「訂正する」とした記述。prefetch 全廃後は速度差の前提自体が消える）
- `docs/adr/README.md` のテーマ一覧に新 ADR の行を追加する（タイトル列に「0086 決定 3 のページ側プリフェッチを置き換え」と置き換え関係を含める。索引本文中は `ADR-` 接頭辞なしの ADR-0088 の索引行の形式に倣う）。加えて ADR-0086 の行のタイトル列にも「ページ側プリフェッチは新 ADR で廃止」を併記する（ADR-0088 の際は置き換え元の行に注記していないが、今回は影響節まで無効になる部分置き換えのため追跡性を優先して入れる）
- 実装時に `adjacent-word-nav.tsx` の prefetch コメント（「前後 1 件はフルルートを先読みする」）を新方針の説明に書き換える

採用理由: プリフェッチ導入（ADR-0086）と廃止で判断が反転するため、経緯の追跡には独立した ADR が必要。ADR-0088 決定 6 が同様の部分改訂（ダイアログ側先読みの置き換え）を注記方式で行っており、形式を揃える。

却下した代替案:

- **ADR-0086 を直接書き換える** — ADR は不変の決定記録であり、置き換えは新 ADR ＋改訂注記で表すのが本リポジトリの運用（ADR-0088 決定 6 の前例）。
