状態: **確定**（2026-08-07）

## 前提（確定事項の再掲）

このトピックが依存する決定。覆す場合はハブ（README.md）と決定元の両方を更新すること。

- 前後ナビの `<Link>` は `prefetch={false}` の明示で前後ナビの先読みを全廃する（ダイアログ側・詳細ページの他リンクは対象外）。`<Link>` intercept・遷移中フィードバック（ADR-0086 決定 1・2）は維持する（01 確定）。
- `staleTimes` 既定（dynamic 0 秒）により、フルプリフェッチ廃止後はクライアント遷移（前後ナビの `router.push`・戻る / 詳細リンク等の `<Link>` クリック。ブラウザ back/forward の履歴復元を除く）の前後移動・一覧との往復が毎回サーバー取得になる。ルーターキャッシュに残るのは (a) back/forward キャッシュ復元（`staleTimes` の対象外。削除済み単語の stale 表示・404 到達窓が残るが許容）と (b) 共有レイアウトセグメント（partial rendering。レイアウトに載るデータ取得は `SiteHeader` のセッション参照のみで単語データ・隣接ナビを含まず、鮮度問題には無関係）（01 確定）。
- 新 ADR に `revalidatePath` 群（ADR-0086 決定 4）の扱い（本トピックの結論）を含める（01 確定）。

## 議論・決定

### 決定 1: `revalidatePath` 群（5 箇所）はすべて維持し、新 ADR で維持理由を再定義する

`words/new/actions.ts`（createWord）・`words/[id]/actions.ts`（deleteWord）・`words/[id]/edit/actions.ts`（updateWord・音源アップロード/削除系）の計 5 箇所の `revalidatePath` は削除しない。呼び出しと、それを固定している unit テスト 3 ファイルは変更なし。ただし各呼び出しに付く説明コメント 3 件（「プリフェッチ済みのルーターキャッシュを無効化する」等）は導入理由の失効に伴い虚偽になるため、下記の維持理由に書き換える（createWord の 1 件には「効果は現行の全パージ挙動（暫定）に依存する」旨を併記する。下記注意参照）。新 ADR で ADR-0086 決定 4 を置き換え、あわせて ADR-0086 決定 4 にも改訂注記を入れる（注記全体の構成は 01 決定 4）。再定義する維持理由: **変更（作成・編集・削除・音源変更）を実行した同一タブ（同一ルーターインスタンス）で、back/forward 履歴復元により変更前の内容が出るのを防ぐ**。

採用理由: Server Action からの `revalidatePath` は現行 Next（16.2.9）では「過去に訪問した全ページを、次回ナビゲーション時に再取得させる」（同梱 docs `revalidatePath.md`。クライアントキャッシュの全パージ）。ページは既定でルーターキャッシュに残らないが back/forward では再利用される（同梱 docs `04-glossary.md`）ため、プリフェッチ廃止後もこの呼び出しには「変更した同一タブの back/forward 復元を stale にしない」機能が残っており、dead code ではない。パージが届くのは Server Action を呼んだタブのルーターキャッシュだけで（サーバーは他クライアントの in-memory キャッシュに触れられない）、他タブ・他端末の変更による stale は 01 決定 2 の許容範囲に属する。同一タブでの変更直後の stale（編集したのに古い内容が出る・作成したのに一覧に無い・削除したのに残って見える）は「自分の操作が失われたように見える」点で質が異なり、許容に含めない。

注意（新 ADR にも記載する）: 全パージは docs 上「暫定挙動（将来は指定パスのみに狭める）」と明記されている。5 箇所が渡すパスはいずれも `/words/<id>`（詳細）で `/words`（一覧）を渡す呼び出しは無いため、挙動が狭められた場合に確実に残るのは「変更した単語自身の詳細ページ」の効果のみで、一覧・他ページへの波及効果（作成後に back/forward で一覧へ戻ったとき新単語が見える等）は失われる。特に createWord が渡すのは作成直後の新規 ID の詳細パスで、そのページはどのルーターキャッシュにも存在し得ないため、狭められた時点で createWord の呼び出しは効果が残らない。その時点で `/words` の revalidate 追加（createWord は追加または削除）を再検討する。

却下した代替案:

- **全削除（back/forward 復元の stale は他タブ・他端末の変更で許容済みなのだから同一タブも同様に許容する）** — 上記のとおり同一タブの変更直後の stale は操作の成否を疑わせる。削除で得られるのは 5 行＋テストアサーションの削減のみで釣り合わない。
- **一部削除（createWord のみ削除等）** — 現行挙動では createWord の呼び出しにも「作成後に back/forward で一覧へ戻ったとき新単語が見える」効果が残っている（暫定の全パージ挙動に依存する点は上記注意のとおり）。現行の暫定挙動の下では 5 箇所とも機能が残っており、切り分ける根拠がない。

### 決定 2: `toggleBookmark` は現行方針のまま変更しない

楽観的更新・`revalidatePath` を呼ばない方針（ADR-0086 決定 4、`src/app/words/actions.ts` 冒頭コメント）は本変更の影響を受けず、変更しない。プリフェッチ廃止によりブックマーク初期表示の stale 窓（従来「最大 5 分」）はむしろ縮む: リンク遷移では毎回サーバー取得となり、残るのは back/forward 復元経由のみ（表示中は楽観的更新の表示が正であり、開き直せば解消）。新 ADR で「最大 5 分の stale は許容」の記述をこの内容に更新する。

採用理由: 変更が不要である上、挙動は改善方向にしか動かない。

却下した代替案: なし（対立する案が成立しない）。

### 決定 3: 体感確認は dev ＋ CDP throttling で行い、それが本番の体感を代表する

実装チケットの完了条件として、skill e2e-verify の過渡状態観測レシピ（playwright-core + system Chrome、CDP throttling 目安 600ms で本番相当の遅延を再現し、ポーリングではなく MutationObserver で `data-*` 属性の遷移列を記録する）で次を確認する:

1. ボタン押下・フリックのそれぞれで、操作直後から到着まで pending 状態（`data-pending`）が継続して観測できる（淡色化 =「操作を受け付けた」の表示。目視は補助）
2. 到着時の `data-direction` が操作方向と一致し、方向スライドで差し替わる
3. 遷移中に連打しても最終的な表示 URL が最後の操作の意図と一致する（issue #200（操作が効いたか分からず繰り返す）の再発なし）

採用理由: `<Link>` の自動プリフェッチは production のみ有効だったため、従来はプリフェッチ命中時の挙動を本番でしか確認できなかった。廃止後は dev と production の遷移経路が一致する（どちらも毎回サーバー取得）ため、dev ＋ throttling の確認がそのまま本番の体感を代表する。

却下した代替案:

- **本番デプロイ後の実機確認のみで済ませる** — 実装 PR の段階で確認できる手段があるのに後回しにする理由がない（本番での最終確認を妨げるものではない）。

### 決定 4: 削除反映の E2E 確認シナリオ（恒久テストは追加しない）

実装チケットの完了条件として、skill e2e-verify で次のシナリオを 1 本実施する:

1. 一般ユーザー（既定の使い回し test1@example.com）で headword を `e2e-nav-a`〜`e2e-nav-d` とした単語 4 件を用意し、**見出し順（`sort=headword`。並び順トグルのボタン文言は「見出し順」）の一覧**で a→b→c→d と並ぶことを前提にする（既定の新着順は作成順の逆で並ぶため、順序を一意にする目的で見出し順を使う）
2. コンテキスト 1 で見出し順の一覧を開き、検索欄で `e2e-nav` に絞り込んでから `e2e-nav-b` の詳細を開く（単語ビューコンテキスト。以降のナビ・戻りリンクには `sort=headword` と `q=e2e-nav` が引き継がれる。使い回しユーザーは他の単語を持ちうるため、絞り込みなしでは 1 ページ 20 件の一覧で対象が 1 ページ目に載らず確認が空振りしうる）
3. **同一ユーザー（test1）**で 2 つ目の context を `newContext` + `login` で開き（cookie jar もルーターキャッシュも別 = 別端末相当。skill e2e-verify の「1 ユーザー 1 context」規約は別ユーザー混入防止のためのもので、本件は意図的な同一ユーザー 2 端末の再現。単語は owner スコープのため別ユーザーでは `e2e-nav-c` を開けず削除できない）、`e2e-nav-c` を削除する
4. コンテキスト 1 で詳細ヘッダの戻るリンク（`ScreenHeader`、`aria-label="戻る"`）から一覧（絞り込みは維持される。href は `/words?q=e2e-nav&sort=headword` だが、`buildWordsHref` の組み立て順とツールバー操作で到達した URL の順は異なりうるため、クエリは文字列一致でなく個別に検査する）へ戻り、`e2e-nav-a` / `e2e-nav-b` / `e2e-nav-d` が見えていること・`e2e-nav-c` が無いことを確認する
5. `e2e-nav-b` を開き直し、「次へ」の href が `e2e-nav-d` を指すこと・「次へ」で遷移して `e2e-nav-d` の詳細が表示される（404 にならない）ことを確認する

運用は e2e-verify の規約に従う: 実施後に `cleanupWordsByPrefix("e2e-nav-")` で後始末し、検証スクリプトは一回きりの確認として確認後に削除する（`package.json` には追加しない）。対象経路はリンク遷移のみ（ブラウザバック復元経由の stale 表示は 01 決定 2 で許容済みのため対象外）。恒久の自動テストは追加しない。

位置づけ: このシナリオは**変更後の期待挙動のスモーク確認**であり、変更前コードとの差分の判別は目的にしない（この経路は変更前でもプリフェッチ対象外のため同じ結果になる。プリフェッチが飛ばなくなったこと自体は `prefetch={false}` のコードレビューと、dev / production の遷移経路が一致する整理 = 決定 3 採用理由で担保する）。

採用理由: リポジトリのテスト基盤は Vitest の unit / integration（include は `.ts` のみ）で、ブラウザ E2E の恒久基盤は無く、ADR-0086 でも E2E は DOM 確認のみの位置づけ。一度の回帰確認で足りる検証を恒久化する投資は見合わない。

却下した代替案:

- **Playwright の恒久 E2E テストを新設する** — この変更 1 件のために新しいテスト基盤（CI 実行環境・DB seed 分離）を導入することになり、スコープ肥大。必要になったら別 issue で扱う。

### 決定 5: `docs/features/word-management.md` の前後ナビ説明を同一 PR で更新する

前後ナビ節の「（前後の単語はあらかじめ読み込むため、多くの場合は待ちを感じずに切り替わります）」（現 102 行目付近）を、先読みを前提としない説明（例: 「移動のたびに最新の内容を読み込むため、切り替わるまで淡色表示のまま待ちます」）に書き換える。画面自体は変わらないためスクリーンショットの再撮影は不要。実装と同一 PR で行う（AGENTS.md の機能紹介ドキュメント更新規約）。

採用理由: ユーザー向け挙動の説明が「あらかじめ読み込む」と明記されており、廃止後は虚偽になる。文言変更のみで画面変化は無いため、本文更新だけで足りる。

却下した代替案: なし（規約上必須の作業で、対立する案が成立しない）。
