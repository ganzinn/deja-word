# 03. 出題・選択肢生成アルゴリズム

状態: **確定**（2026-06-12）

## 前提（確定事項の再掲）

このトピックが依存する決定。覆す場合はハブ（README.md）と決定元の両方を更新すること。

- 機能名は quiz。
- 任意起動の腕試し型。出題対象は Occurrence＋掲載番号の範囲指定で決まり、範囲内の単語を全て出題する。アルゴリズムによる取捨選択はしない（01 確定。意味未登録の単語の除外のみ本トピックで例外として追加）。
- 復習期限ベース（SRS）・復習間隔の管理は MVP スコープ外（01 確定。将来拡張）。
- 出題順序はランダム（毎回シャッフル）（01 確定）。
- 出題形式は英→日の3形式: 四択＋「わからない」 / 自己判定 / 多義語選択（選択肢数ランダム）。将来形式4・5（日→英）の追加に耐えること（01 確定）。
- 四択の選択肢は、単語の最初の Meaning の MeaningText を「; 」で連結して表示する（本トピックで 01 の文言を更新）。
- テスト内容はカウントダウン画面の間にクライアントへ全ロードし、テスト中はサーバー通信なしで進行する（01 確定）。
- drill のラウンドは未卒業（DrillWord.remaining > 0）の単語を全て出題する（06 確定）。
- 「わからない」（GAVE_UP）は drill の残数計算上 INCORRECT と同じ扱い（02 確定）。

## 検討事項リスト

## 議論・決定

### 出題対象の例外: 意味未登録の単語は除外（確定 2026-06-12）

意味（MeaningText）が 1 件も登録されていない単語は、**全形式共通で問題生成時に出題対象から除外する**。登録フォーム上、意味 0 件の単語は作成可能（`word-form.ts` の meanings 配列に最小件数の制約がない）であり、含めると正解選択肢・解答表示が作れないため。01 の「範囲内全出題」の例外として 01 にも追記した。

- **却下案（生成エラーにする）**: 意味なし単語が 1 語あるだけでその範囲のテストが開始できなくなり、腕試しの手軽さを損なう。
- **却下案（登録側で意味必須に変更）**: 「とりあえず単語だけメモして後で意味を足す」運用を塞ぐ。quiz 設計のスコープ外の変更でもある。
- 開始画面での見せ方（対象件数・注記）は occurrenceNumber なし単語の除外と同列で 04 へ引き継ぎ。

### 選択肢に並べる「意味」の単位（確定 2026-06-12）

形式によって粒度を使い分ける。

- **四択**: 1 選択肢 = 1 単語。表示はその単語の**最初の Meaning（sortOrder 先頭）**の MeaningText を「; 」で連結した文字列（例: `走る; 駆ける`）。2 つ目以降の Meaning（別品詞の意味など）は表示しない。正解・ダミーとも同じルール。
- **多義語選択**: 1 選択肢 = 1 MeaningText。正解集合はその単語の**全 Meaning 横断の全 MeaningText**。

四択の表示は 01 の当初文言「複数の意味がある場合は全て表示し、最初に登録した意味を目立たせる」を覆す決定のため、01・ハブの文言を更新した（運用ルール 4）。

- **却下案（四択で全 Meaning 表示・最初を強調）**: 選択肢が縦に長くなり 4 つ並べたときの一覧性が落ちる。最初の Meaning だけで腕試しの判別には十分。
- **却下案（多義語選択も Meaning 単位）**: 同一 Meaning 内の MeaningText は同義の訳語バリエーションであり、Meaning 単位だと「語義の数」を問う出題にならない。MeaningText 単位で全部選ばせることで多義語の網羅を問う。

### 四択のダミー選択肢（確定 2026-06-12）

- **プール**: 出題対象と同一の Occurrence に紐づく他の単語（出題単語自身を除く）を優先する。MeaningText 未登録の単語は候補外。**重複排除後の有効候補**が 3 語に満たない場合のみ、同一 Occurrence 由来の候補は保持したまま、**不足分だけ**をユーザーの全登録単語から補完する。
  - 採用理由: 同じ教材の単語は文脈が近く紛らわしいため、腕試しのダミーとして質が高い。
  - **却下案（テスト範囲内のみ）**: 範囲が狭い（4 語未満）と選択肢が作れない。
  - **却下案（全登録単語からランダムのみ）**: 教材と無関係な単語が混ざり、消去法で当てやすくなる。
- **選定**: プールから無作為に 3 語選ぶ。品詞の一致等の選定基準は MVP では設けない。
- **重複排除**: ダミー候補の表示対象 MeaningText のいずれかが、正解単語のいずれかの MeaningText と一致（trim 後の完全一致）する場合は候補から除外する（正解が 2 つ見える事故の防止）。ダミー同士の重複も同様に排除。
- **フォールバック**: 全登録単語への補完後も重複排除後の有効候補が 3 語未満なら選択肢数を縮退する（3択・2択＋わからない、最低 2 択）。ダミーが 0 件の場合は問題生成エラーとする。開始画面で形式を選ばせない等の制御は 04 で検討（引き継ぎ）。

### 多義語選択の選択肢構成（確定 2026-06-12）

- 正解選択肢 = その単語の全 MeaningText（各 1 選択肢）。trim 後に同じテキストが複数ある場合（別 Meaning に同じ訳語を登録している等）は 1 選択肢に統合する。
- ダミー候補 = 他単語（出題単語自身を除く）の**全 Meaning 横断の全 MeaningText**（四択と違い最初の Meaning に限定しない）。**同一単語から複数のダミーを取ってよい**。単語の優先順（同一 Occurrence → 不足分のみ全登録単語へ補完）と重複排除（正解集合・ダミー同士と trim 後完全一致なら除外）は四択と同じ。
- **ダミー数は 2〜5 のランダム**（総選択肢数 = 正解数 + 2〜5）。これが 01 の「選択肢の数はランダム」の実現方法。プール不足時はある分まで縮退（最低 1）。ダミーが 0 件の場合は四択と同様に問題生成エラーとする。
- 意味が 1 つしかない単語も除外せず出題する（正解 1 ＋ダミー N。「1 つだけ選ぶ」判断自体が出題になる）。
- **判定**: 選択集合が正解集合と完全一致（全部選び、かつ余計に選ばない）で CORRECT、それ以外は INCORRECT。部分点はなし。
- **「わからない」ボタンを多義語選択にも置く**（GAVE_UP 記録）。3 形式すべてで GAVE_UP が揃い、drill の残数計算（GAVE_UP=INCORRECT 扱い）と一貫する。02 の enum コメントを拡張した。

### 自己判定形式の判定段階（確定 2026-06-12）

解答表示後のボタンは「**合っていた / 間違っていた / 思い浮かばなかった**」の 3 つ。3 つ目は既存 enum の GAVE_UP として記録する（enum 変更不要）。

- 解答表示は全 Meaning を見せる（選択肢ではなく解答提示のため。表示詳細は 04）。
- **却下案（2択のみ）**: 思い浮かばなかった場合と「考えた答えが違った」場合の区別が履歴に残らない。GAVE_UP は既に enum にあり追加コストゼロ。
- **却下案（部分正解あり）**: QuizResult enum への値追加が必要になり、02（確定済み）と drill の残数計算の見直しが発生する。腕試しの粒度として 3 段階で十分。

### 問題データの生成場所: サーバーで全問生成（確定 2026-06-12）

カウントダウン中に、選択肢構成・シャッフルまで済んだ**完成品の問題データ一式**をサーバーで生成し一括返却する。クライアントは表示・採点・回答保持のみ。

- 採用理由: ダミーを範囲外（同一 Occurrence 全体・全登録単語）から引くにはサーバー側のクエリが自然。生成ロジックの所在がサーバーに一元化され、クライアントが薄くなる。将来形式（4・5）の追加もサーバー側の生成器追加で完結する。
- **却下案（素材を渡してクライアント生成）**: drill のラウンド再生成が通信なしでできる利点があるが、ラウンド境界では解答送信の通信が必ず発生するため利点が薄い。生成ロジックがクライアントに乗り、payload（ダミー候補プール）も大きくなる。
- 採点はクライアントで行うため、**正解情報も payload に含む**。DevTools で覗けばカンニング可能だが、任意起動の腕試しアプリであり不正対策は不要と判断（明示的に許容）。
- drill も各ラウンド開始時に同じ生成ロジックでサーバー再生成する（05・06 へ引き継ぎ）。ラウンドごとに選択肢・順序が変わるのはむしろ望ましい。
- 問題データ構造の概形（API・型定義の詳細は 05）:

```ts
// 共通: { format, questions: [...] }
// CHOICE        : { wordId, headword, choices: [{ text }], correctIndex }
// MULTI_MEANING : { wordId, headword, options: [{ text, isCorrect }] }  // シャッフル済み
// SELF_JUDGE    : { wordId, headword, answer: 全Meaningの表示用データ }
```

### ランダム性の実装方針（確定 2026-06-12）

- 生成ロジックは **RNG（`() => number`、`Math.random` 互換）を引数に取る純関数**として実装する。本番は `Math.random` を渡し、ユニットテストはシード付き PRNG を注入して決定的に検証する（`*.unit.test.ts`、DB 不要）。
- シャッフルは Fisher–Yates（偏りのない標準的な配列シャッフル）。出題順・四択の選択肢順・多義語選択の選択肢順に適用する。
- シードの永続化はしない。中断＝破棄（01 確定）のためテスト内容の再現は不要。

### 将来拡張メモ: SRS 導入時の影響範囲

生成ロジックは「出題対象の単語リスト」を入力に取る純関数のため、将来 SRS（SM-2 等）を導入しても変更は**対象選定側**（範囲指定 → スケジュール選定への置き換え）に閉じ、選択肢生成・問題データ構造は無変更で済む。スケジュール属性の置き場は 02 の将来拡張方針（side table 加算）に従う。
