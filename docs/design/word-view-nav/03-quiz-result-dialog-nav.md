# 03. テスト結果一覧 → 詳細ダイアログの順序ソースとナビ実装方式

状態: **確定**（2026-08-07）

## 前提（確定事項の再掲）

このトピックが依存する決定。覆す場合はハブ（README.md）と決定元の両方を更新すること。

## 議論・決定

### 決定 1: 順序ソースは「ダイアログを開いた時点の表示行」のクライアントスナップショットを正とする

前後ナビの順序は、結果一覧でダイアログを開いた時点の表示行（`wrongOnly` フィルタ適用後の `visibleRows`）の wordId 配列とする。隣接判定はすべてクライアント側の配列 index で行い、サーバへの隣接取得は行わない。

- フィルタ OFF なら全行 = 出題順、ON なら誤答行のみ（01 の決定どおり「表示中の行だけを辿る」）
- ダイアログ表示中はフィルタを操作できない（モーダル）ため、開いた時点のスナップショットで順序が陳腐化することはない。閉じて開き直せば再スナップショットされる

採用理由: サーバは出題順を復元できず（ADR-0024。`QuizAnswer` は append-only の解答行のみ）、順序の真実は `rows` 配列にしかない。表示行スナップショットは「一覧に見えている順」とナビ集合が定義上一致する。
却下した代替案: 順序（wordId 配列）をサーバへ渡して隣接をサーバ計算する（順序の正はどのみちクライアントにあり、ラウンドトリップと入力検証を増やすだけで得る情報が無い）。`wrongOnly` を quiz-flow へリフトして親で順序を導出する（`ResultList` の表示専用の関心が親へ漏れる。開いた時点のスナップショット受け渡しで足りる）。

### 決定 2: 順序は `onOpenDialog` の引数で渡し、quiz-flow が `dialogNavOrder` として保持する

- `ResultList` の `onOpenDialog(wordId)` を `onOpenDialog(wordId, navOrder: string[])` に拡張し、`visibleRows.map((r) => r.wordId)` を渡す
- `quiz-flow.tsx` は `dialogNavOrder: string[] | null` state に保持する。結果一覧から開いたとき順序をセットし、`dialogStack` が空になったとき（閉じるボタン・ブラウザバックによる pop のいずれでも）null に戻す。出題中の詳細ボタン経由は従来どおり順序なし（null のまま）
- `WordDetailDialog` へは、スタック深さ 1 のときのみ `navOrder` を渡す（深さ 2 以上 = 関連語スタック先は null → ナビ非表示、01 の決定を維持）
- ダイアログ内の現在位置は `navOrder.indexOf(表示中 wordId)` で解決する（1 語 1 問で wordId は一覧内一意）。prev / next は前後の要素、端（index 0 / 末尾）は disabled。ナビの表示条件は「`navOrder` が非 null」のみとし、`occurrenceId` に依存しない → 全件ブックマークモード（`occurrenceId === null`）でもナビが出る（01 の決定の実現）
- 前後移動は従来どおり `setDialogStack([id])` の置換（深さ 1 維持、履歴エントリ数も不変）。隣接が同期的に分かるため、既存の「隣接応答待ちの間ナビ行を残して両ボタン disabled」「初回は隣接応答が来るまでナビ行を描画しない」という応答待ち状態は不要になり、ナビ行は開いた瞬間から確定表示できる

採用理由: 順序の所有者（結果一覧の表示状態）から消費者（ダイアログ）へ、開くイベントの引数として一度だけ渡すのが最小の結合。`dialogStack` の型・back ガード（`guardDepth`）・出題中ダイアログとの共用構造に変更が無い。
却下した代替案: `dialogStack` を `{ wordId, index }` 等に変える（関連語 push には index が無く型が歪む。順序はスタックと独立した 1 本の配列で十分）。ダイアログの所有を `ResultList` へ移す（back ガードと出題中ダイアログが quiz-flow 所有で共用されており、移すと二重管理になる）。

### 決定 3: `getAdjacentWordsForDialog` action と `findAdjacentWordsByOccurrenceNumber` を廃止する

クライアント配列ナビへの置き換えにより、隣接取得のサーバ経路は不要になる。

- `src/app/quiz/actions.ts` の `getAdjacentWordsForDialog`・`GetAdjacentWordsForDialogResult` と、`src/lib/schema/quiz.ts` の `adjacentWordsInputSchema`（`AdjacentWordsInput`）を削除する
- `src/lib/words-list.ts` の `findAdjacentWordsByOccurrenceNumber` を削除する（プロダクション呼び出しは上記 action の 1 箇所のみ。integration テストの該当ケースも削除）
- ダイアログ側の `navResponse` / `navCache` / `resolveNavView` / `resolveCurrentNav` の隣接応答系 state は、`navOrder` ベースの同期導出に置き換える
- `findAdjacentWordsByOccurrence`（詳細ページ用、02 で拡張対象）は別物であり存続する

採用理由: 順序ソースが二重になる余地を残さない（サーバ隣接とクライアント配列が食い違う可能性を構造的に排除）。利用箇所が 1 経路のみで廃止コストが最小。
却下した代替案: action を残して全件ブックマークモード等の補完に併用する（順序ソースの二重定義そのもの。掲載番号昇順ナビは 01 で廃止確定済みで、残す用途が無い）。

### 決定 4: 見出し語右の `#N` は詳細応答（WordDetail の掲載箇所一覧）から導出する

隣接応答の `current.occurrenceNumber`（廃止）に代わり、表示中の詳細データが持つ掲載箇所一覧から、ダイアログの基準掲載箇所（`dialogOccurrenceId`）に一致する行の `occurrenceNumber` を引いて表示する。

- `dialogOccurrenceId` が null（全件ブックマークモード）または一致する掲載が無い・番号なしの場合は `#N` を出さない（ナビは決定 2 のとおり出る。番号はあくまで掲載箇所コンテキストの情報）
- 詳細と同じ応答から導出するため、「前の単語を残して淡色化している間に番号だけ先に進む」問題は構造的に起きない（既存コメントで警戒していた事象。専用の防御コードが不要になる）

採用理由: 詳細応答に既に含まれる情報で賄え、追加の取得経路・データ伝搬が不要。表示タイミングが見出し語と常に一致する。
却下した代替案: `ResultRow` に `occurrenceNumber` を追加して一覧から供給する（quiz 生成データ〜結果行まで伝搬範囲が広く、詳細応答から引けば足りる。関連語スタック先の表示にも使えない）。

### 決定 5: 削除済み単語の行はナビからスキップしない

削除済み単語の行も順序リストに含めたまま辿る。到達時は既存のエラービュー（「対象の単語が見つかりません。」）を表示し、前後ナビはそのまま操作できる（隣接が配列 index で決まるため、詳細取得の成否とナビの可用性が独立する）。

採用理由: 「表示中の行だけを辿る」（01）の裏返しとして、一覧に見えている行は飛ばさないのが一貫する（削除済み行は一覧に残り、クリックでも開ける。削除済みの明示はモードにより行内バッジまたは残数バッジ側で行われる）。現行実装の「削除済み単語に到達すると隣接応答が null になりナビごと消えて先へ進めない」デッドエンドは、配列ナビへの置き換えで自然に解消する。
却下した代替案: 削除済み行をスキップする（見えている行を黙って飛ばすと一覧とナビが不一致になる。削除判定源が送信応答（`skippedWordIds` / DRILL の確定残数）にありモードごとに判定が分かれるため、順序リスト構築が複雑化する割に得る体験が小さい）。

### 決定 6: 先読みは navOrder の前後 1 件の詳細のみとする（隣接先読みの廃止）

`resolvePrefetchTargets` を再設計する:

- 対象は `navOrder` 上の前後 1 件の未キャッシュ詳細（`kind: "detail"`）のみ。隣接応答の先読み（`kind: "adjacent"`）は廃止する
- 発火条件は「表示中単語の詳細が settle した後」（従来の「詳細と隣接の両方が settle」から簡素化。隣接応答自体が無くなるため）。連続送り中の中間単語で先読みが走らない性質は維持される
- `occurrenceId` への依存を外し、`navOrder` がある間は先読みする → 全件ブックマークモードでも先読みが効くようになる（現状は無効）
- エラー応答（削除済み等）をキャッシュしない既存方針は維持する（削除済みの隣へ移動するたび再取得が走るのは従来どおり許容）
- ADR-0086 本文の該当記述（隣接ナビの先読み）の改訂は 04 のドキュメント更新論点で扱う

採用理由: 先読みの目的（前後移動時の待ち時間削減）に対し、隣接情報は配列で既知になったため詳細のみで足りる。判定条件が減り、対象モードはむしろ広がる。
却下した代替案: 前後 2 件以上の先読みへ拡張する（ADR-0086 で前後 1 件・追い越し許容と確定済みで、覆す動機が無い）。
