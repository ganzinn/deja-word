# 例文音源の抽出（ターゲット1900 例文 mp3 の切り出し）

「英単語ターゲット1900(6訂版)」の例文音源（`tmp/1900_4_all/`、書籍付属の連続 mp3）から、
**英語例文だけ**を 1 語 1 ファイルに切り出して取り込み用ディレクトリを作る手順。
`scripts/extract-example-audio.py` が実装。2026-08-05 に**全 110 ファイル / 全 1900 語で完了**（欠番ゼロ）。

> 音源そのものは著作権があるためリポジトリには含めない。ここに残すのは手順とハマりどころだけ。
> 発音音源（単語のみ）の突合・検証の一般論は [verify-audio-mapping](./verify-audio-mapping.md) を参照。本書はその例文音源版。

## 元データの構造（実測）

- ファイルは `TG1900_4_Sec<NN>_<開始番号>_<終了番号>.mp3` が 110 本（全 1900 語をカバー）。
  **収録範囲はファイル名の 4 桁ゼロ埋め番号から機械的に読める**。
- 1 エントリの構造は「**見出し語(EN) → 日本語訳(1〜2 区間) → 英語例文(末尾の長い区間)**」。
- エントリ間の無音は **1.4 秒以上**、エントリ内の区間間は 0.5〜0.95 秒。→ 閾値 1.2 秒でエントリ分割できる。
- 無音検出は `silencedetect=noise=-35dB:d=0.35` で安定して切れた。
- **区切りアナウンスが単語エントリの間に紛れ込む**（実例: 1578 と 1579 の間に「形容詞編」）。
  品詞セクションの切り替わり位置（#0779 形容詞 / #1000 副詞 / #1341 名詞 / #1501 動詞 など。
  過去の混入実績は `tmp/audio_audit/README.md`）に出るため、**グループ数 = 収録語数と仮定してはいけない**。

## 手順

```sh
# 1) ASR 環境（初回のみ。モデルは初回実行時に ~/.cache/huggingface/ へ自動取得）
python3 -m venv /tmp/asr && /tmp/asr/bin/pip install faster-whisper numpy

# 2) 全ファイル処理（処理済みファイルは report を見てスキップ → 中断しても再実行で続きから）
/tmp/asr/bin/python scripts/extract-example-audio.py

# 特定ファイルだけなら引数で渡す
/tmp/asr/bin/python scripts/extract-example-audio.py tmp/1900_4_all/TG1900_4_Sec16_1574_1600.mp3
```

出力は `tmp/1900_4_split/EN/<掲載番号4桁>_<見出し語>.mp3`（import-audio のファイル名規約）と
`tmp/1900_4_split/report.jsonl`（1 語 1 行の処理記録。resume 判定とレビューの根拠を兼ねる）。

### 並列実行（壁時計はほぼ縮まない。実測値を先に読むこと）

**8 コアの Apple Silicon では 3 プロセス並列にしても速くならなかった**（実測）:

| 実行形態 | 実測 | スループット |
| --- | --- | --- |
| 単プロセス（1 ファイル 14 語） | 2 分 34 秒 / CPU 364% | 5.4 語/分 |
| 3 プロセス並列（108 ファイル 1859 語） | 5 時間 28 分 | 5.7 語/分 |

単プロセスで既に約 3.6 コアを使っており、8 コアといっても性能コアは 4 つなので**そこで飽和している**。
全 1900 語で 5〜6 時間かかる前提で、resume を使って分割実行する計画を立てるほうが実効的。

それでも並列にする場合は、`report.jsonl` への同時追記を避けるため
**`--report` をプロセスごとに分け、最後に統合する**（同時追記は行が壊れうる）。

```sh
# 3 分割（i 番目のプロセスは i, i+3, i+6, ... 番目のファイル）
for i in 0 1 2; do
  OMP_NUM_THREADS=3 nohup /tmp/asr/bin/python scripts/extract-example-audio.py \
    $(ls tmp/1900_4_all/*.mp3 | awk "NR % 3 == $i") \
    --report tmp/1900_4_split/report.part$i.jsonl > /tmp/asr_run$i.log 2>&1 &
done

# 統合（掲載番号順・1 語 1 行に正規化して report.jsonl へ）
python3 -c "
import json, pathlib
d = pathlib.Path('tmp/1900_4_split')
recs = {}
for p in [d/'report.jsonl'] + sorted(d.glob('report.part*.jsonl')):
    if p.exists():
        for l in open(p):
            if l.strip(): r = json.loads(l); recs[r['num']] = r
with open(d/'report.jsonl', 'w') as f:
    for n in sorted(recs): f.write(json.dumps(recs[n], ensure_ascii=False) + '\n')
for p in d.glob('report.part*.jsonl'): p.unlink()
print(len(recs))"
```

## 運用方針: 一発で綺麗に分割できなくてよい

**実施と検証を繰り返し、失敗した語だけ個別対応して、最終的に全 1900 語が揃えば良い**という方針で回す。
スクリプトもその前提の設計（ファイル単位の resume・失敗ファイルは未処理のまま報告・`CHECK` は人手レビュー行き）。

1. **全件実行** — 途中で中断してもよい。再実行すれば report にあるファイルはスキップされる
2. **失敗ファイルの個別再実行** — エントリ数不一致で止まったファイルを潰す。`--redo` は対象ファイルの
   旧記録を report から除去してから追記するので、何度やり直しても report は 1 語 1 行に保たれる。
   なお 2026-08-05 の 21 ファイルは**無音検出パラメータの調整では直らず、分類ルールの修正で全ファイル解決した**。
   まず原因を特定すること（パラメータ探索から入らない）

   **パラメータを振る前に、失敗ファイルの ASR 結果を JSON にキャッシュして分類ルールをオフラインで検証すること**。
   ASR は 1 ファイル約 2.5 分かかるが、区間分割・言語判定・グルーピングの結果さえ持っておけば
   ルールの試行は無料で何度でも回せる（グルーピング閾値 `--entry-gap` もキャッシュ上で振り直せる）。
   2026-08-05 の 21 ファイル一括修正はこの手順で当てた（キャッシュ 1 回 → ルール修正 → 21/21 一致を確認 → 本実行）

   ```sh
   /tmp/asr/bin/python scripts/extract-example-audio.py tmp/1900_4_all/<file>.mp3 \
     --redo --noise -38 --min-silence 0.3 --entry-gap 1.1   # 値は状況に応じて
   ```

3. **`CHECK` のレビュー** — `verdict=CHECK` の行を聴くか transcripts を見て判断。ASR の誤認識
   （短い語・同音異義語）が大半で音源は正しいことが多い。本当にズレていたら該当ファイルを 2 と同様に再処理
4. **どうしても割れないものは手動切り出し** — 該当時刻を聴いて特定し、ffmpeg で直接切る。
   切り出し後は必ず ASR で読ませて内容を確認する

   ```sh
   ffmpeg -ss <start> -to <end> -i tmp/1900_4_all/<file>.mp3 -c:a libmp3lame -q:a 2 \
     tmp/1900_4_split/EN/<番号4桁>_<見出し語>.mp3
   ```

5. **最後に完全性チェック** — 欠番が無いことを確認して完了

   ```sh
   python3 -c "
   from pathlib import Path
   have = {int(p.name[:4]) for p in Path('tmp/1900_4_split/EN').glob('*.mp3')}
   missing = sorted(set(range(1, 1901)) - have)
   print(f'{len(have)}/1900, 欠番: {missing or \"なし\"}')"
   ```

6. **切り出し済みファイルの全件読み直し監査** — 日本語音声の混入を潰す（下の「全件監査」を参照）

### スクリプトがやること

1. `silencedetect` で発話区間に分割 → 無音 1.2 秒以上でエントリにグルーピング
2. 全区間を faster-whisper `small`（多言語）で文字起こし（日本語/英語の判別が構造分類に必要）
3. **日本語区間の判定**（言語判定だけに頼らない。下の「ハマりどころ」参照）:
   `lang != en` か日本語文字を含めば日本語。英語判定でも確信度 0.90 未満なら
   `language="ja"` 強制で読み直し、日本語文字が出れば日本語とみなす
4. **例文が離れて切れたグループの再結合**: 「全区間が英語 かつ 先頭区間が 1.8 秒以上（＝短い見出し語読み上げで
   始まっていない）」グループは前のエントリの例文の続きとして戻す
5. **構造でアナウンスを除外**: 「日本語区間の後ろに英語区間で終わる」形をしていないグループは単語エントリではない
6. 単語エントリ数がファイル名の収録範囲と一致することを検証（不一致ならそのファイルは未処理のまま報告して続行）
7. 例文 = **最後の日本語区間より後ろの全区間**。前 0.2 秒 / 後 0.3 秒のパディング付きで
   `libmp3lame -q:a 2` により再エンコードして切り出し
8. 切り出した実ファイルを**別モデル `small.en` で読み直し**、見出し語が例文に含まれるかを判定
   （見出し語読み上げ区間の照合と合わせて `OK` / `CHECK` を report に記録）

### 全件監査（切り出し後）

`OK`/`CHECK` 判定は「見出し語が例文にあるか」しか見ないので、**例文の頭に日本語訳が混入していても `OK` になる**
（日本語が英語と誤判定された場合に起きうる）。取り込み前に切り出し済み mp3 を多言語モデルで読み直し、
日本語文字・非英語判定・空ファイルをゼロにしておくこと。1900 件で約 2 時間（3 プロセス並列、実測 14 ファイル/分）。

```sh
python3 - <<'PY'
import json, re
from pathlib import Path
from faster_whisper import WhisperModel   # /tmp/asr/bin/python で実行する
JA = re.compile(r"[぀-ヿ一-鿿]")
m = WhisperModel("small", device="cpu", compute_type="int8")
bad = []
for p in sorted(Path("tmp/1900_4_split/EN").glob("*.mp3")):
    segs, info = m.transcribe(str(p), beam_size=5)
    t = "".join(s.text for s in segs).strip()
    if JA.search(t) or info.language != "en" or len(re.findall(r"[A-Za-z']+", t)) < 3:
        bad.append((p.name, info.language, t))
print(f"要確認 {len(bad)} 件"); [print(" ", *b) for b in bad]
PY
```

## ハマりどころ・知見

- **失敗の主因は「短い日本語訳が英語と誤判定されること」**（全 110 ファイル中 21 ファイルがこれで停止）。
  「規範」→ `"Kihan!"`、「指紋」→ `"Shimon"`、「方法」→ `"Ho Ho"` のように**日本語文字を含まない英語テキスト**として
  出てくるため、`lang == "en"` だけ見ると日本語区間が消える。結果、単語エントリが「日本語区間を持たない」形になり
  区切りアナウンスとして丸ごと除外されてエントリ数が合わなくなる。
  対策は**確信度の併用**: この誤判定時の `language_probability` は 0.4〜0.9 と低く、
  正しい英語区間（見出し語 0.97+ / 例文 0.99+）とはっきり分かれる。0.90 未満なら `language="ja"` で読み直し、
  日本語文字が出るかで判定する。
- **例文が途中ポーズで 2 区間に割れることがある**（実例: 1595 susceptible、文中の休止 0.36 秒）。
  「最後の日本語区間より後ろの**全区間**」を結合するルールで正しく 1 文になる。
- **例文がエントリ境界（1.2 秒）を超える無音で切り離されることがある**（実例: 115 prove、1350 horror）。
  グルーピングだけでは前のエントリに戻らないので、「全区間が英語かつ先頭区間が長い」グループは
  例文の続きとみなして前のグループに結合する。`--entry-gap` を上げて対処すると別エントリ同士が
  くっつくので、閾値ではなく構造で直すこと。
- **短い日本語区間の言語判定は当てにならない**（`zh` と誤判定して中国語字幕クレジットを幻覚した実例あり）。
  分類は「日本語 or 英語」の 2 値でしか使わないこと。
- **`CHECK` = 誤りではなく人手レビュー対象**。実例: 1594 vain は見出し語読み上げの ASR が "Then" になったが、
  例文・音源自体は正しかった。短い語の誤認識パターンは [verify-audio-mapping](./verify-audio-mapping.md#asr-の誤りと音源の誤りを切り分ける) を参照。
  全 1900 語での `CHECK` は 94 件で、**内訳は「不規則活用」と「ASR 誤認識」だけ・音源のズレはゼロ**だった。
  レビューは活用形を吸収する緩いマッチで自動的に絞り込める（94 件 → 目視 12 件まで落ちた）。
  残った 12 件も strike→struck / weave→woven / undergo→underwent / versus→"vs" のような不規則活用と、
  surf→"serves"、confine→"can find"、ward→"wore it" のような ASR 誤認識だった。
- **import-audio のメモ不一致警告では例文音源のズレは検出できない**。ファイル名メモは words.csv（期待値）から
  生成しており DB 見出し語と必ず一致するため、音声内容の検証は本スクリプトの `OK`/`CHECK` 判定と
  上の「全件監査」だけが防衛線になる。**両方を潰してから取り込むこと**
  （`CHECK` は見出し語の対応、全件監査は日本語の混入と、見ている軸が違う）。
- 処理コストは Whisper の 30 秒ウィンドウ単位（区間の長短に関わらず一定）。1 エントリあたり約 4〜5 区間
  ＋検証 1 回。**全 1900 語では数時間規模**になるので、report による resume を前提に分割実行してよい。
  並列化してもコア秒総量は減らない（[verify-audio-mapping](./verify-audio-mapping.md) の実測どおり）。
  **壁時計時間も縮まなかった**（上の「並列実行」の実測表）。1 プロセスの CPU 使用率が 364% でも
  「まだ 4 コア余っている」とは読めない（性能コアが 4 つで既に飽和している）。
- `ffmpeg -ss` は再エンコード時は正確にサンプル位置で切れる（stream copy はフレーム境界に丸まるので使わない）。

## 実績

- **完了**: 全 110 ファイル / 全 1900 語を切り出し済み（2026-08-05、欠番ゼロ）。
  出力 `tmp/1900_4_split/EN/`、記録 `tmp/1900_4_split/report.jsonl`（1900 行）、
  一覧 `tmp/1900_4_split/examples.csv`（掲載番号・見出し語・ファイル名・秒数・例文テキスト・判定）。
  例文テキストは ASR の読み取りなので書籍本文と完全一致はしない（内容確認用の記録という位置づけ）。
- **経過**: 全 110 ファイル中 89 ファイルが一発成功 / 21 ファイルがエントリ数不一致で停止 →
  停止分の ASR 結果をキャッシュして分類ルールを修正（日本語判定の確信度併用・例文の再結合）→
  21/21 成功。全 1900 件の読み直し監査で日本語混入・非英語・空ファイルはいずれもゼロ。
  ファイル名も `tmp/target1900.words.csv` と 1900/1900 で一致。
- **取り込み方法は未確定**: 登録先は掲載箇所種別「例文」だが、既存 [import-audio](./import-audio.md) は
  対象単語の先頭 Meaning の発音音源（`pronunciation.mp3`）に登録する仕様。例文への音源登録の
  スキーマ上の置き場・スクリプト対応は取り込み着手時に設計する。
