# セキュリティ設計時チェックリスト

diff レビューでは検知できない（コードの形からは NG 判定できない）セキュリティ観点集。新機能の設計時、特にセキュリティ境界（認証・認可・データ所有・外部入出力）に触れるトピックで参照する。diff レビューで機械的に判定できる観点は `.claude/skills/sec-review/SKILL.md` 側にあり、そちらとは重複させない。

各項目は「このコードベースの現行アーキテクチャが持つ前提」であり、設計がその前提を破る場合は明示的な決定（採用理由・却下案）として設計ドキュメントに残すこと。

## データ所有・テナント分離

- **新しい共有 / system データ種別を導入するとき**: pass-through セマンティクス（一般ユーザーは閲覧・並べ替え・自分の子データ付加まで可 / body 編集・削除・改名は不可）を row-policy の拡張としてどう定義するかを設計時に決める。既存の word 系は `src/lib/words/policy/row-policy.ts` に集約されており、新種別で別ルールにするなら独立した policy モジュールを作る（暗黙の例外を handler に散らさない）
- **read/write 非対称の維持**: 「read は `scopedOwnerIds`（system + 自分）、write は自分の行のみ」が全機能共通の原則。新機能で「system 行にユーザーが書ける」要件が出たら、それは row-policy 拡張案件であり、handler 内の条件分岐で済ませない

## ルーティング・権限モデル

- **新トップレベルルートセグメント**: `src/proxy.ts` の matcher に足すか、page の self-guard のみにするかを設計時に決める。matcher への追加漏れは実行時に気づけない（self-guard があれば安全側だが、cookie 無しアクセスが sign-in リダイレクトでなく各ページ依存の挙動になる）
- **権限モデルの限界**: role カラムは存在せず、管理者 = `SYSTEM_USER_ID` との一致のみ。「一部ユーザーに特別な権限」「複数の管理者」「権限の委譲」が要件に入った時点で、単一 system ユーザーモデルでは表現できない — スキーマ変更を伴う設計判断として扱う

## 外部との境界

- **生成 URL の origin 戦略**: 招待・確認リンク等の URL 生成は、現状 `resolveOrigin()`（`src/app/admin/users/actions.ts`）がリクエストヘッダ（`x-forwarded-host` / `host`）に依存している。admin 限定 + リンク手動送付という前提で緩和されているが、リンクを自動送信する機能（メール送信の導入等）を設計する際は、ヘッダ由来をやめ `BETTER_AUTH_URL` / `VERCEL_PROJECT_PRODUCTION_URL` へのピン留めを必須にする
- **blob は public 前提**: Vercel Blob は `access: "public"` + random suffix で運用しており、URL を知っていれば誰でも読める。非公開であるべきデータ（個人情報・非共有コンテンツ）を blob に載せる設計は現行の blob client では不可 — private access 化かアクセス制御付き配信の設計が先に必要
- **CSRF**: 書込みは Server Action の same-origin 保護に依存している。action 以外の書込みエンドポイント（route handler での POST、webhook 受信等）を新設する設計では、CSRF / 認証方式を個別に決める

## 認証まわり

- **レート制限・ブルートフォース**: Better Auth の rateLimit は未設定（デフォルト任せ）。サインイン・パスワードリセット等の auth 面を触る設計時は、better-auth-security-best-practices skill を参照してレート制限の要否を判断する
- **セッション無効化ポリシー**: email 変更・パスワードリセット時に既存セッションを失効させるかは現状未定義。アカウント乗っ取りからの回復シナリオを扱う設計では明示的に決める
- **トークンの副作用マップ**: 検証リンク・リセットトークンは「踏んだ人を誰としてログインさせるか / emailVerified をいつ立てるか」の副作用を持つ。auth フローを追加・変更する設計では、リンクごとの副作用（誰が・どの状態で・何になるか）を表にして設計ドキュメントに残す（過去事例: PR #61 — パスワード未設定ユーザーのメール変更で自動ログインが成立していた）
